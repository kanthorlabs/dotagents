`change_password` in `api/auth/password.py` leaves every refresh token of the user in `refresh_tokens`, so a stolen phone keeps renewing its session for 30 days. Aelita recommends that `change_password` deletes all refresh tokens of the user before it issues the new pair. This meets SR-12 and costs one `DELETE`.

**Timeline without the fix**

1. The user signs in on a phone and a laptop. `issue_tokens` stores one `refresh_tokens` row per device, valid for `REFRESH_TTL` of 30 days.
2. Someone steals the phone.
3. The user changes the password on the laptop. `change_password` updates `password_hash`.
4. `change_password` calls `issue_tokens` for the laptop. It deletes no row in `refresh_tokens`.
5. The access token of the phone expires within `ACCESS_TTL` of 15 minutes. The phone calls `POST /auth/refresh`.
6. `refresh_session` finds the phone row and issues a new pair. It never looks at the password. The thief keeps access for 30 days and can renew it again.

**Timeline with the fix**, diverges at step 4.

4. `change_password` runs `DELETE FROM refresh_tokens WHERE user_id = %s`. Then it calls `issue_tokens` for the laptop.
5. The access token of the phone expires within 15 minutes. The phone calls `POST /auth/refresh`.
6. `refresh_session` finds no row and raises `invalid refresh token`. The thief loses access at most 15 minutes after step 3. The laptop holds the new pair and stays logged in.

**What changes**

- `api/auth/password.py`: add one `db.execute("DELETE FROM refresh_tokens WHERE user_id = %s", user.id)` between the `UPDATE` and `issue_tokens`. The old laptop row goes too, and the new pair replaces it.
- `api/auth/middleware.py`: no change. It stays free of database and Redis reads at 2,500 requests per second.

**Recommendation.** Aelita recommends the refresh-token purge, because the 15-minute access token already matches the SR-12 deadline. It removes the cause: the refresh path never learns about the password change. It can break in one case. A refresh in flight during step 4 can insert a new row after the `DELETE`, because `refresh_session` deletes its row and inserts the next one in separate statements. The window is milliseconds. Running the `UPDATE`, the `DELETE` and the insert in one transaction closes it, if `db` supports that.

**Alternative: a `token_version` claim checked in `authenticate`.** The password change bumps a counter in Redis `quayside-cache`, and the middleware rejects older access tokens. Revocation is instant, not 15 minutes. It adds a Redis read to every request and breaks the stateless rule in `docs/architecture.md`. It becomes the primary if the requirement drops to seconds.

**Question.** Do you approve the refresh-token purge in `change_password`, or do you want the `token_version` alternative?
