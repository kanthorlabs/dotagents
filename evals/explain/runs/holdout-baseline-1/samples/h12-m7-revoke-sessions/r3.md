`change_password` in `api/auth/password.py` leaves every refresh token of the user alive, so a stolen phone keeps access for up to 30 days. Aelita recommends deleting all refresh tokens of the user in `change_password` before it issues the new pair. This meets SR-12 with no change to `middleware.py`.

**Existing behaviour**

1. `change_password` checks the old password and updates `password_hash`.
2. It calls `issue_tokens` for the current device. That adds one row to `refresh_tokens`.
3. It deletes no existing row.
4. `refresh_session` accepts any unexpired row and issues a new pair. Each refresh renews the 30-day `REFRESH_TTL`.

**Timeline without the fix**

1. The user is logged in on a laptop and a phone. `refresh_tokens` holds one row per device.
2. A thief steals the phone.
3. The user changes the password on the laptop. `change_password` updates `password_hash` and issues a new laptop pair.
4. The phone row in `refresh_tokens` is untouched.
5. The phone access token expires after 15 minutes. The thief calls `POST /auth/refresh` with the phone refresh token.
6. `refresh_session` finds the row and issues a new pair. The thief stays logged in after the password change, which is the SR-12 failure.

**Timeline with the fix**, diverges at step 4.

4. `change_password` runs `DELETE FROM refresh_tokens WHERE user_id = %s`. This removes the phone row and the old laptop row.
5. `change_password` calls `issue_tokens` for the laptop. The laptop has one new row.
6. The phone access token stays valid for at most 15 minutes. Then the thief calls `POST /auth/refresh` and `refresh_session` finds no row. It raises `invalid refresh token`. The laptop stays logged in.

**What changes**

- `api/auth/password.py`: add a `DELETE FROM refresh_tokens WHERE user_id = %s` statement after the `UPDATE users` and before `issue_tokens`. The old behaviour kept all rows.
- `api/auth/tokens.py`: no change. `ACCESS_TTL` of 15 minutes is what bounds the window to the SR-12 requirement.
- `api/auth/middleware.py`: no change. It still reads neither the database nor Redis.

**Recommendation.** Aelita recommends deleting the refresh tokens, because the root cause is that the refresh token outlives the password. It costs one `DELETE` per password change and nothing per request. Two things can break it:

- **Race:** a refresh in flight on the phone could insert a row just after the `DELETE`. Running the `UPDATE`, the `DELETE` and the `issue_tokens` insert in one transaction narrows the race.
- **Access tokens:** they are not revoked. Each one lives until its own expiry, up to 15 minutes, which the requirement allows.

**Alternative: a `token_version` claim checked in `middleware.py`.** Each access token carries the version of the user, and a password change bumps it. It ends other sessions at once. It needs a Redis read on every request at about 2,500 requests per second, and it breaks the rule that `middleware.py` reads no store. It becomes the primary if the requirement tightens from 15 minutes to immediate.

**Alternative: rotate `SIGNING_KEY`.** It is one change, but it logs out every user and the laptop too. It fails the requirement that the changing device stays logged in.

**Question.** Does Aelita add the `DELETE` to `change_password` inside one transaction, or do you want the immediate-revocation alternative with the Redis check?
