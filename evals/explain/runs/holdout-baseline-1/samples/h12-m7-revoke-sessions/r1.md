`change_password` in `api/auth/password.py` never revokes the user's `refresh_tokens` rows, so other devices keep renewing their sessions. Aelita recommends deleting all of the user's refresh tokens inside `change_password` before it issues the new pair. It costs one `DELETE` per password change.

**Timeline without the fix**

1. Noor logs in on a phone and a laptop. `issue_tokens` stores two `refresh_tokens` rows, each valid for 30 days.
2. A thief steals the phone.
3. Noor changes the password on the laptop. `change_password` updates `password_hash`.
4. `change_password` calls `issue_tokens` for the laptop. It only inserts a row, so the phone row stays.
5. The access token of the thief expires after 15 minutes. The thief calls `POST /auth/refresh`, and `refresh_session` finds the phone row. It never checks the password or when the password changed.
6. `refresh_session` issues a new refresh token with a fresh 30-day expiry. The thief renews it forever. The gap is worse than the "up to 30 days" in SR-12.

**Timeline with the fix**, diverges at step 4.

4. `change_password` deletes every `refresh_tokens` row of Noor. Then it calls `issue_tokens`, which inserts one row for the laptop.
5. The access token of the thief expires within 15 minutes. `refresh_session` finds no row and raises `PermissionError("invalid refresh token")`.
6. The thief is logged out within 15 minutes, as SR-12 requires. The laptop keeps its new pair.

**What changes**

- `api/auth/password.py`: add `DELETE FROM refresh_tokens WHERE user_id = %s` in `change_password`. It runs after the `UPDATE users` and before `issue_tokens`. The `UPDATE`, the `DELETE` and the insert in `issue_tokens` should share one transaction. I did not check whether `api.db` supports transactions.
- `api/auth/middleware.py`: no change. It stays stateless.

**Recommendation.** Aelita recommends the refresh-token delete. `ACCESS_TTL` is already 15 minutes, so the delete alone meets the SR-12 limit. It adds no read to the 2,500 requests per second that the middleware handles. I delete every row, not "every row except this device". `device_name` is a free label that two devices can share, so it cannot identify the current device safely. The cost is that the laptop gets a new refresh token. One race can break it: a `refresh_session` call already in flight on the phone can insert a fresh row after the `DELETE`. The transaction narrows that window but does not close it.

**Alternative: a `token_version` claim checked in the middleware.** The password change bumps a per-user counter, and `authenticate` compares it to the claim in the token. It ends sessions immediately, not within 15 minutes. It costs a Redis read on every request, and it breaks the stateless design in `docs/architecture.md`. It becomes the primary if the requirement changes to immediate logout.

**Rejected: rotating `SIGNING_KEY`.** It logs out every user and also the device that changed the password. That contradicts SR-12.
