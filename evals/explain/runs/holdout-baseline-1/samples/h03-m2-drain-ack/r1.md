`lantern-worker` loses these uploads because `consume.py:22` sets `auto_ack=True`, so RabbitMQ deletes each job on delivery. Kubernetes then SIGKILLs the pod mid-render. Aelita recommends acknowledging each job only after it finishes.

**Timeline without the fix**

1. RabbitMQ delivers jobs to `lantern-worker-7f9c-2` and deletes each one on delivery. Nothing limits prefetch, so the pool queue fills.
2. At 14:02:05 to 14:02:07, u-88217, u-88218 and u-88219 start as videos. With u-88213, all 4 threads are busy. A video takes 25 to 70 seconds.
3. At 14:02:10, SIGTERM arrives. `stop_consuming` runs and `drain` sets a 60s deadline. `values-prod.yaml:4` gives the pod only 20s.
4. At 14:02:21, u-88213 finishes. `pool.shutdown(wait=False)` keeps queued work, so u-88220 and u-88221 start after SIGTERM.
5. At 14:02:30, kubelet sends SIGKILL. The drain deadline of 14:03:10 never arrives. u-88217, u-88218, u-88219 and u-88221 die mid-render, so no thread can log an error.
6. RabbitMQ holds no copy of those 4 jobs. The upload page shows a placeholder and no error, as `docs/thumbnails.md:6` says.

**Timeline with the fix**, diverges at step 1.

1. RabbitMQ delivers at most `CONCURRENCY` unacked jobs. It keeps each job until the worker acks it.
4. At 14:02:21, u-88213 finishes and is acked. The queued jobs are cancelled and never start. They stay unacked.
5. At 14:02:30, kubelet sends SIGKILL. The connection drops.
6. RabbitMQ requeues every unacked job. Another worker renders u-88217, u-88218, u-88219 and u-88221. All 4 get thumbnails.

**What changes**

- `worker/consume.py` old behaviour: `auto_ack=True` and no prefetch. New behaviour: `auto_ack=False` and `channel.basic_qos(prefetch_count=settings.CONCURRENCY)`. `on_message` passes `method.delivery_tag` to `handle`. After `handle` succeeds, the worker thread calls `connection.add_callback_threadsafe` to run `channel.basic_ack`, because pika is not thread-safe. On an exception, it nacks with `requeue=True`.
- `worker/lifecycle.py` old behaviour: `pool.shutdown(wait=False)` keeps queued jobs. New behaviour: `pool.shutdown(wait=False, cancel_futures=True)`.
- `deploy/helm/values-prod.yaml` add: `LANTERN_DRAIN_SECONDS: "15"`. The drain deadline must stay below the 20s grace period.

**Recommendation.** Aelita recommends the manual ack. It removes the root cause, which is that the broker forgets a job before the work is done. It also covers OOM kills and node loss. The cost is that a pod killed between `record_usage` and the ack redelivers the job, and the thumbnail is billed twice. Whether `meter.internal` dedups on `ref` is unverified. Its code is outside this repository (`docs/billing.md:4`). The Billing team can settle it.

**Alternative: raise the grace period.** Keep `auto_ack=True` and set `terminationGracePeriodSeconds: 90` with `LANTERN_DRAIN_SECONDS: "80"`. It is a config-only change with no double-billing risk. It still loses jobs on OOM or node loss, and it slows every deploy. It becomes the primary if the consumer code cannot change this week.
