`lantern-worker` loses the jobs that are still queued or running when the pod is killed. `auto_ack=True` deletes each message from RabbitMQ on delivery. The drain window is 60s, but Kubernetes kills the pod after 20s. Aelita recommends manual acks with a prefetch limit, plus a longer grace period.

**Existing behaviour**

1. `worker/consume.py:22` consumes `thumbnails` with `auto_ack=True` and no prefetch limit. RabbitMQ deletes each message on delivery and pushes the backlog to the worker.
2. `on_message` submits each job to a `ThreadPoolExecutor` with `CONCURRENCY` 4. Jobs beyond 4 wait in the pool queue in memory.
3. On SIGTERM, `channel.stop_consuming()` runs, then `drain` waits up to `DRAIN_SECONDS`, which is 60 (`worker/settings.py:5`).
4. `deploy/helm/values-prod.yaml` sets `terminationGracePeriodSeconds: 20`. Video jobs take 25 to 70s (`docs/thumbnails.md`).

**Timeline without the fix**

1. 14:02:05 to 14:02:07: `lantern-worker-7f9c-2` starts videos u-88217, u-88218 and u-88219. u-88213 is still running, so all 4 threads are busy.
2. 14:02:10: SIGTERM arrives. Consuming stops and `drain` starts with a 60s deadline.
3. RabbitMQ already deleted every delivered message. Jobs waiting in the pool queue exist only in worker memory.
4. 14:02:21: u-88213 finishes. u-88220 and u-88221 start from the pool queue.
5. 14:02:30: kubelet sends SIGKILL, because the 20s grace period expired. `drain` would have waited until 14:03:10.
6. u-88217, u-88218, u-88219 and u-88221 never log `job done`. The broker has no copy, so they are never retried. The upload page shows the placeholder forever, with no error.

**Timeline with the fix**, diverges at step 3.

3. `basic_qos(prefetch_count=CONCURRENCY)` limits the worker to 4 unacked messages. The broker keeps the rest.
4. 14:02:21: u-88213 finishes and is acked. No new job arrives, because consuming has stopped.
5. 14:02:30: SIGKILL closes the connection. RabbitMQ requeues the unacked u-88217, u-88218 and u-88219.
6. Another worker pod consumes them and writes the thumbnails. No upload is lost.

**What changes**

- `worker/consume.py` old behaviour: `auto_ack=True`, and `on_message` calls `pool.submit(handle, body)`. New behaviour: add `channel.basic_qos(prefetch_count=settings.CONCURRENCY)` and `auto_ack=False`. After `handle` returns, the pool thread acks through `connection.add_callback_threadsafe`, because pika's `BlockingConnection` is not thread-safe.
- `worker/lifecycle.py` old behaviour: `drain` only sleeps in its loop. New behaviour: `drain` takes the connection and calls `connection.process_data_events(time_limit=0.5)` in the loop, so acks of jobs that finish during the drain are sent.
- `deploy/helm/values-prod.yaml` old value: `terminationGracePeriodSeconds: 20`. New value: `90`. Add `LANTERN_DRAIN_SECONDS: "75"` so the drain ends before SIGKILL and covers the 70s video worst case.

**Recommendation.** Aelita recommends manual acks with prefetch and the longer grace period. Manual acks remove the cause, because a job leaves the broker only after it succeeds. This also covers OOM kills and node loss, which a grace period cannot. The cost is one redelivery risk. If a pod dies after `record_usage` but before the ack, the job reruns and may bill twice. `record_usage` already sends `ref=upload_id`, but `meter.internal` is outside this repository. I cannot verify that it ignores duplicate refs. Also, `worker/render.py` is imported by `handler.py` but is not in the repository, so I did not read it.

**Alternative: config only.** Set the grace period to 90 and the drain to 75, with no code change. It is the smallest change. It still loses jobs on crashes and on any drain that overruns. It becomes the primary only if code changes are blocked.
