Pointing `osprey-nightly-report` at `pg-osprey-2` by changing only the secret makes the job fail at the churn query. Aelita recommends moving the reads to the replica and keeping one small write on the primary.

**Existing behaviour**

1. `deploy/cronjob.yaml` gives the job `DATABASE_URL` from secret `osprey-primary`.
2. `jobs/nightly_report.py` opens one connection with it and uses it for everything.
3. `reports/queries.py` reads invoices, then runs `CREATE TEMP TABLE churn_window` and reads it back.
4. `reports/runs.py` runs `INSERT INTO report_runs` and commits.
5. `logs/primary-load-2026-10-26.txt` shows the 01:00 to 01:22 run drives `pg-osprey-1` to 88% CPU. Checkout API p95 rises from 340 ms to 1,900 ms.

**Timeline without the fix**

1. At 01:00 UTC `osprey-nightly-report` starts with `DATABASE_URL` from `osprey-replica`.
2. The connection to `pg-osprey-2` succeeds.
3. `revenue_by_region` runs as a read and succeeds.
4. `churn_by_plan` runs `CREATE TEMP TABLE`. The hot standby rejects it, as `docs/database.md` states.
5. The job exits with an error. `write_pdf` never runs, so no PDF exists.
6. `record_run` never runs. The nightly report fails every night and `restartPolicy: Never` does not retry.

**Timeline with the fix**, diverges at step 4.

4. `churn_by_plan` runs one query with a CTE in place of the temp table. The replica accepts it.
5. `write_pdf` writes `nightly-<day>.pdf` as before.
6. `record_run` opens a short connection to `pg-osprey-1` and inserts one row into `report_runs`. The heavy reads stay off the primary.

**What changes**

- `deploy/cronjob.yaml`: `DATABASE_URL` stays on `osprey-primary`. Add `REPLICA_DATABASE_URL` from `osprey-replica`, key `url`.
- `reports/queries.py`: delete `CHURN_WINDOW`. Fold its select into `CHURN_BY_PLAN` as `WITH churn_window AS (...)`. `churn_by_plan` then runs one `execute`.
- `jobs/nightly_report.py`: open the read connection with `REPLICA_DATABASE_URL`. Open a second connection with `DATABASE_URL` only for `record_run`.

**Recommendation.** Aelita recommends this split because the replica rejects all writes and the job needs exactly one. The CTE removes the temp table instead of working around it. The cost is a second connection and a second secret. Two things can break:
- **Lag:** p99 is 2 seconds, and the job reports on yesterday's data at 01:00, so lag does not matter.
- **Long queries:** a long query on a hot standby can be cancelled by replication conflicts. No file in the repository shows the standby's settings, so I could not check this. The first run will show it.

**Alternative: leave the job on the primary and reschedule it.** It needs no code change. It costs the same 88% CPU spike at a quieter hour. It becomes the primary if checkout traffic is near zero at some hour.
