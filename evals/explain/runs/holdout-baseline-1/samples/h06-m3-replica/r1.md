Pointing `osprey-nightly-report` at `pg-osprey-2` alone makes the job fail, because the job writes twice and the replica rejects every write. Aelita recommends that the job reads from the replica and writes its one row to the primary.

**Timeline without the fix**, with only the secret in `deploy/cronjob.yaml` swapped to `osprey-replica`:

1. The cron starts at 01:00 UTC. `DATABASE_URL` now points at `pg-osprey-2`.
2. `jobs/nightly_report.py` connects to the hot standby.
3. `revenue_by_region` runs a plain `SELECT` and succeeds.
4. `churn_by_plan` runs `CREATE TEMP TABLE churn_window`. The standby rejects it, as `docs/database.md:5` says.
5. `psycopg` raises and the job exits non-zero. `write_pdf` and `record_run` never run.
6. No PDF exists and `report_runs` has no row for that day.

**Timeline with the fix**, diverges at step 4.

4. `churn_by_plan` runs one `SELECT` that has the 30-day filter as a subquery. The standby accepts it.
5. `write_pdf` writes `nightly-<day>.pdf`.
6. `record_run` uses a second connection to `pg-osprey-1`. It inserts one row and commits.

**What changes**

- `deploy/cronjob.yaml`: add env `REPLICA_DATABASE_URL` from secret `osprey-replica`, key `url`. `DATABASE_URL` stays on `osprey-primary`.
- `jobs/nightly_report.py`: `main` opens a read connection from `REPLICA_DATABASE_URL`. `record_run` gets a separate connection from `DATABASE_URL`.
- `reports/queries.py`: delete `CHURN_WINDOW`. `CHURN_BY_PLAN` selects from the same filter as a subquery. `churn_by_plan` runs one statement instead of two.

**Recommendation.** Aelita recommends the split connections. The job reads and writes through one connection today, and the replica cannot write. The split moves the heavy reads off the primary, and the primary keeps one tiny insert. `logs/primary-load-2026-10-26.txt` shows the problem you want to fix. From 01:00 to 01:22 CPU hit 88 % and checkout API p95 rose from 340 ms to 1,900 ms.

- **Lag:** p99 lag is 2 seconds and the report covers yesterday, so lag cannot change the numbers.
- **Cost:** the job needs a second secret and two connections.
- **Risk:** the subquery must return the same churn counts as the temp table. A long query on a standby can also be cancelled by replay conflicts. No file in the repo shows the standby's conflict settings.

**Alternative: skip `record_run`.** The job runs fully on the replica with one connection. It beats the recommendation on simplicity. It loses the `report_runs` audit row. It becomes the primary only if nothing reads `report_runs`. No file in the repo reads it, but other services might.
