`pinewood-docs` rejects every Halvorsen Marine drawing because two layers cap request bodies at 10 MB. nginx has `client_max_body_size 10m` and Flask has `MAX_CONTENT_LENGTH = 10 * 1024 * 1024`. Aelita recommends raising both to 200 MB for `/api/files`. That needs no frontend release, so it meets the Friday 30 October deadline.

**Timeline without the fix**

1. Eirik Dahl picks a 94 MB drawing. The web client sends a plain form POST to `/api/files` at about 2.5 MB/s, which is the 20 Mbit/s uplink.
2. `nginx` reads the request header with `Content-Length: 94371840` and compares it with `client_max_body_size 10m`.
3. `nginx` answers 413 and logs `client intended to send too large body` at 09:14:02. The request never reaches `pinewood-app`.
4. Raising only `nginx` would move the failure. `MAX_CONTENT_LENGTH` in `app/settings.py` would then return 413 at 10 MiB. All 25 daily drawings fail, and the yard review on Monday 2 November has no files.

**Timeline with the fix**, diverges at step 3.

3. `nginx` accepts bodies up to 200m on `/api/files`. It buffers the drawing to `/var/cache/nginx/client_temp`. A 180 MB file uses under 1% of the 20 GB volume.
4. When the body is complete, `nginx` forwards it. Flask accepts it under the 200 MiB cap. `storage.put` sends it to `pinewood-files` at about 60 MB/s, which takes about 3 s for 180 MB. That is under the 30 s gunicorn `timeout`, and the response is 201.

**What changes**

- `deploy/nginx/pinewood.conf`: add `location = /api/files` above `location /api/`. It sets `client_max_body_size 200m;` and repeats the same `proxy_pass` and `proxy_set_header` lines. `location /api/` keeps 10m.
- `app/settings.py`: change `MAX_CONTENT_LENGTH` from `10 * 1024 * 1024` to `200 * 1024 * 1024`.
- `deploy/gunicorn.conf.py`: no change. `nginx` buffers the slow client transfer, so a worker is busy only for the roughly 3 s bucket upload.

**Recommendation.** Aelita recommends raising both limits, because the ticket's blocker is that no frontend release is possible before 9 November. The cost is that a worker is held about 3 s per upload. At 25 uploads per day with 4 workers, that is negligible. The risk is that the Flask cap applies to every route. The `nginx` cap stays 10m everywhere except `/api/files`, so other routes remain protected at the edge.

**Alternative: presigned direct upload.** The web client would call `storage.presign_post` and upload straight to `pinewood-files`. It removes the app and `nginx` from the data path and needs no size limit here. It costs a new endpoint and a frontend change. That change cannot ship before 9 November. It becomes the primary if uploads grow well beyond 200 MB or the worker load matters.
