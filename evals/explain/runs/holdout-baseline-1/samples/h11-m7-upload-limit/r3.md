Raise the 10 MB upload limit to 200 MB in both `nginx` and Flask. This needs no frontend release, so it meets the Friday 30 October deadline. Aelita recommends this over the presigned-upload route, which needs a frontend change.

**Existing behaviour**

1. `deploy/nginx/pinewood.conf:8` sets `client_max_body_size 10m`. `nginx` rejects any larger body with 413 before `pinewood-app` sees it.
2. `app/settings.py:3` sets `MAX_CONTENT_LENGTH` to 10 MB. `app/__init__.py:6` loads it, so Flask would also reject a larger body with 413.
3. `docs/ops.md` says `nginx` buffers the whole body to disk before it proxies. So `gunicorn` only sees the request after the slow client upload ends.

**Timeline without the fix**

1. Eirik Dahl uploads a 94 MB drawing from the Halvorsen Marine office.
2. The browser sends `POST /api/files` with the 94371840-byte body.
3. `nginx` reads the `Content-Length` header and compares it with `client_max_body_size 10m`.
4. `nginx` logs "client intended to send too large body" (`logs/nginx-error-2026-10-27.log`, 09:14:02) and returns 413.
5. The request never reaches `pinewood-app`. Every drawing from 60 to 180 MB fails the same way, including the 167772160-byte one at 09:31:47.

**Timeline with the fix**, diverges at step 3.

3. `nginx` compares the body with the new 200 MB limit and accepts it. A 180 MB drawing takes about 72 s on the 20 Mbit/s uplink.
4. `nginx` buffers the body to `/var/cache/nginx/client_temp`, then proxies to `pinewood-app`. The `gunicorn` 30 s timeout does not start until the worker has the request.
5. The Flask check passes at the new 200 MB `MAX_CONTENT_LENGTH`. `storage.put` streams the file to `pinewood-files` at about 60 MB/s, so about 3 s for 180 MB.
6. `upload_file` returns 201 with the key. The drawing is stored.

**What changes**

- `deploy/nginx/pinewood.conf`: add `location = /api/files { client_max_body_size 200m; ... }` with the same `proxy_pass` and headers as `/api/`. The global `client_max_body_size 10m` stays, so other endpoints keep the 10 MB cap.
- `app/settings.py`: `MAX_CONTENT_LENGTH` changes from `10 * 1024 * 1024` to `200 * 1024 * 1024`. It is global to Flask, but `nginx` still caps the other endpoints at 10 MB.

**Recommendation.** Aelita recommends the two limit changes. They need no frontend release, and the frontend team is away until 9 November.
- **Why it holds:** the 20 GB buffer volume holds the 25 drawings a day. The upload to the bucket takes about 3 s of one of the 4 sync workers, so load is small.
- **Cost:** each large upload ties up one `nginx` buffer file and one worker for a few seconds.
- **What can break:** a client slower than 20 Mbit/s still works, because `nginx` waits per read and not for the whole body. A drawing over 200 MB still fails with 413.

**Alternative: presigned direct-to-bucket upload.** The client calls `storage.presign_post` and uploads straight to `pinewood-files`. This removes the size limit on `pinewood-app` and the `nginx` buffering. It costs a frontend change and a new endpoint. It becomes the primary when files grow far beyond 200 MB or a frontend release is possible. Today it misses Friday 30 October.
