`kestrel-billing` charged 212 subscribers twice because the clocks went back in Europe/Berlin and the scheduler fired `charge_renewals` for 02:30 twice. Aelita recommends two small guards: one in the scheduler and one in `charge_renewals`.

**Timeline without the fix**

1. `kestrel-scheduler` fires `charge_renewals` at 00:30Z, which is 02:30+0200. It charges 212 subscriptions and inserts 212 `renewal_charges` rows (`logs/scheduler-2026-10-25.log:1-2`).
2. `send_dunning` fires at 00:45Z and sends 41 emails.
3. At 01:00Z Berlin moves from CEST to CET. Local time goes from 03:00 back to 02:00, so 02:30 happens a second time.
4. At 01:30:02Z the local time is 02:30+0100. `matches` in `scheduler/cron.py` sees only the wall clock. `due_jobs` in `scheduler/clock.py` sees a gap of 60 minutes, which exceeds `MIN_GAP_SECONDS = 60`, so `charge_renewals` fires again.
5. `charge_renewals` selects `renews_on <= today`. `renews_on` has not moved, because only `settle_renewals` advances it. The same 212 subscriptions come back. `psp.charge` sends them to Payrail with no idempotency key, and Payrail charges each one again.
6. `send_dunning` fires again and sends the same 41 emails.
7. `settle_renewals` runs at 04:00Z and reports `settled=424`. It advances `renews_on` only after both runs, so it is too late.

The result is 212 subscribers with two identical charges on 25 October, and 41 duplicate dunning emails.

**Timeline with the fix**, diverges at step 4.

4. At 01:30:02Z `due_jobs` finds that `charge_renewals` already fired for local date 2026-10-25. It skips the job.
5. No second charge runs. `send_dunning` skips for the same reason, and `settle_renewals` settles 212 rows.

**What changes**

- `scheduler/clock.py`: `due_jobs` today compares the time since the last fire against `MIN_GAP_SECONDS`. The new version skips a job when its last fire has the same local date and the same cron match. `scheduler/loop.py` would store `(local.date())` in `last_fired`.
- `billing/renewals.py`: add `AND NOT EXISTS (SELECT 1 FROM renewal_charges rc WHERE rc.subscription_id = subscriptions.id AND rc.charged_on = %s)` to the `charge_renewals` query. A repeated run then skips subscriptions that were already charged today.

**Recommendation.** Aelita recommends both guards.
- **Scheduler guard.** It removes the cause, a wall-clock hour that repeats. It also stops the duplicate dunning emails, which the charge guard cannot do.
- **Charge guard.** It protects money if the scheduler ever runs a job twice again, for example after a restart.
- **Cost.** Both changes are small.
- **What can break.** `last_fired` lives in memory, so a restart loses the guard, and only the charge guard covers that case. On the spring-forward night 02:30 does not exist, so the job is skipped that day. The job still runs the next day because it selects `renews_on <= today`.

**Alternative: move `charge_renewals` to UTC.** Set `timezone: UTC` in `schedules/charge_renewals.yaml`. It needs no code change, because UTC never repeats an hour. It does not protect `send_dunning` or any job that stays on local time. It becomes the primary if you want a one-line hotfix before the next clock change.

**Alternative: send a Payrail idempotency key from `psp.charge`.** I did not verify that Payrail supports one, because no file settles it. It would also catch a crash between `psp.charge` and the `renewal_charges` insert, which neither guard covers.
