`kestrel-scheduler` fired `charge_renewals` twice because the clocks went back at 03:00 on 25 October, so 02:30 in Berlin happened twice. `charge_renewals` then charged the same 212 subscriptions both times. Aelita recommends a guard in the charge job plus a fix in the scheduler. It costs one unique index and a few lines.

**Timeline without the fix**

1. At 00:30:04Z, `scheduler/clock.py` matches `30 2 * * *` against Berlin time 02:30+0200. `charge_renewals` fires and charges 212 subscriptions.
2. `billing/renewals.py` inserts 212 `renewal_charges` rows with `charged_on` 2026-10-25. It does not touch `renews_on`. Only `settle_renewals` advances `renews_on`, and it runs at 05:00.
3. At 00:45:03Z, `send_dunning` fires and emails 41 customers.
4. At 01:00Z the Berlin clock goes from 03:00+0200 back to 02:00+0100. Local time 02:30 now happens a second time.
5. At 01:30:02Z, `due_jobs` matches 02:30 again. `last_fired` is 60 minutes old, so `MIN_GAP_SECONDS = 60` does not block it. The same happens with `send_dunning` at 01:45.
6. `charge_renewals` reruns with the same local date. Every subscription still has `renews_on <= today`, and nothing checks `renewal_charges`. It charges the same 212 subscriptions again. The 41 dunning emails go out again.
7. At 04:00Z, `settle_renewals` settles 424 rows and moves `renews_on` forward once per subscription.
8. 212 subscribers now hold two identical charges dated 25 October.

**Timeline with the fix**, diverges at step 5.

5. `due_jobs` sees that `charge_renewals` already fired for the local minute 2026-10-25 02:30. It skips the job. It also skips `send_dunning` at 02:45.
6. If a restart or a bug fires the job anyway, the unique key on `renewal_charges` rejects the second row before `psp.charge` runs. Nobody is charged twice.

**What changes**

- `scheduler/clock.py`: add a check that skips a job when it already fired for the same naive local minute. Today it only checks that 60 seconds have passed.
- `scheduler/loop.py`: `last_fired` is in memory, so a restart loses it. Persist it, or leave this to the charge guard.
- `billing/renewals.py`: insert the `renewal_charges` row first. If the unique key on `(subscription_id, charged_on)` rejects it, skip that subscription. Only then call `psp.charge`.
- `billing/psp.py`: send an idempotency key such as `Renewal {sub.id}:{today}`. I found no file that shows whether Payrail supports one, so the database guard does not depend on it.
- `billing/dunning.py`: no change. The scheduler fix covers it.

**Recommendation.** Aelita recommends both changes. The scheduler fix removes the cause. The charge guard protects money against any double fire, including a process restart. The guard can break a retry after a Payrail timeout. The row exists but the charge never happened. That needs a `pending` state.

**Alternative: scheduler fix only.** This is the smaller change. It costs nothing in billing code. It becomes the primary only if the team refuses a schema change. A restart can still double charge.
