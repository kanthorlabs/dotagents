The CDN is not the cause, so lowering its TTL will not fix the stale price. `saltmarsh-shop` caches prices in a per-pod `price_cache` in `pricing/service.py`, and the admin clears it on only one of six pods. Aelita recommends that every pod subscribes to the existing `price.changed` event and evicts the SKU.

**Timeline without the fix**

1. Before 10:02, the six `shop-api` pods each hold KET-2210 at 39.90 in their own `price_cache`. The cache lives in each process and its TTL is 3600.
2. At 10:02, Tove Lindqvist changes KET-2210 to 34.90. The load balancer sends the POST to one pod, for example pod 3.
3. `update_price` in `admin/prices.py` writes the database, then runs `price_cache.pop(sku)`. That clears pod 3 only.
4. `update_price` publishes `price.changed`. Only `search/indexer.py` subscribes. No pod evicts its cache.
5. A product page loads and calls `/api/prices?sku=KET-2210`. The `/api/*` rule has `cache: false`, so the CDN passes every call to a pod. Pod 3 answers 34.90. Pods 1, 2, 4, 5 and 6 answer 39.90. This matches the 34.90 and 39.90 mix that SM-140 reports on reload.
6. Each stale pod keeps 39.90 until its entry expires, up to 3600 seconds after it was cached. The last report came at 10:57. Checkout reads `/api/prices` too, so customers pay the old price.

**Why the proposal fails.** `cdn/rules.yaml` sets `ttl_seconds: 3600` for `/product/*`, and those pages hold no price in their HTML. The price comes from `/api/prices`, which the CDN never caches. Lowering a TTL for the price API changes nothing, because no such CDN TTL exists. The 3600 match is a coincidence.

**Timeline with the fix**, diverges at step 4.

4. `update_price` publishes `price.changed`. Every pod runs a subscriber that calls `price_cache.pop(sku)`.
5. A product page calls `/api/prices?sku=KET-2210`. Every pod misses the cache and reads 34.90 from the database.
6. Customers see 34.90 within about a second of the admin change. Pod 3 evicts itself twice, which is harmless.

**What changes**

- `pricing/service.py`: add `on_price_changed(event)`, which calls `price_cache.pop(event["sku"], None)`.
- `shop/app.py`: call `subscribe("price.changed", on_price_changed)` at startup. I did not find this file in the repository, so the exact location needs confirming.
- `admin/prices.py`: keep the local `pop`, so the pod that handled the POST stays correct if Redis is slow.
- `pricing/service.py`: lower the cache `ttl` from 3600 to 300. This is a backstop for a lost pub/sub message, because Redis pub/sub does not redeliver.
- `cdn/rules.yaml`: no change.

**Recommendation.** Aelita recommends event-driven eviction on every pod. It removes the root cause, which is that one pod clears a cache held by six. It reuses the Redis channel that already exists. It costs one subscriber thread per pod. A pod that misses a message stays stale until the backstop TTL expires.

**Alternative: drop the per-pod cache TTL to 60 and add no subscriber.** This is your idea moved to the layer that holds the cache. It needs no Redis dependency in the pods. Staleness is bounded at 60 seconds, not removed, and the database takes more reads. It becomes the primary if a stale price for one minute is acceptable and you want no new moving part.
