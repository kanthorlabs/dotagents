The stale price comes from the in-process `price_cache` in each `shop-api` pod, not from the CDN. Lowering the CDN TTL would change nothing, because `/api/*` is already `cache: false`. Aelita recommends that every pod subscribe to `price.changed` and evict its own entry.

**Existing behaviour**

1. `cdn/rules.yaml` caches `/product/*` for 3600 seconds. It does not cache `/api/*`.
2. The product page holds no price in its HTML. It calls `/api/prices?sku=...` after load (`docs/frontend.md`).
3. `pricing/service.py` keeps `price_cache = TTLCache(maxsize=50_000, ttl=3600)` inside each pod process.
4. `admin/prices.py` calls `price_cache.pop(sku)` and then `publish("price.changed")`. The pop affects only the pod that served the admin request.
5. Only `search/indexer.py` subscribes to `price.changed`. No pricing code subscribes.

**Timeline without the fix**

1. At 10:02, Tove Lindqvist sets KET-2210 from 39.90 to 34.90. The load balancer sends the request to pod A of 6 `shop-api` pods.
2. `update_price` writes the database, pops KET-2210 from pod A, and publishes `price.changed`.
3. `search/indexer.py` updates the search index. No pod evicts its own cache.
4. Pods B to F still hold KET-2210 at 39.90 from an earlier read.
5. The load balancer spreads `/api/prices` calls over all pods. Pod A returns 34.90 and the others return 39.90. This matches the "some reloads" report in SM-140.
6. Each stale entry expires up to 3600 seconds after it was filled. The last old price appeared at 10:57. Customers saw 39.90 at checkout for nearly an hour.

**Timeline with the fix**, diverges at step 3.

3. Every `shop-api` pod runs a subscriber on `price.changed`. Each one calls `price_cache.pop(sku)` on its own cache.
4. Pods A to F hold no entry for KET-2210.
5. The next `/api/prices` call on any pod reads the database and returns 34.90.
6. Customers see 34.90 on every pod within about one second. That is the subscriber `sleep_time=0.5` plus delivery.

**What changes**

- `pricing/service.py`: add `start_invalidation()`. It calls `subscribe("price.changed", lambda e: price_cache.pop(e["sku"], None))`.
- `shop/app.py`: call `start_invalidation()` at startup. I did not find this file in the repository, so I could not check the startup hook.
- `cdn/rules.yaml`: no change.

**Recommendation.** Aelita recommends event-driven eviction in every pod. It removes the cause, which is that only one of six caches hears about the change. It costs one Redis subscription per pod. A missed message leaves that pod stale until the 3600 second TTL, so keep the TTL as a backstop. Pub/sub does not replay messages for a pod that restarted or lost its connection.

**Why not the CDN TTL change.** `/api/*` bypasses the CDN, so 3600 to 60 changes nothing for prices. The only 3600 rule is `/product/*`, and its HTML holds no price. Lowering that rule would add CDN misses and fix nothing.

**Alternative: lower the pod TTL to 60 seconds.** Change `ttl=3600` to `ttl=60` in `pricing/service.py`. It needs no subscriber and is the smallest edit. It still shows old prices for up to a minute, and it raises database reads about sixty-fold. It becomes the primary if a one-minute delay is acceptable and Redis delivery cannot be trusted.

**Question.** Should Aelita add the `price.changed` subscriber to every `shop-api` pod, or lower the pod TTL to 60 seconds?
