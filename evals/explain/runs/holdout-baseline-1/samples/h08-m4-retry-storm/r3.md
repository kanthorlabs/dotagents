Search stayed down because `ranker` kept scoring requests that clients had already abandoned. The retries from `web` and `query-gw` fed a queue with no limit. Aelita recommends a bounded queue in `ranker`, which sheds load once waits pass the timeout.

**Existing behaviour**

1. `web` (`searchClient.ts`) tries each search up to 3 times, with a 2000 ms timeout.
2. `query-gw` (`config.yaml`) sends each attempt to `ranker` with a 600 ms timeout and 2 retries. That is up to 3 calls per attempt.
3. `ranker` (`server.py`) hands every request to a 64-thread pool. The queue has no limit, and nothing cancels a request after its client leaves.

**Timeline without the fix**

1. 14:02. The merge raises `ranker` p99 from 400 ms to 900 ms. The `query-gw` timeout is 600 ms.
2. 14:04. Slow calls time out, and `query-gw` retries them. Load grows toward 400 searches/s × 3 `web` attempts × 3 `query-gw` calls = 3,600/s. The incident notes show about 3,500/s.
3. 14:04. The 8 instances serve about 1,200/s. The queue grows faster than the workers drain it.
4. 14:06. The merge ends and `ranker` is fast again. The queue is already deep, so a new request waits minutes. That is far more than 600 ms.
5. 14:06 to 14:39. Every request times out at `query-gw`. `ranker` still scores it later, because nothing cancels it. Each timeout triggers another retry, so arrivals stay near 3,500/s. Useful output is zero and the error rate is 97%.
6. 14:39. Tomasz turns on the maintenance page. User traffic drops to zero. The queue of about 180,000 drains at 1,200/s in about 150 s, so it is empty at 14:41.
7. The failure: the overload kept itself going after its trigger had ended, so search could not recover without outside help.

**Timeline with the fix**, diverges at step 4.

4. 14:06. The merge ends. The `ranker` queue is capped at about 600 requests, so a queued request waits about 0.5 s at 1,200/s.
5. Extra requests get an immediate 503. They cost almost nothing, so workers spend their time on live requests.
6. Within seconds the queue drains. Calls finish inside 600 ms again and retries stop. Search recovers by about 14:07, with no operator action.

**What changes**

- `ranker/server.py`: `rank` currently queues without limit. It will count in-flight requests and return 503 above 64 + 512. This is a new check, and the limit is a constant to tune.
- `docs/capacity.md`: replace "The queue has no limit." with the new limit.

**Recommendation.** Aelita recommends the cap in `ranker`, because it removes the cause of the stuck state: a queue that outlives its clients. It works whatever the clients do. Its cost is that a real spike now sees fast 503s instead of slow answers. `query-gw` retries on 5xx, so shed requests are retried. That is cheap now, but it still adds load.

**Alternative: set `retries: 0` for `ranker` in `config.yaml`.** It cuts the load multiplier from 3 to 1 in `query-gw`. It is a one-line change. It leaves `web`'s 3 attempts, and the queue stays unbounded. It becomes the primary if `ranker` code cannot change soon.

**Unverified.** At about 2,300/s of excess load, the queue should have grown far beyond 180,000. I cannot explain this from the files. It does not change the cause. The drain time of 150 s matches the 14:39 to 14:41 gap.
