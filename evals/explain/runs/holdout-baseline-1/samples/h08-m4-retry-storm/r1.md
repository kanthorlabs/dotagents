Search stayed down because `ranker` kept scoring requests that `query-gw` had already abandoned, and retries refilled its unbounded queue as fast as it drained. Aelita recommends a bounded queue in `ranker` that rejects excess requests immediately.

**Existing behaviour**

1. `web` calls `/api/search` with `TIMEOUT_MS` 2000 and `MAX_ATTEMPTS` 3.
2. `query-gw` calls `ranker` with `timeout_ms` 600 and `retries: 2`. That is 3 tries per attempt.
3. `ranker` runs `score` on a 64-thread `ThreadPoolExecutor`. It queues the overflow with no limit and never checks whether the caller is still waiting.

**Timeline without the fix**

1. At 14:02 the merge pushes p99 from 400 ms to 900 ms. Some tries pass 600 ms.
2. By 14:04 `query-gw` times out and retries. `web` retries on top of that. Each search can become 3 × 3 = 9 `ranker` requests. 400 searches per second × 9 = 3,600 per second, which matches the 3,500 in the notes.
3. The 8 `ranker` instances serve about 1,200 per second. The extra 2,300 per second go into the queue.
4. At 14:06 the merge ends, but the queue is already deep. It reaches about 180,000 requests, so the wait is about 150 s (180,000 ÷ 1,200 per second). The gateway gives up after 600 ms, so every answer arrives too late.
5. `ranker` still scores each dead request, and each timeout triggers another retry. Arrivals stay near 3,500 per second against 1,200 served. The state sustains itself with no error in `ranker`.
6. At 14:39 the maintenance page stops new searches. The queue drains in about 2 minutes at 1,200 per second and is empty at 14:41. Search was down for 37 minutes.

**Timeline with the fix**, diverges at step 4.

4. At 14:06 the queue is capped near 64 waiting requests per instance, about 400 ms of work. `ranker` rejects the rest at once with a 503.
5. `ranker` scores only requests that can still finish inside 600 ms. It serves about 1,200 per second of fresh work, and retries are cheap rejections.
6. Once the merge ends, p99 returns to 400 ms and the retries stop. Search recovers by about 14:07 with no manual action.

**What changes**

- `ranker/server.py`: `rank` currently awaits `run_in_executor` with an unlimited queue. It will count waiting requests and return 503 above a limit. Add a check that drops a request that waited longer than 500 ms before `score` starts.
- `docs/capacity.md`: the line "The queue has no limit" becomes the new limit, with the 64 and 500 ms values.

**Recommendation.** Aelita recommends bounding the queue in `ranker`. The root cause is that a standing queue of dead work outlives the overload. This fix removes that queue and protects `ranker` from any caller. It costs some rejected searches during a real overload. A limit set too low would reject healthy traffic.

**Alternative: cut the retry amplification.** Set `retries: 0` in `query-gw/config.yaml`, and reduce `MAX_ATTEMPTS` in `web/src/searchClient.ts`. This lowers the load to about 400 per second, with no `ranker` change. It leaves the queue unbounded, so any other overload can fill it again. It becomes the primary if `ranker` cannot be changed this quarter.
