Search stayed down because every user search turned into about 9 `ranker` requests, and `ranker` kept scoring requests whose clients had already given up. That load stayed above capacity after the merge ended. Aelita recommends a bounded queue with load shedding in `ranker/server.py`, plus fewer retry layers.

**Existing behaviour**

1. `web/src/searchClient.ts` makes up to 3 attempts per search, with a 2000 ms timeout each.
2. `query-gw/config.yaml` gives `ranker` a 600 ms timeout and 2 retries on timeout or 5xx. That is 3 tries per attempt.
3. `ranker/server.py` hands each request to a 64-thread `ThreadPoolExecutor`. Its queue has no limit, and nothing checks whether the client is still waiting.
4. `docs/capacity.md` says 8 instances serve about 1,200 requests per second.

**Timeline without the fix**

1. 14:02: the merge starts and p99 rises from 400 ms to 900 ms. This is above the 600 ms `query-gw` timeout.
2. 14:04: `query-gw` times out more than 50 % of requests and retries them. `ranker` receives about 3,500 requests per second from 400 searches per second.
3. The multiplier is 3 `web` attempts × 3 `query-gw` tries = 9. That gives 400 × 9 = 3,600 per second, three times the 1,200 capacity.
4. 14:06: the merge ends and `ranker` is fast again. The queue already holds a backlog, and the executor scores every entry in order.
5. Each new request waits behind the backlog, far longer than 600 ms. Even 10,000 queued requests mean more than 8 seconds of wait. It times out, and `query-gw` and `web` retry it. The retries refill the queue, and `ranker` spends its capacity on abandoned requests.
6. 14:06 to 14:39: the rate holds at 3,400 to 3,600 per second and the queue reaches 180,000. The error rate is 97 %.
7. 14:39: the maintenance page stops user traffic, so no new retries arrive. The queue drains in about 2 minutes.
8. 14:41: search works again. Nothing inside the system could have ended the overload without that manual step.

**Timeline with the fix**, diverges at step 4.

4. 14:06: the merge ends. The `ranker` queue is capped, for example at about 700 entries, which is roughly 600 ms of work at 1,200 per second. Beyond the cap, `ranker` returns 429 immediately.
5. The queue never holds more than about 600 ms of work. Requests that get in are served before their client times out.
6. Excess requests get a fast 429. `query-gw` does not retry it, because `retry_on` lists only timeout and 5xx.
7. Load falls back to 400 searches per second within seconds. Search recovers by itself at about 14:06.

**What changes**

- `ranker/server.py`: `rank` currently always awaits `run_in_executor`. It will count in-flight requests and return 429 when the count passes the cap. The cap is a constant, for example `MAX_QUEUED = 700`.
- `web/src/searchClient.ts`: `MAX_ATTEMPTS` goes from 3 to 1, or the retry runs only on a fast 429 with backoff. I could not read `./http`, so I don't know which errors `fetchJson` raises.
- `query-gw/config.yaml`: `retries` goes from 2 to 0 or 1. This cuts the multiplier from 9 to 1 or 2.

**Recommendation.** Aelita recommends the bounded queue in `ranker` first. It removes the cause that made the overload permanent: unbounded dead work. It costs a few rejected searches during a real overload. The cap needs tuning, and a value too low sheds healthy traffic. The retry cuts are a second step. Without them, `web` still retries 429s at 3×.

**Alternative: remove retries only.** Set `web` to 1 attempt and `query-gw` to 0 retries. This is a config edit with no new mechanism. It leaves the unbounded queue, so any burst above capacity still builds a backlog. It becomes the primary if `ranker` cannot be redeployed soon.

**Alternative: drop expired requests.** The client sends a deadline and `ranker` skips entries past it. This is more precise than a fixed cap. It needs a new header and changes in all three layers.

**Open item.** The numbers don't fully reconcile. At 3,500 per second in and 1,200 per second capacity, the queue would grow far beyond 180,000 over 33 minutes. The mechanism still holds, but the notes may not list all the load, so the cap should be tuned from real data.
