`tidepool-sync` sends one request per contact, and Juniper allows 100 requests per minute per key. Exponential backoff alone would not fix this. Aelita recommends switching `sync/crm_client.py` to `POST /v2/contacts:batchUpsert`, which sends 100 contacts per request.

**Timeline without the fix**

1. Marketing imports 45,600 Fairhaven leads on 26 Oct. `changed_contacts` returns 46,800 rows on 27 Oct.
2. `run_sync` starts 8 workers. Each calls `upsert_contact`, which sends one `PUT` per contact.
3. The log shows about 400 requests per minute, and about 300 of them return 429. Juniper accepts 100 per minute per key.
4. `sync_one` catches the error, logs a warning and skips `mark_synced`. Those contacts stay pending.
5. The job hits `activeDeadlineSeconds: 7200` in `deploy/cron.yaml`. The log reads 11,940 upserted and 34,860 pending.
6. With your backoff, workers wait 60 s after each 429 and retry. Retries still count against the 100 limit, so the ceiling stays at about 100 contacts per minute, or 12,000 per 2-hour run. The 34,860 pending need about 3 more nights. Each 40,000-lead November import needs about 3.4 nights. The job still fails.

**Timeline with the fix**, diverges at step 2.

2. `run_sync` splits the contacts into chunks of 100. Each worker sends one `batchUpsert` call per chunk.
3. A batch call takes 5 to 7 s. With `WORKERS` lowered from 8 to 4, the job sends at most about 48 calls per minute, under the 100 limit.
4. Juniper returns a result per contact. `sync_one` calls `mark_synced` only for the contacts that succeeded.
5. 468 calls at 4 workers take about 12 minutes. All 46,800 contacts sync in one night, before Friday 09:00 UTC. A 40,000-lead expo needs 400 calls and takes about 10 minutes.

**What changes**

- `sync/crm_client.py`: add `upsert_contacts(contacts)`, which posts up to 100 contacts to `/contacts:batchUpsert`. It returns the per-contact results. `upsert_contact` is deleted.
- `sync/run_sync.py`: `sync_one` becomes `sync_chunk`. It calls `mark_synced` per succeeded contact and logs a warning per failed contact. `WORKERS` goes from 8 to 4.

**Recommendation.** Aelita recommends batching. It removes the cause, which is the number of requests, and it cuts requests by 100 times. Its cost is one new response parser. Two things can break it. First, `docs/juniper-api.md` says only that the response "lists the result per contact", so I could not check the exact field names. Second, I found no log for the 28 Oct run, so I could not check how it went. I would still keep a small retry that honors `Retry-After: 60` on 429 as a safety net. It is not the fix.

**Alternative: enterprise tier.** This raises the limit to 1,000 requests per minute for 1,450 USD per month. It needs no code change. Juniper quotes 3 weeks of lead time, so it misses Friday. It becomes the primary if daily volume grows past what batching handles.
