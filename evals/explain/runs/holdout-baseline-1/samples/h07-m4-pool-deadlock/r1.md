`checkout` holds one pool connection and then asks the same pool for a second one inside `hold_seats`. Under load, every connection is held by a request that waits for a second one, so the pool deadlocks until the 30-second timeout. Aelita recommends passing the open connection into `hold_seats`.

**Timeline without the fix**

Each `checkout-api` replica has its own pool of `max_size=10` (`app/db.py:5-10`). `post_checkout` is a sync handler, so many requests run at once in the threadpool.

1. At 19:00:00 the Halden Arena on-sale starts. Each `checkout-api` replica receives more concurrent requests than its pool has connections. Log line 3 shows `checkout-api-2` with `in_flight=14`.
2. Ten requests on `checkout-api-2` each take a connection at `app/checkout.py:6`. The pool is full with `pool_in_use=10`.
3. Each of the ten inserts the order, then calls `hold_seats`. It requests a second connection at `app/seats.py:5`, while still holding the first.
4. The pool has none free, so all ten wait. The other four requests wait at `app/checkout.py:6`. Log line 3 shows `pool_waiting=14`.
5. No holder can finish without a second connection, so nobody releases one. `pg-copperline` shows `active_connections=38` of 200 (log line 4), so the database is idle. The limit is the per-replica pool.
6. At 19:00:31 the timeouts fire together. Ten fail in `hold_seats`, four fail in `checkout`, and all 14 requests return 500 (log lines 5-7). The next 12 requests take the freed connections and repeat this at 19:01:02 (log lines 9-11).

At normal traffic, log line 1 shows `in_flight=3`. The pool never fills, so the second request for a connection always succeeds.

**Timeline with the fix**, diverges at step 3.

3. Each of the ten requests passes its own `conn` to `hold_seats`. The seat update runs on the connection it already holds.
4. Each request commits and releases its connection within milliseconds.
5. Waiting requests take the freed connections. The queue drains at database speed.
6. Under a surge, requests may wait briefly for a connection, but none deadlock.

**What changes**

- `app/seats.py`: old behaviour is `hold_seats(event_id, seat_ids)` opens `pool.connection()`. New behaviour is `hold_seats(conn, event_id, seat_ids)` uses the given `conn`. Delete the `pool` import.
- `app/checkout.py`: old call at line 12 is `hold_seats(order.event_id, order.seat_ids)`. New call is `hold_seats(conn, order.event_id, order.seat_ids)`.

**Recommendation.** Aelita recommends one connection per request. It removes the root cause, which is a nested checkout from the same pool. It also puts the order insert, the seat hold and the status update in one transaction. Today the seat hold commits on its own connection. If the order transaction rolls back, the seats stay held for 10 minutes. The cost is a small signature change. Nothing else calls `hold_seats` in this repository.

**Alternative: raise `max_size`.** It is a one-line change in `app/db.py`. It only moves the deadlock threshold. A surge of more than `max_size` concurrent requests still hangs, and 4 replicas × a larger pool pushes toward the database limit of 200. It becomes the primary only if a hotfix must ship without touching the code path.

**Alternative: shorten `timeout`.** This makes failures faster, but the deadlock stays. Pair it with the fix if you want load shedding under a surge.
