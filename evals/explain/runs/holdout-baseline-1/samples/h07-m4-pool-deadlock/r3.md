`checkout` in `app/checkout.py` holds one pool connection and then calls `hold_seats`, which asks the same pool for a second one. Under load, every connection is held by a request that is waiting for another, so nothing can proceed until the 30-second timeout. Aelita recommends passing the open connection into `hold_seats`.

**Existing behaviour**

1. `post_checkout` in `app/api.py` is a sync handler, so requests run concurrently in worker threads.
2. `checkout` takes connection A from `pool` at `app/checkout.py:6` and opens a transaction.
3. `checkout` inserts the order, then calls `hold_seats` while still holding A.
4. `hold_seats` takes connection B from the same `pool` at `app/seats.py:5`.
5. The pool has `max_size=10` and `timeout=30` in `app/db.py`. There are 4 replicas, so at most 40 connections. That matches `active_connections=38` of 200 in the log.

**Timeline without the fix**

1. At 19:00:00 the Halden Arena on-sale starts. Requests per replica jump past 10.
2. By 19:00:01 on `checkout-api-2`, `in_flight=14`, `pool_in_use=10` and `pool_waiting=14`.
3. Ten requests each hold connection A inside `checkout`. Each one waits in `hold_seats` for connection B.
4. The other 4 requests wait at `app/checkout.py:6` for their first connection.
5. No connection is ever freed, because the 10 holders need a second connection before they can commit. The checkout freezes.
6. At 19:00:31 the 10 `hold_seats` calls and the 4 `checkout` calls raise `PoolTimeout`. All 14 requests return 500.
7. The released connections go to the 12 queued requests. They deadlock the same way and fail at 19:01:02.
8. At normal traffic, `in_flight=3`, so fewer than 10 requests overlap and B is always free. The database never nears its limit, because the pool caps each replica at 10 connections.

**Timeline with the fix**, diverges at step 3.

3. `checkout` passes `conn` to `hold_seats`. The seat update runs on connection A, inside the same transaction.
4. Each request uses exactly one connection. Requests beyond 10 queue briefly at `app/checkout.py:6`.
5. Each request commits and releases its connection within milliseconds. The next waiting request takes it.
6. The pool drains in a steady stream. No request waits 30 seconds, and none fail.

**What changes**

- `app/seats.py` old behaviour: `hold_seats(event_id, seat_ids)` opens `pool.connection()`. New behaviour: `hold_seats(conn, event_id, seat_ids)` runs the `UPDATE` on the given `conn`. Delete the `from app.db import pool` import.
- `app/checkout.py` old behaviour: `hold_seats(order.event_id, order.seat_ids)`. New behaviour: `hold_seats(conn, order.event_id, order.seat_ids)`.

**Recommendation.** Aelita recommends passing `conn`, because it removes the cause: one request needing two connections. It costs nothing at runtime.

It also fixes a second bug. Today the seat hold commits on its own connection. If the order transaction rolls back, the seats stay held for 10 minutes. After the fix, both roll back together. The risk is that the seat `UPDATE` now runs inside the order transaction. Row locks on `seats` last slightly longer, but the transaction is short.

**Alternative: raise `max_size`.** This is a one-line change to `app/db.py`. It only moves the threshold. The deadlock returns once concurrent requests per replica exceed the new size. Four replicas at size 50 would also use 200 connections, which is the whole `max_connections`. It becomes the primary only if the code cannot change before the next on-sale.
