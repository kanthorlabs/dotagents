- **Today's key is right.** `cache_key` in `edge/cache.py:5` returns the path and query string only.
- **The cause is right.** Safari 13 cannot decode WebP, and it receives WebP bytes that Chrome's request cached.
- **The fix is wrong.** The key gets the negotiated format (`avif`, `webp` or `orig`), not the whole `Accept` header.

The case is not a key built from the raw header. `logs/accept-stats-2026-10.txt` counts 1,912 distinct `Accept` values in October. A raw-header key would split the cache into 1,912 variants, and the hit rate would drop. The negotiated format has three values.

**Existing behaviour**

1. `serve_image` in `edge/handler.py:7` calls `lookup(request)` first.
2. `lookup` builds the key from the path and query only.
3. On a miss, `serve_image` calls `negotiate` at line 10, then `render`, then `save`.

Negotiation runs after the lookup, so `cache_key` cannot see the format today. Petra needs to know this.

**What changes**

- `edge/handler.py`: old behaviour is `lookup(request)` before `negotiate`. New behaviour is that `serve_image` calls `negotiate` first and passes `image_format` to `lookup` and `save`.
- `edge/cache.py`: old behaviour is `cache_key(request)` returns `f"{request.path}?{request.query_string}"`. New behaviour is that `cache_key(request, image_format)` appends the format to that string. `lookup` and `save` take `image_format` and pass it on.
