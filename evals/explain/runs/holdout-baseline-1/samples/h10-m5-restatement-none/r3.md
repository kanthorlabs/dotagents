- **Today's key: correct.** `cache_key` in `edge/cache.py:5` returns `request.path` plus `request.query_string`, and nothing else.
- **Safari 13 cause: correct.** It cannot decode WebP, and `img-edge` serves it the WebP bytes that Jonas Ek's Chrome request cached.
- **Key with the fix: wrong.** The key gets the negotiated format (`avif`, `webp` or `orig`), not the whole `Accept` header.

The case is not "one cache entry per `Accept` header". `logs/accept-stats-2026-10.txt` shows 1,912 distinct `Accept` values in October. Keying on the raw header would split each image into up to 1,912 entries and the hit rate would collapse. The negotiated format has 3 values.

**Timeline with the fix**, diverges at step 4.

4. `img-edge` negotiates `avif`, `webp` or `orig` from the `Accept` header, then looks up the key. Safari 13 negotiates `orig`, so it misses the `webp` entry.
5. `img-edge` renders `orig`, caches it under its own key, and Hanna Lind sees the image.

**What changes**

- `edge/cache.py` old behaviour: `cache_key(request)` returns path and query. New behaviour: `cache_key(request, image_format)` appends the format. `lookup` and `save` take `image_format` too.
- `edge/handler.py` old behaviour: `serve_image` calls `lookup` at line 7, before `negotiate` at line 10. New behaviour: `serve_image` calls `negotiate` first and passes `image_format` to `lookup` and `save`. Without this reorder, the key has no format at lookup time and the bug stays.
