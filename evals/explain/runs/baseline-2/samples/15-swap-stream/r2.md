`export_contacts` in `app/exports.py` sends no byte until the whole CSV is built, so `edge-lb` closes the connection after 30 seconds of silence. Aelita recommends streaming the CSV in batches so bytes flow from the first second.

**Existing behaviour**

1. `export_contacts` runs `db.query` and loads every row for the tenant.
2. It writes all rows into an `io.StringIO` buffer.
3. It returns `Response(buffer.getvalue())` only after the buffer is complete.
4. `edge-lb` has `idle_timeout_seconds: 30`, and the timer restarts on every upstream byte.

**Timeline without the fix**

1. A user at `bluefin-logistics` clicks Export. `db.query` loads 412880 rows in 12 seconds.
2. `export_contacts` builds the buffer for 77 more seconds. No byte reaches `edge-lb`.
3. At 30 seconds `edge-lb` closes the idle connection and returns 504.
4. The gunicorn worker keeps building until 89 seconds, then writes to a closed connection.
5. The user gets no file. The log shows the same failure at 09:12 and 14:02 on 2026-10-27.

**Timeline with the fix**, diverges at step 2.

2. `export_contacts` returns a streaming `Response` and sends the header row at once.
3. It reads rows in batches of 1000 and yields CSV text per batch. Each batch resets the idle timer.
4. The export ends at about 90 seconds. No silent gap passes 30 seconds, so the browser receives the full file with status 200.

**What changes**

- `app/exports.py`: `export_contacts` old behaviour is one `db.query` plus a `StringIO` buffer. New behaviour is a generator that yields the header, then CSV rows per batch from a cursor. `tenant_id` filtering stays the same.
- `deploy/edge-lb.yaml`: no change.

**Recommendation.** Aelita recommends streaming, because it removes the cause, which is the silent gap. It also drops memory use from the full 412880 rows to one batch. It costs a rewrite of one function.

- **Can break:** `ferngrove.web` and `ferngrove.db` are not in this repository. I could not confirm that `Response` accepts a generator or that `db` offers a cursor. If either is missing, the fix needs a small helper in that package.
- **Residual risk:** gunicorn `timeout = 120` still applies to the worker. A tenant that needs more than about 120 seconds would be killed mid-stream. Streaming also shortens the run, because the 77 second build step is mostly gone.

**Alternative: raise `idle_timeout_seconds` in `edge-lb.yaml` to 120.** This is one line. It costs a longer idle window for every route, and it fails again when a tenant grows past the new limit. It becomes the primary only if streaming cannot be shipped soon.

**Alternative: background job plus emailed link.** This has no timeout limit at any size. The stack has no job queue and no email service, and `docs/exports.md` says each new component needs an owner and on-call. It becomes the primary only if exports grow far beyond what one request can serve.
