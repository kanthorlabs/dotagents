`export_contacts` in `app/exports.py` builds the whole CSV in memory before it sends a single byte, so `edge-lb` closes the connection at 30 seconds of silence. Aelita recommends streaming the CSV from the handler, which costs a small change to one function.

**Timeline without the fix**

1. A user at `bluefin-logistics` clicks "Export contacts". `export_contacts` runs the query for 412,880 rows, which takes 12 seconds.
2. `export_contacts` writes every row into `io.StringIO`, which takes 77 seconds. The client receives no byte during this time.
3. `edge-lb` sees 30 seconds without a byte and closes the connection, per `idle_timeout_seconds: 30`.
4. The browser gets a 504 and no file. The worker finishes at 89 seconds and discards the result. The log shows the same failure at 09:12 and 14:02 on 2026-10-27.

**Timeline with the fix**, diverges at step 2.

2. `export_contacts` returns a streaming response. It sends the header row at once, then sends rows in chunks as it reads them.
3. Each chunk restarts the idle timer, as `docs/exports.md` states. `edge-lb` never sees 30 seconds of silence.
4. The browser receives the full CSV after about 89 seconds with status 200.

**What changes**

- `app/exports.py`: old behaviour is `writer.writerows(rows)` into `StringIO`, then `Response(buffer.getvalue())`. New behaviour is a generator that yields the header and then each row's CSV line, passed to `Response`.

**Recommendation.** Aelita recommends streaming. It removes the cause, which is zero bytes sent for 89 seconds. It needs no new component, and `docs/exports.md` says each new component needs an owner and on-call coverage. Two things can break it:
- **Response support.** `ferngrove.web.Response` is not in this repository, so I could not confirm it accepts an iterator. If it does not, the handler needs a different streaming return type.
- **Worker timeout.** `gunicorn.conf.py` sets `timeout = 120`. If the sync workers are the default type, an export that runs past 120 seconds is killed even while streaming. Bluefin Logistics is at 89 seconds today, so it has limited headroom.

**Alternative: raise `idle_timeout_seconds` in `edge-lb.yaml`.** It needs no code change. It beats streaming only as a stopgap. It also loosens the limit for every route, and it fails again when a tenant grows past the new value. It becomes the primary if the streaming return type turns out to be unavailable.

**Alternative: background job plus email.** This removes the time limit entirely. It needs a job queue and an email service, which the stack lacks. It becomes the primary if exports grow well past the 120-second worker limit.
