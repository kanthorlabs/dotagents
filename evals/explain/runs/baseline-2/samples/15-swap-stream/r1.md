`export_contacts` in `app/exports.py` sends no byte for 89 seconds, so `edge-lb` closes the connection after 30 idle seconds. Aelita recommends streaming the CSV: write the header at once, then send rows as they come. This resets the idle timer on every chunk.

**Existing behaviour**

1. `export_contacts` runs `db.query` and loads all rows of the tenant (`app/exports.py:10`).
2. It writes every row into an `io.StringIO` buffer (`app/exports.py:11-14`).
3. It returns `Response(buffer.getvalue())` only after the buffer is complete (`app/exports.py:15`).
4. `edge-lb` has `idle_timeout_seconds: 30` and no request timeout (`deploy/edge-lb.yaml:3-4`). It resets the timer on every upstream byte (`docs/exports.md:7`).

**Timeline without the fix**

1. A user at `bluefin-logistics` clicks "Export contacts". `edge-lb` forwards the request to `ferngrove-web`.
2. `export_contacts` queries 412880 rows. This takes 12 seconds and sends no byte.
3. At 30 seconds, `edge-lb` sees no byte in either direction. It closes the connection and returns 504.
4. `export_contacts` keeps building the CSV, 77 more seconds (`build_seconds=77`). Nobody receives it. The worker finishes at 89 seconds, under the gunicorn `timeout = 120`.
5. The log records `status=504 reason=edge-lb-idle-timeout` at 09:12 and again at 14:02. `harrow-dental` with 3120 rows finishes in 1 second and works.

The 504 is not a gunicorn timeout. At 89 to 90 seconds the export is also close to the 120-second limit, so a larger tenant will hit that limit next.

**Timeline with the fix**, diverges at step 2.

2. `export_contacts` returns a streaming response and yields the CSV header at once. `edge-lb` receives the first byte and resets its timer.
3. The query runs and rows are yielded in batches. Each batch resets the idle timer, so `edge-lb` never sees 30 silent seconds.
4. The browser downloads the file as it is produced.
5. The last batch is sent and the response ends. The log records `status=200` for `bluefin-logistics`.

**What changes**

- `app/exports.py` old behaviour: `export_contacts` builds a `StringIO` and returns `getvalue()`. New behaviour: it returns a generator that yields the header, then rows in batches of about 1000 from a cursor.
- `deploy/gunicorn.conf.py`: the file sets no `worker_class`, so it uses the default sync worker. I expect `timeout = 120` to still apply to a stream that lasts longer. Moving to a gthread or gevent worker class is a separate decision.

**Recommendation.** Aelita recommends streaming because it removes the root cause, which is that the first byte waits for the whole export. It adds no component, which fits `docs/exports.md:9`. What can break:

- **Unverified:** `ferngrove.web.Response` may not accept an iterator, and `ferngrove.db` may not offer a cursor. The `ferngrove` package is not in this repository, so no file settles either point.
- **Sync worker limit:** a stream that lasts over 120 seconds still gets the worker killed. Streaming also holds a worker for the full export, and there are 16 workers at about 6 exports a day.
- **Mid-stream errors:** an error after the header can no longer return a 500. The download just truncates.

**Alternative: raise `idle_timeout_seconds` to 300.** This is a one-line change in `deploy/edge-lb.yaml`. It beats streaming on effort. The cost is that every route on `ferngrove-web` gets a longer idle limit, and the gunicorn 120-second limit still caps it. It becomes the primary only if the streaming API turns out not to exist and a fix is needed today.

**Alternative: background job and email link.** The export runs offline and the user gets a download link. It has no timeout limit. It needs a job queue and an email service, and `docs/exports.md:9` says each needs an owner and on-call. It becomes the primary if exports grow well beyond the gunicorn limit.
