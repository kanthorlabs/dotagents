Caching the pnpm store should cut the median `ci` run in `fernway-web` from 11 min 05 s to about 8 min 00 s, a saving of 28%. Aelita recommends `cache: pnpm` on `actions/setup-node`. It is a one-line change.

**Timeline without the fix**

1. A developer pushes a branch. Workflow `ci` starts, because `on.push.branches` is `["**"]`.
2. `actions/setup-node@v4` installs Node 22 and restores nothing.
3. Step `Install` runs `pnpm install --frozen-lockfile` and downloads the full 1.1 GB store. The median is 3 min 40 s.
4. Steps `Lint` and `Test` run.
5. The run ends after 11 min 05 s. All 412 runs of week 43 repeated the same download, and developers waited each time before merging.

**Timeline with the fix**, diverges at step 2.

2. `actions/setup-node@v4` installs Node 22 and restores the pnpm store. The key comes from the hash of the lockfile.
3. Step `Install` finds a warm store. The median is 0 min 35 s, which is 3 min 05 s less.
4. Steps `Lint` and `Test` run unchanged.
5. The run ends after about 8 min 00 s.

**What it buys, from `docs/ci-metrics.md`**

- **Developer wait:** 3 min 05 s less on every push, 28% of the median run.
- **Runner time:** 412 runs × 3.08 min is about 1,270 minutes, or 21 hours per week.
- **Money:** 1,270 min × 0.008 USD is about 10 USD per week. The money is small. The wait time is the real gain.

**What changes**

- `.github/workflows/ci.yml`, step `actions/setup-node@v4`. Old: `with: node-version: 22`. New: add `cache: pnpm` under `with`. `pnpm/action-setup@v4` already runs before it, which this option requires.

**Recommendation.** Aelita recommends `cache: pnpm` because it is one line and the action manages the key and the store path. It has these costs and risks:

- **Cache misses:** The first run after each lockfile change is a miss. That run still takes 3 min 40 s and adds a save step.
- **Eviction:** The store is 1.1 GB and the repository limit is 10 GB. About 9 full entries fit before eviction. Many branches with changed lockfiles can evict the entry of `main`. The cache is compressed, so the real entry is likely smaller. That size is unverified.
- **Measurement:** The 0 min 35 s figure comes from 20 manual runs with a warm store. It excludes restore time, so the real saving is slightly lower.
- **Lockfile:** This directory holds only `ci.yml` and `docs/ci-metrics.md`. I could not check the lockfile. `setup-node` fails if it finds no `pnpm-lock.yaml`. `--frozen-lockfile` suggests the file exists in the real repository.

**Alternative: `actions/cache` with an explicit key.** It uses the store path from `pnpm store path` and a key from `hashFiles('pnpm-lock.yaml')`. It beats the recommendation when you need `restore-keys` fallbacks or a custom lockfile path. It costs about ten more lines to maintain. It becomes the primary if eviction of the `main` entry shows up in practice.
