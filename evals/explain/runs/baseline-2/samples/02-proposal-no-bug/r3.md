Caching the pnpm store cuts the median `Install` step from 3 min 40 s to about 35 s. That saves about 3 min 05 s per run, roughly 21 hours of waiting and 10 USD of runner time per week. Aelita recommends `cache: pnpm` on `actions/setup-node@v4`, which is a one-line change.

**Timeline without the fix**

1. A developer pushes a branch. `ci` starts on `ubuntu-24.04`.
2. `actions/checkout@v4`, `pnpm/action-setup@v4` and `actions/setup-node@v4` run.
3. `Install` runs `pnpm install --frozen-lockfile` with an empty store. It downloads 1.1 GB and takes 3 min 40 s.
4. `Lint` and `Test` run.
5. The run ends at a median of 11 min 05 s. The developer waits, because merges depend on `ci`.

**Timeline with the fix**, diverges at step 3.

3. `setup-node` restores the pnpm store from the cache, keyed on the hash of `pnpm-lock.yaml`. `Install` links packages from the local store and takes about 35 s.
4. `Lint` and `Test` run unchanged.
5. The run ends at about 8 min 00 s, which is 28% shorter (665 s minus 185 s).

**What it buys**

- **Time.** 185 s saved per run, across 412 runs per week, is about 1,270 minutes, or 21 hours.
- **Money.** 1,270 minutes at 0.008 USD per minute is about 10 USD per week.
- **Merge speed.** About 60 pull requests merge per week, and each one waits roughly 3 minutes less per CI run.

**What changes**

- `.github/workflows/ci.yml` step `actions/setup-node@v4`: add `cache: pnpm` under `with`. The order is already correct, because `pnpm/action-setup@v4` runs before `setup-node`.

**Recommendation.** Aelita recommends `cache: pnpm` because it needs no new step and no hand-written key. The cost is cache storage. The store is 1.1 GB against a 10 GB repository limit, and every lockfile change writes a new entry. Old entries are evicted least-recently-used first, so about 9 entries fit.

**Caveats for the team**

- **Measurement.** The 35 s figure comes from 20 manual runs with a warm store. The doc does not say whether it includes the cache restore time. A 1.1 GB restore may add some seconds, so the real saving is slightly lower.
- **Branch scope.** `ci` runs on every branch. A feature branch can read the default branch cache but not another feature branch's cache. The cache must be saved on the default branch for most runs to hit it.
- **Lockfile changes.** A run that changes `pnpm-lock.yaml` misses the cache once and pays the full 3 min 40 s.
- **Missing files.** The snapshot here has no `package.json` or `pnpm-lock.yaml`. `cache: pnpm` needs the lockfile, and `--frozen-lockfile` implies it exists in the real repository.

**Alternative: `actions/cache` with an explicit store path.** It gives control over the key and `restore-keys`, so a lockfile change can still reuse a near-match cache. It costs about 6 more lines in `ci.yml`. It becomes the primary if lockfile changes are frequent and the miss cost matters.
