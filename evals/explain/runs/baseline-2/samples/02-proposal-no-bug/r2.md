Caching the pnpm store cuts the median `Install` step from 3 min 40 s to 35 s. Per `docs/ci-metrics.md`, that saves about 3 min 05 s per run, or about 21 runner-hours and 10 USD per week. Aelita recommends `cache: pnpm` on `actions/setup-node@v4`.

**Timeline without the fix**

1. A developer pushes a branch of `fernway-web`. The `ci` workflow starts on `ubuntu-24.04`.
2. `actions/checkout@v4` and `pnpm/action-setup@v4` finish.
3. `actions/setup-node@v4` installs Node 22. It caches nothing.
4. `pnpm install --frozen-lockfile` downloads every package, a store of 1.1 GB. The median is 3 min 40 s.
5. `pnpm lint` and `pnpm test` run. The median total is 11 min 05 s.
6. The developer waits 11 min 05 s before merging. Over week 43 that repeated 412 times, with 3 min 05 s of each run spent re-downloading packages that did not change.

**Timeline with the fix**, diverges at step 3.

3. `actions/setup-node@v4` installs Node 22. It restores the pnpm store, keyed on the hash of `pnpm-lock.yaml`.
4. `pnpm install --frozen-lockfile` finds the packages in the store. The measured median is 35 s.
5. `pnpm lint` and `pnpm test` run. The median total drops to about 8 min 00 s.
6. The developer waits about 3 min 05 s less per run. The week saves 412 × 3.08 min, about 1,270 minutes. That is about 10.16 USD at 0.008 USD per minute.

**What changes**

- `.github/workflows/ci.yml`: add `cache: pnpm` under `with:` of the step `actions/setup-node@v4`. The step already runs after `pnpm/action-setup@v4`, which this option requires. Nothing else changes.

**Recommendation.** Aelita recommends the built-in `cache: pnpm` option. It is one added line and needs no separate `actions/cache` step. It keys the cache on the lockfile hash by default.

- **Cost:** each lockfile change writes a new entry, up to 1.1 GB uncompressed. The repository limit is 10 GB. GitHub evicts the oldest entries first, so old entries cannot block new ones.
- **What can break:** a cold run after a lockfile change is no faster than today. The cache also adds restore and save time.

**Caveats on the numbers**

- **Warm-store figure:** the 35 s comes from 20 manual runs. The metrics file does not say whether it includes cache restore time. Treat 8 min 00 s as an estimate until a real cached run confirms it.
- **Repo contents:** this checkout holds only `ci.yml` and `docs/ci-metrics.md`. I could not read `pnpm-lock.yaml`, so I did not check the lockfile path.

**Alternative: `actions/cache` with an explicit key.** It lets you add `restore-keys` for partial hits after a lockfile change. It costs about six more lines. It becomes the primary if cold runs after lockfile changes hurt.
