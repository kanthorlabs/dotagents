`purge-worker` deletes in-progress uploads for `acme-labs` because `validate` accepts `retention_days: 0`, but `docs/retention.md` supports only 1 to 3650. Aelita recommends that `validate` rejects values below 1. That matches the documented contract.

**Existing behaviour**

1. `TenantConfig.validate` in `config/schema.py:10` rejects only values below 0, so 0 passes.
2. `purge_tenant` in `purge/worker.py:5` computes `cutoff = now - timedelta(days=0)`, which is now.
3. `purge_tenant` deletes every upload with `created_at < cutoff` (line 7).
4. The worker never checks whether an upload has finished. `created_at` is the start time.

**Timeline without the fix**

1. Tenant `acme-labs` sets `retention_days: 0` in `tenants/acme-labs.yaml`.
2. `validate` accepts it, because 0 is not below 0.
3. A user starts a multipart upload at 10:00. It can run for up to 6 hours.
4. `purge-worker` runs at 10:15. The cutoff is 10:15.
5. The upload has `created_at` 10:00, which is before the cutoff, so `purge-worker` calls `store.delete`.
6. The upload is deleted while still in progress. The user loses data mid-transfer.

**Timeline with the fix**, diverges at step 2.

2. `validate` raises `ValueError("retention_days must be >= 1")`. The tenant config does not load.
3. The owner of `acme-labs` sees the error and removes the setting or picks 1 or more. Per the docs, a tenant that wants no retention deletes through the API.
4. With `retention_days: 1`, the 10:15 run uses a cutoff of yesterday 10:15, so the upload survives.

**What changes**

- `config/schema.py` old behaviour: `validate` raises when `retention_days < 0`. New behaviour: `validate` raises when `retention_days < 1`, with the message `retention_days must be >= 1`.
- `tenants/acme-labs.yaml` old value: `retention_days: 0`. New value: `retention_days: 1`, or the tenant deletes through the API.

**Recommendation.** Aelita recommends the stricter validation. It removes the root cause, a config value outside the documented range, and it adds no new mechanism. It can break any other tenant file that already uses 0. The search found only `acme-labs`. One gap remains: `validate` has no upper bound, so 3650 is still unenforced. A value of 1 also does not protect an upload that runs longer than the retention, but the 6-hour limit makes that impossible.

**Alternative: skip in-progress uploads in `purge_tenant`.** The worker would delete only uploads that are complete. It beats the recommendation when 0 must stay valid, for example when a tenant needs fast deletion of finished uploads. It costs a status field on uploads. I found no such field in this repository, so `store` would need one. It becomes the primary if the docs change to allow 0.

**Question.** Does Aelita change `validate` to reject values below 1 and set `acme-labs` to 1, or do you want 0 to stay valid with a worker guard for in-progress uploads?
