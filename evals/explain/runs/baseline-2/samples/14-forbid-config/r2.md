`purge-worker` deleted the in-progress uploads because `TenantConfig.validate` accepts `retention_days: 0`, which `docs/retention.md` does not support, so the cutoff becomes "now". Aelita recommends that `validate` reject values outside 1 to 3650, the range the docs already state.

**Timeline without the fix**

1. `acme-labs` sets `retention_days: 0` in `tenants/acme-labs.yaml`.
2. `TenantConfig.validate` checks `retention_days < 0`. Zero passes.
3. A user of `acme-labs` starts a multipart upload. It can stay in progress for up to 6 hours.
4. `purge-worker` runs and computes `cutoff = now - timedelta(days=0)`, which is now.
5. `purge_tenant` compares `upload.created_at < cutoff`. The in-progress upload started earlier, so it matches.
6. `purge_tenant` calls `store.delete`. The in-progress upload is deleted, and the user's multipart upload fails.

**Timeline with the fix**, diverges at step 2.

2. `TenantConfig.validate` checks `1 <= retention_days <= 3650`. Zero raises `ValueError`, so `acme-labs` cannot load with that value.
3. `acme-labs` must pick a valid value, or use the API to delete uploads, as `docs/retention.md` says.
4. The in-progress upload is not at risk from a zero cutoff. The smallest cutoff is one day, longer than the 6-hour upload limit.

**What changes**

- `config/schema.py` old behaviour: `validate` raises only when `retention_days < 0`. New behaviour: `validate` raises unless `1 <= retention_days <= 3650`, with a message naming that range.
- `tenants/acme-labs.yaml` old value: `retention_days: 0`. New value: a value from 1 to 3650, chosen by the tenant.

**Recommendation.** Aelita recommends tightening `validate` to the documented range. The code and the docs then agree, and the bad value cannot enter the system. The cost is one line. It breaks loading of `acme-labs` until its value changes. I found no caller of `validate` in this repository, so this fix only works if the loader that reads `tenants/*.yaml` calls it. That loader is not in `vaultline`.

**Alternative: skip in-progress uploads in `purge_tenant`.** The worker would skip uploads that have not completed. It is safe even if a bad config slips through. It costs a new status field, because `store.list_uploads` exposes none in this repository. It becomes the primary if `retention_days: 0` must stay valid.
