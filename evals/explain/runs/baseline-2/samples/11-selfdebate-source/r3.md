The same `digest-builder` job runs twice every Monday, once from `ops-box-2` cron and once from the Kubernetes CronJob. Aelita recommends deleting the `digest_builder` line from the `ops-box-2` crontab. That removes the cause. Your two fixes only guard against the symptom.

**Existing behaviour**

1. `ops/hosts/ops-box-2/crontab` runs `python -m jobs.digest_builder` at `0 6 * * 1`.
2. `deploy/k8s/cronjob-digest-builder.yaml` runs the same module at the same schedule.
3. `jobs/digest_builder.py` inserts one `pending` outbox row per active subscriber. It does no check for an existing row.
4. `mailer/digest_mailer.py` sends every `pending` row.

**Timeline without the fix**

1. Monday 06:00:02Z. `ops-box-2` starts `jobs.digest_builder`.
2. 06:00:04Z. Pod `digest-builder-29353080-k7x2q` starts the same job. `concurrencyPolicy: Forbid` only covers the Kubernetes side, so it does not stop the cron host.
3. 06:01:10Z. `ops-box-2` logs `enqueued=18412`.
4. 06:01:13Z. The pod logs `enqueued=18412`. `outbox` now holds two rows per subscriber for the same `digest_date`.
5. `digest-mailer` reads all `pending` rows and sends each one.
6. Every subscriber gets the Monday digest twice.

The cutover checklist in `docs/migrations/2026-09-k8s-cutover.md` shows why. The Kubernetes job was created and verified. The line "Remove the `digest_builder` line from the crontab of `ops-box-2`" was never ticked.

**Timeline with the fix**, diverges at step 1.

1. Monday 06:00. Only the Kubernetes CronJob starts `jobs.digest_builder`. `ops-box-2` no longer fires.
2. The pod enqueues 18412 rows, one per subscriber.
3. `digest-mailer` sends each row once.
4. Every subscriber gets one digest.

**What changes**

- `ops/hosts/ops-box-2/crontab`: delete line 3, the `digest_builder` entry. Also deploy it to the host, because the 26 October log shows the host still runs it.

**Recommendation.** Aelita recommends removing the crontab line. It fixes the cause with no code change, and the checklist already lists it. The cost is one edit on `ops-box-2`. The risk is that someone re-adds the line, or that another host runs the job too.

**Why not your two options**

- **Dedupe by email in `digest-mailer`.** It leaves duplicate rows in `outbox`. It also merges distinct subscribers who share one address, and nothing stops a send between the two builds.
- **Unique index on `outbox(subscriber_id, digest_date)`.** This is the better of your two and is the alternative below.

**Alternative: unique index.** Add the index and change the `INSERT` in `jobs/digest_builder.py` to `ON CONFLICT (subscriber_id, digest_date) DO NOTHING`. Without that clause the second run crashes on its first insert. It protects against any future double scheduling. It costs a migration, and you must first delete the existing duplicate rows or the index build fails. It becomes the primary if more than one scheduler may legitimately exist, for example during a future migration.
