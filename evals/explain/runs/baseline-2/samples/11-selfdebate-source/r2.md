`digest-builder` runs twice every Monday, once from the `ops-box-2` crontab and once from the Kubernetes CronJob. Aelita recommends removing the crontab line, which neither of your two fixes does. It is the step still open in the cutover checklist.

**Timeline without the fix**

1. Henrik Saar cuts the scheduled jobs over to Kubernetes. `docs/migrations/2026-09-k8s-cutover.md` leaves "Remove the `digest_builder` line" unchecked.
2. Monday 06:00 UTC: cron on `ops-box-2` starts `jobs.digest_builder`, and the CronJob `digest-builder` starts a pod 2 seconds later.
3. `concurrencyPolicy: Forbid` only guards runs of the CronJob against each other. It cannot see the cron job on `ops-box-2`.
4. Each run inserts one `pending` row per active subscriber into `outbox`. `logs/digest-builder-2026-10-26.log` shows `enqueued=18412` from both.
5. `db/schema.sql` has no unique constraint on `outbox`, so the table holds 36824 rows for 18412 subscribers.
6. `send_pending` in `mailer/digest_mailer.py` sends every `pending` row. Each subscriber gets the digest twice.

**Timeline with the fix**, diverges at step 2.

2. Monday 06:00 UTC: only the CronJob `digest-builder` starts.
4. It inserts 18412 `pending` rows.
5. `outbox` holds one row per subscriber.
6. `send_pending` sends one digest per subscriber.

**What changes**

- `ops/hosts/ops-box-2/crontab`: delete line 3, `0 6 * * 1 ... jobs.digest_builder`. Keep line 2, `rotate-logs`.
- `docs/migrations/2026-09-k8s-cutover.md`: tick the item "Remove the `digest_builder` line".

**Recommendation.** Aelita recommends deleting the crontab line, because the duplicate run is the root cause. Both of your fixes only hide it. It costs one line, and it breaks nothing in the code. One thing I could not verify from the repo is whether the file in `ops/hosts/` is a copy of the live crontab. If it is, someone must also edit the live crontab on `ops-box-2`.

**Alternative: unique index on `outbox(subscriber_id, digest_date)`.** It beats the recommendation as a backstop against any future double run. It costs more than it looks:
- The existing duplicate rows must be deleted before the index can be created.
- `INSERT` in `jobs/digest_builder.py:7` needs `ON CONFLICT DO NOTHING`. Without it, the second run crashes halfway on a unique violation.

It becomes the primary if the builder must stay on two schedulers.

**Why not dedupe by email in `digest-mailer`.** It leaves the extra 18412 rows in `outbox` every week. It also drops legitimate rows if two subscribers share one address.
