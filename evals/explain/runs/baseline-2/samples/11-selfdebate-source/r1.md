The Monday digest goes out twice because the `digest-builder` job runs on two schedulers: the Kubernetes CronJob and the old crontab on `ops-box-2`. Aelita recommends deleting the crontab line, which removes the cause. Neither of your two fixes does that.

**Existing behaviour**

1. `jobs/digest_builder.py` inserts one `pending` row per active subscriber into `outbox`.
2. `outbox` has no unique constraint in `db/schema.sql`.
3. `mailer/digest_mailer.py` sends every `pending` row and then marks it `sent`.

**Timeline without the fix**

1. At 06:00:02 on 26 October, cron on `ops-box-2` starts `jobs.digest_builder`. The cutover checklist in `docs/migrations/2026-09-k8s-cutover.md` never ticked "remove the `digest_builder` line".
2. At 06:00:04, pod `digest-builder-29353080-k7x2q` starts the same job. `concurrencyPolicy: Forbid` only covers Kubernetes, so it cannot see `ops-box-2`.
3. Both runs log `enqueued=18412`. `outbox` now holds two `pending` rows per subscriber.
4. `digest-mailer` reads all 36824 pending rows.
5. `digest-mailer` sends one email per row. Every subscriber gets the digest twice.

**Timeline with the fix**, diverges at step 1.

1. `ops-box-2` has no digest line, so nothing starts there.
3. Only the pod inserts rows, so `outbox` holds 18412 `pending` rows.
4. `digest-mailer` reads 18412 rows.
5. Each subscriber gets one email.

**What changes**

- `ops/hosts/ops-box-2/crontab` deletes line 3, the `jobs.digest_builder` entry.
- `docs/migrations/2026-09-k8s-cutover.md` ticks line 8, the item that removes the `digest_builder` crontab line.

**Recommendation.** Aelita recommends deleting the crontab line. It removes the second scheduler and costs one edit on `ops-box-2`. Nothing else can break, because the pod already runs the job alone. The `rotate-logs` line on line 2 stays until its own checklist item.

**Why not your two options.**
- **Dedupe by email in `digest-mailer`.** This guards against the symptom and can still fail. If the mailer runs between the two builds, it sends once. The second build then adds new `pending` rows, and those get sent again. It also drops a legitimate row when two subscribers share an email.
- **Unique index on `outbox(subscriber_id, digest_date)`.** This is the better of your two, but `digest_builder.py:8` uses a plain `INSERT`. The losing run would crash on the first conflict. You would need `ON CONFLICT DO NOTHING` in that statement. You would also have to delete the existing duplicate rows before creating the index.

**Alternative: unique index plus `ON CONFLICT DO NOTHING`.** It makes the build idempotent however many schedulers fire. It costs a migration, a duplicate cleanup and a code change. It becomes the primary if you cannot edit `ops-box-2` soon. It also works as a second layer after the crontab fix.

**Question.** Do you approve deleting the `digest_builder` crontab line on `ops-box-2` as the fix, or do you want the unique index instead?
