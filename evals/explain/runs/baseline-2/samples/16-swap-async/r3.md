`export_invoices` in `app/exports.py` builds the whole CSV in memory and sends no byte until it finishes, so `gw-billing` cuts the request after 30 idle seconds. Aelita recommends moving the export to a `taskq` job on the `documents` queue that emails a signed link, as `render_invoice_pdf` already does.

**Timeline without the fix**

1. An accountant at `northfield-accounting` requests `/exports/invoices.csv` at month end.
2. `export_invoices` runs `db.query` and loads 1,840,211 rows. That takes 18 seconds, and `gw-billing` has received no byte yet.
3. `export_invoices` writes the rows into `io.StringIO` through `csv.writer`. That takes 222 seconds, and no byte leaves the worker.
4. `gw-billing` reaches 30 seconds without a byte and returns 504 with reason `gw-idle-timeout`.
5. The gunicorn worker keeps building the CSV until 240 seconds, because nothing tells it the client is gone. The accountant retries, and the retry starts another export.
6. Around 900 exports run in two days, so `web_workers_busy` reaches 12/12 and `/invoices` p99 climbs to 9.4 seconds. The largest tenants get no CSV, and every other tenant's invoice page slows down.

**Timeline with the fix**, diverges at step 2.

2. `export_invoices` enqueues `render_invoice_export(tenant_id, recipient)` on `documents` and returns 202 in milliseconds.
3. A `taskq` worker runs the query and writes the CSV to a temporary file, outside the web workers.
4. The job calls `storage.put` for `exports/<tenant_id>/invoices.csv`, then `storage.signed_url`.
5. The job calls `mailer.send` with the link.
6. The accountant downloads the file. Web workers stay free, so `/invoices` stays near its 0.4 second p99 from the 2026-10-15 log line.

**What changes**

- `app/exports.py`: `export_invoices` stops querying. It enqueues the job and returns 202.
- `jobs/invoice_export.py`: add `render_invoice_export`, modelled on `jobs/invoice_pdf.py`. It writes the CSV to a temp file, then calls `storage.put`, `storage.signed_url` and `mailer.send`.

**Recommendation.** Aelita recommends the background job. It removes the root cause, which is a long synchronous request on a web worker. It reuses `taskq`, `storage` and `mailer`, which `docs/exports.md` says already run in this stack. It costs a changed UX: the file arrives by email, not in the response. Two things can break it. The `documents` queue now carries about 900 more jobs in two days. And `storage.put` may not accept a file object, which I could not confirm from this repo.

**Alternative: stream the CSV.** `export_invoices` returns a generator, so bytes flow and the idle timeout never fires. The UX stays the same. It still holds a worker for the whole export and still hits the 300 second cap. The 1.84M row tenant already needs 240 seconds, so it will fail as that tenant grows. It becomes the primary if the product must return the file in the same request.

**Alternative: raise `idle_timeout_seconds`.** It is a one-line change in `deploy/gateway.yaml`. It guards against the symptom only. The worker exhaustion stays, and the 300 second cap stays.

**Question.** Does the export become an emailed `taskq` job, or must the file still download in the same request, which would make streaming the primary?
