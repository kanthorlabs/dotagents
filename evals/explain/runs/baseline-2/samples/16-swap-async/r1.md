`export_invoices` builds the whole CSV in memory before it sends a byte, so `gw-billing` closes the connection at its 30-second idle limit. Aelita recommends moving the export to a `taskq` job that emails a signed link, the way `render_invoice_pdf` already works.

**Timeline without the fix**

1. An accountant at `northfield-accounting` requests `GET /exports/invoices.csv`.
2. `export_invoices` takes 1 of the 12 gunicorn workers. It runs the query for 1,840,211 rows in 18 seconds.
3. `export_invoices` writes every row into one `io.StringIO` buffer. This takes 222 seconds, and the response sends no byte meanwhile.
4. `gw-billing` sees 30 seconds with no byte. It closes the connection and returns 504 with `reason=gw-idle-timeout`.
5. The worker ignores the closed connection and keeps building until second 240. At month end `web_workers_busy` reaches 12/12, and `/invoices` p99 rises to 9.4 seconds against 0.4 on a quiet day.
6. The accountant gets no file. The worker time is wasted, and other tenants slow down.

**What changes**

- `app/exports.py`: `export_invoices` no longer queries or builds the CSV. It enqueues `render_invoice_csv` and returns 202 with a short message.
- `jobs/invoice_csv.py` (add): the new `taskq` task on queue `documents` runs the query and writes the CSV in chunks to `storage`. It then calls `storage.signed_url` and `mailer.send`, as `jobs/invoice_pdf.py:5-9` does.

**Timeline with the fix**, diverges at step 2.

2. `export_invoices` enqueues `render_invoice_csv` for the tenant and returns 202 within milliseconds. The gunicorn worker is free again.
3. A `taskq` worker on `documents` runs the query and writes rows to a temporary file in batches. Memory stays flat, and no gateway timer applies.
4. The task calls `storage.put`, then `storage.signed_url`, and `mailer.send` emails the link to the accountant.
5. The accountant downloads the file from storage. The web workers never carry it.

**Recommendation.** Aelita recommends the async job. It removes the root cause, which is a long synchronous build inside a web worker. It also stops the month-end starvation of `/invoices`. The cost is a changed contract: callers get an email instead of a file. The 900 month-end exports also share the `documents` queue with PDFs, so a PDF can wait behind a large export. I found no file that sets the queue's concurrency, so I could not check that.

**Alternative: stream the response.** `export_invoices` yields rows as it reads them, so bytes flow and the idle timer never fires. It keeps the one-click download. It still holds a worker for the full build, and the 300-second total limit will kill a tenant above roughly 2.3 million rows. It becomes the primary only if accountants must get the file in the same click and no tenant exceeds that size.

**Alternative: raise `idle_timeout_seconds`.** This is a one-line change in `deploy/gateway.yaml`. It does not stop worker starvation, and 240 seconds is already near the 300-second cap. I would not pick it.
