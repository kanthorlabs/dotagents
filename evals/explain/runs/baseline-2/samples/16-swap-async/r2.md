`export_invoices` in `app/exports.py` sends no byte until it has built the whole CSV, so `gw-billing` closes the connection at its 30-second idle limit. Aelita recommends moving the export to a `taskq` job that emails a signed link, the way invoice PDFs already work.

**Timeline without the fix**

1. An accountant at `northfield-accounting` requests `/exports/invoices.csv` at month end.
2. `export_invoices` runs `db.query` for 1,840,211 rows. It takes 18 seconds and sends no byte.
3. The handler writes every row into `io.StringIO`. This takes 222 more seconds and sends no byte.
4. At 30 seconds `gw-billing` hits `idle_timeout_seconds: 30` and returns 504 to the accountant.
5. The gunicorn worker keeps building until 240 seconds. The log shows `web_workers_busy=12/12`, and each abandoned export holds one of the 12 workers.
6. `/invoices` p99 reaches 9.4 seconds, against 0.4 on a quiet day. The export fails and slows the rest of the app.

**Timeline with the fix**, diverges at step 2.

2. `export_invoices` enqueues `render_invoice_csv` on queue `documents`. It returns 202 within milliseconds.
3. A `taskq` worker runs the query, builds the CSV and calls `storage.put`. The 300-second gateway limit no longer applies.
4. The job calls `mailer.send` with a `storage.signed_url`. The accountant gets the link.
5. The gunicorn worker was free at step 2. `/invoices` latency stays flat.
6. The accountant downloads the file from storage. No gateway timeout applies.

**What changes**

- `app/exports.py`: `export_invoices` currently queries, builds the CSV and returns it. It will enqueue the job with `request.tenant_id` and the user's email, and return 202.
- `jobs/invoice_csv.py`: add `render_invoice_csv`, modelled on `render_invoice_pdf` in `jobs/invoice_pdf.py`. It writes the file to `storage` and mails the signed URL.

**Recommendation.** Aelita recommends the async job. It removes the cause, which is a long synchronous request on a gateway with a 30-second idle limit. It also frees the web workers at month end, when about 900 exports run in two days. The cost is that the user waits for an email instead of a download. The job should write rows to a file in chunks. A 1.84M-row `StringIO` is large, and I found no file that shows whether `db` supports a streaming cursor, so I have not verified that part.

**Alternative: stream the response.** The handler yields CSV chunks as it builds them, so bytes flow and the idle timer never fires. It keeps the download in the browser and needs no email. It still holds a gunicorn worker for the whole export, so month-end starvation stays. It also fails at 300 seconds total, and `northfield-accounting` took 240. It becomes the primary if exports must download immediately and tenants stay under about 250 seconds.

**Question.** Should `export_invoices` enqueue a `taskq` job that emails a signed link, or stream the response instead?
