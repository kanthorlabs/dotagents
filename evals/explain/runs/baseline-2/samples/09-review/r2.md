`handle` in `quillpay/webhooks.py` changes the ledger before it verifies the signature, so anyone can credit an account with a forged webhook. Aelita found 4 blockers and 4 suggestions. Only `pr-311.diff` exists in the directory, so the `ledger` code was not checked.

**Timeline without the fix**

1. An attacker posts a forged `charge.succeeded` event to the webhook URL. The event has `account_id` set to their account and a large `amount_cents`. It has no `Quill-Signature` header.
2. `handle` parses the body with `json.loads` at line 19.
3. `handle` logs the full payload at line 20.
4. `handle` calls `ledger.credit` at line 23.
5. `handle` calls `verify` at line 27. `verify` fails and `handle` returns 400.
6. The credit from step 4 is already written. The attacker is paid with no valid charge.

**Review findings**

- **B1 - status:OPEN - action:YES - Ledger changes before signature check** - `handle` runs `ledger.credit` and `ledger.debit` at lines 22-25, and only then calls `verify` at line 27. A rejected request still changes the ledger. - fix: move the `verify` call and its 400 return above `json.loads` and the ledger calls. - why: forged events move real money.
- **B2 - status:OPEN - action:YES - Default webhook secret** - `settings.py` sets `WEBHOOK_SECRET = os.environ.get("QUILL_WEBHOOK_SECRET", "dev-secret")`. A missing variable in production silently uses a public secret, and anyone can then sign valid events. - fix: use `os.environ["QUILL_WEBHOOK_SECRET"]`, as `DATABASE_URL` does on the line above. - why: the service should fail at start-up, not accept forged signatures.
- **B3 - status:OPEN - action:YES - Unsafe signature compare** - `verify` uses `expected == parts.get("v1")` at line 42. The comparison is not constant-time, so it leaks timing. - fix: use `hmac.compare_digest(expected, parts.get("v1", ""))`. - why: it blocks timing attacks on the signature.
- **B4 - status:OPEN - action:YES - Malformed header raises** - `verify` builds a dict from `header.split(",")` at line 33. An empty header gives `[""]`, and `"".split("=", 1)` has one element, so `dict` raises `ValueError`. A header like `t=abc` makes `int` raise too. Both cause a 500 instead of a 400. - fix: wrap the parse in `try/except ValueError` and return `False`. - why: the missing-header case is the default for any forged request.
- **S1 - status:OPEN - action:YES - No replay protection** - The 300-second window allows the same signed event to be replayed. A replayed `charge.succeeded` credits twice. - fix: store the event `id` and skip any id already seen. - why: payment providers retry events, and attackers replay them.
- **S2 - status:OPEN - action:YES - Payload logged in full** - Line 20 logs the raw body at info level. It holds account ids and amounts, and it is logged before verification. - fix: log only `event["type"]` and the event id, after verification. - why: it limits data exposure and log injection.
- **S3 - status:OPEN - action:YES - Unknown or malformed events** - `json.loads` and `event["data"][...]` raise on bad input, which gives a 500. Unknown types return 200 silently. - fix: return 400 on a parse error or missing key, and log unknown types at debug. - why: the provider's retry logic depends on correct status codes.
- **S4 - status:OPEN - action:YES - Dead code** - `_unused_helper` at lines 45-46 does nothing. - fix: delete it. - why: it adds noise.

**Recommendation.** Aelita recommends that you fix B1 to B4 before merge. B1 and B2 are the exploitable ones. The reorder in B1 is the smallest change that removes the root cause. The cost is a few lines. Nothing in the diff relies on the current order.
