Two `restock-planner` pods both ran `reorder` and each bought SKU HT-4410 because the lock never covered the 4-minute run. Either region fails this way for a different reason, so the fix covers both. Aelita recommends a 15-minute lock TTL in `planner/reorder.py` and a real lock backend in `config/us-east.yaml`.

**Existing behaviour**

1. `run_reorder` in `planner/reorder.py:5` calls `locks.acquire("reorder", ..., ttl_seconds=60)`.
2. `locks.acquire` in `planner/locks.py:7` returns `True` at once when `backend == "none"`.
3. Otherwise it runs Redis `SET lock:reorder NX EX 60`.
4. The winner loops over `items_below_reorder_point()` and creates a purchase order per item. It never releases the lock.

**Timeline without the fix, branch eu-west** (`lock_backend: redis`, `replicas: 2`)

1. At 01:00, pod A starts `reorder`.
2. Pod A sets `lock:reorder` with a 60-second TTL.
3. Pod A starts creating purchase orders. The job needs about 4 minutes.
4. At 01:01, the Redis key expires while pod A is still working.
5. At 01:02, pod B starts after the node restart.
6. Pod B sets the lock successfully and sends a second purchase order for HT-4410 to Halvorsen Tools.

**Timeline without the fix, branch us-east** (`lock_backend: none`, autoscale up to 3 replicas)

1. At 01:00, pod A starts `reorder`.
2. `locks.acquire` returns `True` without any check.
3. Pod A starts creating purchase orders.
4. Nothing holds a lock at any point.
5. At 01:02, pod B starts.
6. `locks.acquire` returns `True` again, and pod B sends the second purchase order for HT-4410.

**Timeline with the fix, branch eu-west**, diverges at step 2.

2. Pod A sets `lock:reorder` with a 900-second TTL.
4. The key stays alive for the whole 4-minute run.
5. At 01:02, pod B starts.
6. `SET NX` fails and pod B returns `skipped`. Halvorsen Tools gets one order.

**Timeline with the fix, branch us-east**, diverges at step 2.

2. `config/us-east.yaml` now says `lock_backend: redis`, so pod A takes a real lock.
4. The key stays alive for the whole run.
5. At 01:02, pod B starts.
6. Pod B fails to get the lock and returns `skipped`.

**What changes**

- `planner/reorder.py:5`: old `ttl_seconds=60`, new `ttl_seconds=900`. This is about 3 times the observed runtime.
- `config/us-east.yaml`: old `lock_backend: none`, new `lock_backend: redis`.
- `planner/locks.py:7`: delete the `if backend == "none": return True` branch, so no region can turn the lock off again.

**Recommendation.** Aelita recommends the longer TTL plus the removal of `none`. This removes both causes, and it works without knowing which region ran the duplicate. It costs nothing at runtime. Two things can break:
- If a pod crashes mid-run, `reorder` stays locked for up to 15 minutes. That night's run may then be skipped.
- If `us-east` cannot reach `redis-locks`, `acquire` raises an error and `reorder` fails. Today it would run unlocked.

I do not release the lock after `done`. A release would let a late pod rerun the job and buy again.

**Alternative: idempotency key per purchase order.** `purchasing.create_purchase_order` would take a key such as `sku + date` and reject repeats. It protects even if the lock fails. It costs a change in `purchasing`, which is not in this repository, so I could not read it. It becomes the primary if lock outages must never cause double purchases.
