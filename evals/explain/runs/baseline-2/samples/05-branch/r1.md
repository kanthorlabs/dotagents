`restock-planner` sent two purchase orders for HT-4410 because the `reorder` lock failed to keep the second pod out in either region. You don't need to know the region. Aelita recommends a 900-second lock TTL and removing the `none` lock backend, which fixes both regions.

**Branch: eu-west** (`lock_backend: redis`, `ttl_seconds=60` in `planner/reorder.py:5`)

*Timeline without the fix*

1. Pod A starts `reorder` at 01:00. `locks.acquire` sets `lock:reorder` in Redis with a 60-second expiry.
2. Pod A reads the items below reorder point and creates a purchase order for HT-4410.
3. The lock expires at 01:01. Pod A is still running, because the job takes about 4 minutes.
4. Pod B starts at 01:02 after the node restart. `set(nx=True)` succeeds because the key is gone.
5. Pod B creates a second purchase order for HT-4410.
6. Halvorsen Tools receives two identical orders.

*Timeline with the fix*, diverges at step 3.

3. The lock lasts 900 seconds, so it is still held at 01:02.
4. Pod B's `set(nx=True)` fails and `run_reorder` returns `skipped`. Only one order exists.

**Branch: us-east** (`lock_backend: none`, `replicas: 1`, `autoscale_max_replicas: 3`)

*Timeline without the fix*

1. Pod A starts `reorder` at 01:00. `locks.acquire` returns `True` at once because the backend is `none`.
2. Pod A creates a purchase order for HT-4410.
3. No lock exists, so nothing marks the job as running.
4. Pod B starts at 01:02 and `acquire` returns `True` again.
5. Pod B creates a second purchase order for HT-4410.
6. Halvorsen Tools receives two identical orders.

*Timeline with the fix*, diverges at step 1.

1. `acquire` always uses Redis and takes `lock:reorder` for 900 seconds.
4. Pod B's `set(nx=True)` fails and `run_reorder` returns `skipped`. Only one order exists.

**What changes**

- `planner/reorder.py`: `ttl_seconds=60` becomes `ttl_seconds=900`. This is more than three times the 4-minute runtime.
- `planner/locks.py`: delete the `if backend == "none": return True` branch. Keep the `backend` argument in the signature so callers don't break.
- `config/us-east.yaml`: `lock_backend: none` becomes `lock_backend: redis`.

**Recommendation.** Aelita recommends the longer TTL and no `none` backend. It removes the two causes the repo shows: a lock that expires before the job ends, and a region with no lock. The TTL needs no new code. Forbidding `none` means no region can turn the lock off again. The cost is that a crashed pod holds the lock for up to 15 minutes. That is harmless for a nightly job. The risk is that `redis-locks` must be reachable from `us-east`. I found no file that settles this.

**Alternative: idempotent purchase orders.** `create_purchase_order` would take a key of SKU, supplier and run date, and refuse a repeat. It beats the lock because it also survives a lock outage or a TTL that is too short. It costs a change in `stockpile.purchasing`, which is not in this repository, so I could not read it. It becomes the primary if you want protection that does not depend on Redis.
