`restock-planner` sent Halvorsen Tools two purchase orders for HT-4410 because the `reorder` lock does not protect a 4-minute job in either region. The region does not matter, because both configs fail. Aelita recommends raising the lock TTL to 3600 seconds and setting `lock_backend: redis` in `config/us-east.yaml`.

**Existing behaviour**

1. `run_reorder` in `planner/reorder.py:5` calls `locks.acquire("reorder", ..., ttl_seconds=60)`.
2. `acquire` in `planner/locks.py:9` runs Redis `SET lock:reorder NX EX 60`. It never releases the lock, so the lock lives only as long as the TTL.
3. With `lock_backend: none`, `acquire` returns `True` at `planner/locks.py:8` and never touches Redis.
4. A pod that gets the lock loops over `db.items_below_reorder_point()` and creates one purchase order per item.

**Branch eu-west** (`lock_backend: redis`, TTL 60s, job about 4 minutes)

Timeline without the fix:

1. Pod A starts `reorder` at 01:00 and takes `lock:reorder` with a 60s TTL.
2. Pod A starts its loop. It needs about 4 minutes.
3. The lock expires at 01:01 while pod A is still running.
4. A node restart starts pod B at 01:02. `SET NX` succeeds because the key is gone.
5. Pod B reads the same below-reorder-point list, which still includes HT-4410. It creates its own order.
6. Halvorsen Tools receives two identical purchase orders.

Timeline with the fix, diverges at step 3:

3. The lock has a 3600s TTL and is still held at 01:01.
4. Pod B starts at 01:02. `SET NX` fails and `run_reorder` returns `"skipped"`.
5. Only pod A creates orders.
6. Halvorsen Tools receives one purchase order.

**Branch us-east** (`lock_backend: none`)

Timeline without the fix:

1. Pod A starts `reorder` at 01:00. `acquire` returns `True` without checking anything.
2. Pod A starts its loop.
3. No lock exists anywhere.
4. Pod B starts at 01:02. `acquire` returns `True` again.
5. Both pods create an order for HT-4410.
6. Halvorsen Tools receives two identical purchase orders.

Timeline with the fix, diverges at step 1:

1. `lock_backend: redis` makes pod A take `lock:reorder` with a 3600s TTL.
3. The lock is held in Redis.
4. Pod B's `SET NX` fails and it returns `"skipped"`.
5. Only pod A creates orders.
6. Halvorsen Tools receives one purchase order.

**What changes**

- `planner/reorder.py` old behaviour: `ttl_seconds=60`. New behaviour: `ttl_seconds=3600`.
- `config/us-east.yaml` old behaviour: `lock_backend: none`. New behaviour: `lock_backend: redis`.

**Recommendation.** Aelita recommends the longer TTL plus a real lock in `us-east`. The TTL is about 15 times the job runtime, and the job runs once a night. The cost is that a pod crash mid-run blocks a retry for up to an hour. That block is acceptable, because a retry would re-order the items the first pod already ordered. The TTL still fails if the job ever runs longer than an hour.

**Alternative: make `create_purchase_order` idempotent.** Key each order on SKU plus date, so a second order is rejected. This removes the root cause, and it is safe even when a lock fails. It beats the recommendation if `reorder` must tolerate any lock failure. `purchasing` is not in this repository, so I could not check how it works. It becomes the primary if you can change `purchasing`.

**Question.** Do you approve raising the TTL to 3600 and switching `us-east` to `lock_backend: redis`, or do you want the idempotent purchase order instead?
