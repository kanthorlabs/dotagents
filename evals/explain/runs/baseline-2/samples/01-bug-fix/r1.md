`list_orders` sorts by `created_at` alone, and `import_tidewater_batch` gives every row in a batch the same `created_at`. Postgres may order those tied rows differently on each page query, so page boundaries drop some orders and repeat others. Aelita recommends adding `id DESC` as a tiebreaker in `ORDER BY`.

**Existing behaviour**

1. `import_tidewater_batch` reads the clock once into `batch_time`.
2. It inserts all ~200 rows of the batch with that same `created_at`.
3. `list_orders` runs `ORDER BY created_at DESC LIMIT 50 OFFSET (page-1)*50`.
4. For rows with equal `created_at`, SQL does not define an order. Postgres can return them differently on each query.

**Timeline without the fix**

1. Brennan Hardware holds 1,214 orders. A Tidewater batch of 200 shares one `created_at`.
2. The client requests page 3. The batch straddles the page 3 and page 4 boundary.
3. Postgres returns the first 50 rows of the sort, with tied rows in order A.
4. The client requests page 4. Postgres sorts the tied rows again, this time in order B.
5. Some orders from the batch were on page 3 and appear again on page 4. Others were on neither page.
6. The export holds 1,214 rows, but 9 ids appear twice and 9 are missing. Each duplicate takes the place of one missing order, so the row count still matches.

**Timeline with the fix**, diverges at step 3.

3. Postgres sorts by `created_at DESC, id DESC`. Every row has one fixed position.
4. Page 4 continues exactly where page 3 stopped.
5. No order repeats and none is skipped.
6. The export holds 1,214 distinct rows.

**What changes**

- `src/orders/list_orders.py` old behaviour: `ORDER BY created_at DESC`. New behaviour: `ORDER BY created_at DESC, id DESC`.

**Recommendation.** Aelita recommends the tiebreaker, because it removes the cause: an ordering that is not total. `id` is the primary key, so it is unique and the order becomes fully determined. It costs one extra sort column. It breaks nothing for clients. An order created between two page requests can still shift the pages, but the ticket says none were created during this export.

**Alternative: keyset pagination.** The client passes the last `(created_at, id)` it saw instead of a page number. It stays correct even when new orders arrive mid-export. It changes the API contract in `docs/api.md` and breaks `?page=N` clients. It becomes the primary when exports must stay correct during live writes.

**Alternative: unique `created_at` in `bulk_import.py`.** It reads the clock per row. It does not repair existing batches and it leaves the query unordered for any future ties. It is not a standalone fix.
