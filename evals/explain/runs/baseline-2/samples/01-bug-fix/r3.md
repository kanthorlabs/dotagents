Brennan Hardware's export breaks because `list_orders` sorts only by `created_at`, and `bulk_import.import_tidewater_batch` gives every order in a batch the same `created_at`. Aelita recommends adding `id` as a tie-breaker in the `ORDER BY`. It is a one-line change.

**Existing behaviour**

1. `import_tidewater_batch` sets one `batch_time` and inserts about 200 orders with that same `created_at` (`src/orders/bulk_import.py:5-10`).
2. `list_orders` runs `ORDER BY created_at DESC LIMIT 50 OFFSET (page-1)*50` (`src/orders/list_orders.py:6-10`).
3. PostgreSQL does not define the order of rows that tie on the sort key. Each page is a separate query and may order the tied rows differently.

**Timeline without the fix**

1. Brennan Hardware imports a Tidewater batch. Orders 9001 to 9200 all share one `created_at`.
2. The client requests page 3. PostgreSQL sorts the ties in one arbitrary order and returns 50 of them.
3. The client requests page 4. This is a new query, and it may sort the same ties in a different order.
4. Page 4 repeats some ids that page 3 already returned. It also skips some ids that neither page returned.
5. The client stops at page 25, which holds 14 rows. The row count still matches the tenant total of 1,214.
6. The export holds 9 duplicated ids and 9 missing ids. That matches HO-212.

**Timeline with the fix**, diverges at step 3.

3. The client requests page 4. The query sorts by `created_at DESC, id DESC`, so ties always come out in the same order.
4. Page 4 starts exactly where page 3 ended. No id repeats and none is skipped.
5. The client stops at page 25 with 14 rows.
6. The export holds 1,214 unique orders.

**What changes**

- `src/orders/list_orders.py:8` old: `ORDER BY created_at DESC`. New: `ORDER BY created_at DESC, id DESC`.

**Recommendation.** Aelita recommends the `id` tie-breaker. It removes the root cause, which is a non-unique sort key. `id` is the primary key, so the order is total, and the API contract stays unchanged. The cost is a sort on two columns. I found no schema or index files here, so I cannot check the existing indexes. A composite index on `(tenant_id, created_at DESC, id DESC)` keeps it fast if one is not already there. I could not run the database. The tie ordering is a documented PostgreSQL freedom, and the ticket's 9 and 9 counts fit it, but I have not reproduced it.

**Alternative: keyset pagination.** The client sends the last `(created_at, id)` it saw instead of `page=N`. It beats the recommendation when orders can be created mid-export, because `OFFSET` also shifts rows then. It changes the API in `docs/api.md` and breaks existing clients. It becomes the primary if exports must be safe against live writes.

**Alternative: unique `created_at` per row in `bulk_import.py`.** This fixes only new imports. Existing rows keep their ties, so I do not recommend it.
