`list_orders` sorts only by `created_at`, and `import_tidewater_batch` gives about 200 orders the same `created_at`. Postgres can order those tied rows differently on each page query, so `LIMIT/OFFSET` pages overlap and leave gaps. Aelita recommends adding `id DESC` as a tiebreaker.

**Timeline without the fix**

1. `import_tidewater_batch` stamps every row of a batch with one `batch_time`. About 200 Brennan Hardware orders share one `created_at`.
2. The client requests page 3 of `GET /orders`. `list_orders` runs `ORDER BY created_at DESC LIMIT 50 OFFSET 100`.
3. Postgres returns the tied rows in an arbitrary order. The order is not guaranteed to repeat between queries.
4. The client requests page 4 with `OFFSET 150`. This is a separate query, so Postgres may order the same tied rows differently.
5. A page boundary falls inside a tied batch. Some ids from that batch land on both page 3 and page 4, and other ids land on neither.
6. Every page still holds 50 rows, so the export totals 1,214 rows. It holds 9 duplicate ids and 9 missing ids, as in HO-212.

**Timeline with the fix**, diverges at step 3.

3. `list_orders` sorts by `created_at DESC, id DESC`. Every row has a unique position, so the order is the same on each query.
4. Page 4 with `OFFSET 150` continues the same sequence that page 3 used.
5. A page boundary cuts the tied batch at one fixed point. Each id appears on exactly one page.
6. The export holds 1,214 unique ids.

**What changes**

- `src/orders/list_orders.py`: old `ORDER BY created_at DESC`. New `ORDER BY created_at DESC, id DESC`. `id` is the `bigserial` primary key, so it is unique.

**Recommendation.** Aelita recommends the `id DESC` tiebreaker. It removes the cause, which is a non-unique sort key. It changes one line and keeps the API contract in `docs/api.md`. Postgres may need an index on `(tenant_id, created_at DESC, id DESC)` to avoid a full sort on large tenants. I found no index definition in the repo, so I did not check this.

**Alternative: keyset pagination.** The client sends the last `(created_at, id)` it saw instead of `page=N`. It stays correct if orders are created during an export, which `OFFSET` does not. It changes the API contract and every client. It becomes the primary when exports must stay correct while new orders arrive.
