Dropping `legacy_sku` today would break the nightly Oakline Supply feed, so Aelita recommends moving the Brightstock codes into a new table first and dropping the column afterwards. Your grep covered only `src/`. Three other places use the column.

**Existing behaviour**

1. `db/views.sql:4` defines `v_partner_feed` with `COALESCE(p.legacy_sku, p.sku) AS partner_ref`.
2. `jobs/partner_feed_export.py:7` selects `partner_ref` from `v_partner_feed` and uploads the CSV to `sftp.oaklinesupply.com`.
3. `docs/history/2024-brightstock-migration.md:6` says Oakline Supply still keys its catalog on the Brightstock code.
4. `importers/brightstock_import.py:4` inserts into `legacy_sku`. It ran once on 12 March 2024 for 6,140 products.

**Timeline without the fix**

1. A migration runs `ALTER TABLE products DROP COLUMN legacy_sku`.
2. Postgres refuses, because `v_partner_feed` depends on the column.
3. Someone adds `CASCADE`. Postgres drops `v_partner_feed` along with the column.
4. The nightly `partner_feed_export` runs `SELECT ... FROM v_partner_feed` and errors. No file reaches Oakline Supply.
5. If someone recreates the view with `p.sku` only, the feed sends new SKUs. Oakline Supply does not recognise 6,140 products. The Brightstock codes are lost for good.

**Timeline with the fix**, diverges at step 1.

1. Migration A creates `partner_refs (product_id, partner, ref)`. It backfills one `brightstock` row per product where `legacy_sku IS NOT NULL`.
2. Migration A recreates `v_partner_feed` with `COALESCE(r.ref, p.sku) AS partner_ref`. It uses a `LEFT JOIN` on `partner_refs` filtered to `brightstock`.
3. The next nightly `partner_feed_export` runs unchanged. Its CSV matches the previous night's. A diff of the two files confirms it.
4. Migration B runs `DROP COLUMN legacy_sku`. No view depends on it, so no `CASCADE` is needed.
5. Oakline Supply receives the same `partner_ref` values as before.

**What changes**

- `db/schema.sql`: delete `legacy_sku text,`. Add `CREATE TABLE partner_refs`.
- `db/views.sql`: change line 4 from `COALESCE(p.legacy_sku, p.sku)` to `COALESCE(r.ref, p.sku)`. Add the `LEFT JOIN`.
- `importers/brightstock_import.py`: the insert at line 4 stops writing `legacy_sku`. It writes to `partner_refs` instead. The importer is one-shot, so deleting the file is also an option.
- `docs/history/2024-brightstock-migration.md`: line 4 now points to `partner_refs`.

**Recommendation.** Aelita recommends the two-step move. The partner still needs the codes, and `legacy_sku` is the only place that stores them. The cost is one new table and two migrations. The risk is a backfill that misses rows, which would silently change `partner_ref` for those products. The diff in step 3 catches that before step 4 runs.

**Alternative: keep the column.** Leave `legacy_sku` in place and document it as the Oakline Supply key. It needs no migration and carries no risk. It becomes the primary if Oakline Supply is expected to move to the new SKUs soon.
