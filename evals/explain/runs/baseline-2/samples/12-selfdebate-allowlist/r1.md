The `denylist` in `runner/spawn.py` copies the whole runner environment into every plugin, so any secret it doesn't name leaks. Aelita recommends an allowlist instead of your two-name addition. Your edit would still leak `BILLING_WEBHOOK_SECRET`.

**Existing behaviour**

1. `plugin_env` in `runner/spawn.py:10` starts from `dict(os.environ)`.
2. It removes only the three names in `DENYLIST`: `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`, `GITHUB_TOKEN`.
3. Every other variable in `deploy/runner.env` reaches the plugin.

**Timeline without the fix**

1. On 2 October, the team adds `STRIPE_API_KEY` to `deploy/runner.env` for the billing worker. No one adds it to `DENYLIST`.
2. A customer enables `debug` on a `feed-fetch` request.
3. `plugins/feed-fetch/main.py:14` prints `dict(os.environ)` as JSON to stderr.
4. `plugin_env` has passed the full environment, so the dump holds `STRIPE_API_KEY`, `SENTRY_DSN` and `BILLING_WEBHOOK_SECRET`.
5. On 24 October, the customer pastes the stderr output into a public support ticket.
6. The secrets are public. The next secret added to `deploy/runner.env` leaks the same way.

**Timeline with the fix**, diverges at step 4.

4. `plugin_env` passes only `PATH`, `HOME`, `LANG`, `HTTPS_PROXY` and `TINKERBOX_*` variables. The debug dump holds none of the three secrets.
5. The customer pastes the output. It holds nothing sensitive.
6. A secret added later stays out of plugins until someone allows it on purpose.

**What changes**

- `runner/spawn.py` old behaviour: `DENYLIST` holds three names and `plugin_env` pops them from a copy of `os.environ`. New behaviour: delete `DENYLIST`. Add `ALLOWED = {"PATH", "HOME", "LANG", "HTTPS_PROXY"}`. `plugin_env` keeps a variable only when its name is in `ALLOWED` or starts with `TINKERBOX_`.
- `docs/plugin-contract.md` add one line: a plugin sees only `TINKERBOX_*` and the names in `ALLOWED`.

**Recommendation.** Aelita recommends the allowlist, because it removes the root cause: a new secret is exposed by default. I checked the plugins. `csv-clean` reads `TINKERBOX_CSV_DELIMITER`, `pdf-stamp` reads `HOME`, and `feed-fetch` reads `HTTPS_PROXY`. The list covers all of these. The cost is that a future plugin needing another variable fails until someone adds it. Your two-name edit leaves `BILLING_WEBHOOK_SECRET` exposed, so it does not close the incident.

**Alternative: pattern denylist.** Block names ending in `_KEY`, `_SECRET`, `_TOKEN` or `_DSN`. It is a smaller change and breaks no plugin. It fails on any secret with an unusual name. It becomes the primary only if plugins need many arbitrary variables.

**Rotation.** The incident notes only `STRIPE_API_KEY` was rotated. `SENTRY_DSN` and `BILLING_WEBHOOK_SECRET` appeared in the same output, so rotate them too.
