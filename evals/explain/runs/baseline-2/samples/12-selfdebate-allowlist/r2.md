`plugin_env` copies the whole runner environment and removes only three named keys, so every new secret reaches every plugin. Aelita recommends an allowlist in `runner/spawn.py` instead of your two-name denylist addition, because that addition still leaves `BILLING_WEBHOOK_SECRET` exposed.

**Existing behaviour**

1. `plugin_env` in `runner/spawn.py` copies `os.environ`.
2. It pops `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL` and `GITHUB_TOKEN`, the three names in `DENYLIST`.
3. It adds `TINKERBOX_PLUGIN_DIR` and passes the result to the plugin through `run_plugin`.

**Timeline without the fix**

1. On 2 October, ops adds `STRIPE_API_KEY` to `deploy/runner.env` for the billing worker. Nobody touches `DENYLIST`.
2. A customer sends a `feed-fetch` request with `debug` set.
3. `run_plugin` starts `plugins/feed-fetch/main.py` with the full runner environment minus three keys.
4. `feed-fetch` runs `print(json.dumps({"env": dict(os.environ)}), file=sys.stderr)` at line 14. This dumps `STRIPE_API_KEY` and `SENTRY_DSN`.
5. The customer pastes the stderr into a public support ticket on 24 October.
6. Security rotates the key. `BILLING_WEBHOOK_SECRET` is still in the environment and would leak the same way.

**Timeline with the fix**, diverges at step 3.

3. `plugin_env` builds the environment from an allowlist: `PATH`, `HOME`, `LANG`, `HTTPS_PROXY` and every `TINKERBOX_*` variable. `run_plugin` starts `feed-fetch` with only those.
4. The debug dump prints only those variables. It holds no secret.
5. The ticket shows nothing sensitive.
6. A future secret added to `deploy/runner.env` stays out of plugins with no code change.

**What changes**

- `runner/spawn.py` old behaviour: `DENYLIST` plus `env = dict(os.environ)`. New behaviour: delete `DENYLIST`. Add `ALLOWLIST = {"PATH", "HOME", "LANG", "HTTPS_PROXY"}`. `plugin_env` keeps a variable only when its name is in `ALLOWLIST` or starts with `TINKERBOX_`.
- `docs/plugin-contract.md` add one sentence: a plugin receives only `TINKERBOX_*` and the four base variables.

**Recommendation.** Aelita recommends the allowlist. It removes the root cause, which is that a new secret is exposed by default. The list matches what plugins use today. `pdf-stamp` reads `HOME`, `feed-fetch` reads `HTTPS_PROXY` and `csv-clean` reads `TINKERBOX_CSV_DELIMITER`. `PATH` and `LANG` are base variables. A plugin that needs another variable will fail until someone adds it to `ALLOWLIST`. That failure is deliberate, and I found no such plugin in the repo.

**Alternative: extend the denylist.** Add `STRIPE_API_KEY`, `SENTRY_DSN` and `BILLING_WEBHOOK_SECRET`. It is a three-name edit with no behaviour risk for plugins. Your two names alone leave `BILLING_WEBHOOK_SECRET` exposed. This would be the primary only if third-party plugins depend on unknown inherited variables that you cannot enumerate.

**Not changed.** The `debug` dump in `plugins/feed-fetch/main.py:14` stays. After the allowlist it exposes no secret, but you can remove it separately.
