The leak happens because `plugin_env` copies the whole runner environment and removes only three names. Aelita recommends an allowlist instead of your two-name denylist addition. Your addition would still leak `BILLING_WEBHOOK_SECRET`.

**Existing behaviour**

1. `plugin_env` in `runner/spawn.py:11` starts with `dict(os.environ)`, so every runner variable is copied.
2. It removes only the names in `DENYLIST` (line 7): `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL` and `GITHUB_TOKEN`.
3. `run_plugin` passes that environment to the plugin subprocess.

**Timeline without the fix**

1. On 2 October the team adds `STRIPE_API_KEY` to `deploy/runner.env`. Nobody adds it to `DENYLIST`.
2. `run_plugin` starts `feed-fetch` with `STRIPE_API_KEY` and `SENTRY_DSN` still in its environment.
3. A customer sends a `feed-fetch` request with `debug` set.
4. `plugins/feed-fetch/main.py:14` prints `json.dumps({"env": dict(os.environ)})` to stderr.
5. The customer pastes that stderr into a public support ticket.
6. The ticket shows `STRIPE_API_KEY` and `SENTRY_DSN` in plain text. Security rotated the key on 24 October.

**Timeline with the fix**, diverges at step 2.

2. `run_plugin` starts `feed-fetch` with only `PATH`, `HOME`, `LANG`, `HTTPS_PROXY` and `TINKERBOX_*` variables.
3. The customer sends the same `debug` request.
4. `feed-fetch` dumps its environment. The dump holds only those allowed variables.
5. The ticket shows no secret.
6. A secret added to `deploy/runner.env` later stays out of plugins until someone allows it.

**What changes**

- `runner/spawn.py` old behaviour: `plugin_env` copies `os.environ` and pops `DENYLIST` names. New behaviour: it copies only names in a new `ALLOWLIST = {"PATH", "HOME", "LANG", "HTTPS_PROXY"}` and any name that starts with `TINKERBOX_`. `DENYLIST` is deleted.
- `docs/plugin-contract.md` add one sentence: plugins receive only `PATH`, `HOME`, `LANG`, `HTTPS_PROXY` and `TINKERBOX_*`.

**Recommendation.** Aelita recommends the allowlist. The root cause is that a new secret leaks by default, and a denylist can never keep up with that. I checked that the allowlist covers every variable the plugins read:

- `csv-clean` reads `TINKERBOX_CSV_DELIMITER`.
- `pdf-stamp` reads `HOME`.
- `feed-fetch` reads `HTTPS_PROXY`.

The cost is that a future plugin needing another variable must have it added to the allowlist. The runner env is trusted and the plugin dirs are listed, so I found no other readers.

**Alternative: extend the denylist as you planned.** Add `STRIPE_API_KEY` and `SENTRY_DSN`. It is a two-name edit with no behaviour risk. It still leaks `BILLING_WEBHOOK_SECRET`, which sits in `deploy/runner.env:10`, and the next secret too. It becomes the primary only if plugins need an unknown set of inherited variables that you cannot list.

**Alternative: remove the env dump from `feed-fetch`.** Delete line 14 of `plugins/feed-fetch/main.py`. This removes the disclosure channel but leaves the secrets in every plugin's environment. Do it in addition to the allowlist, not instead of it.
