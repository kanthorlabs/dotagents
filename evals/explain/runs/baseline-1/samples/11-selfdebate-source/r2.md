Both fixes treat a symptom. `ops-box-2` still runs `digest_builder` from its crontab, and so does the Kubernetes CronJob, so the build runs twice every Monday. Aelita recommends deleting the crontab line. The unique index is a good second layer, but it needs a change to the insert.

**Timeline without the fix**

1. **21 Sept:** Henrik Saar's cutover creates CronJob `digest-builder`. The crontab line on `ops-box-2` stays, because that checklist item is still open.
2. **Monday 06:00:** `ops-box-2` fires at 06:00:02 and the pod `digest-builder-29353080-k7x2q` fires at 06:00:04. `concurrencyPolicy: Forbid` only guards runs inside Kubernetes, so it does not stop the cron run.
3. `jobs/digest_builder.py` inserts one `pending` row per active subscriber in each run. `outbox` has no unique constraint, so both runs succeed.
4. The log of 26 Oct shows `enqueued=18412` from each run. `outbox` now holds 36824 rows for 18412 subscribers.
5. `send_pending` in `mailer/digest_mailer.py` sends every `pending` row.
6. Every subscriber receives the digest twice.

**Timeline with the fix**, diverges at step 2.

2. Only the pod fires at 06:00. The crontab of `ops-box-2` has no digest line.
3. The builder inserts 18412 rows.
4. The log shows one `enqueued=18412` line. `outbox` holds 18412 rows.
5. `send_pending` sends 18412 emails.
6. Every subscriber receives one digest.

**What changes**

- `ops/hosts/ops-box-2/crontab`: delete line 3, the `digest_builder` entry. The same line must be removed on the live host. I could only read the repo copy.
- `docs/migrations/2026-09-k8s-cutover.md`: tick line 8, "Remove the `digest_builder` line from the crontab of `ops-box-2`".

**Recommendation.** Aelita recommends deleting the crontab line, because it removes the cause. It costs one edit on the live host. Nothing else can break, because the CronJob already works. The same cause hits `rotate-logs`, which also runs in both places. It is harmless today, but it deserves the same cleanup.

**Why not dedupe by email in `digest-mailer`.** It guards the wrong place. If the mailer runs between the two builds, it sends the first row, then sends the second row later. Two subscribers who share an email would also lose one digest. The duplicate rows would stay in `outbox`.

**Alternative: unique index on `outbox(subscriber_id, digest_date)`.** It stays correct if any future scheduler double-fires. It has two costs. The existing duplicates since 28 Sept must be deleted first, or `CREATE UNIQUE INDEX` fails. The insert in `jobs/digest_builder.py` line 8 also needs `ON CONFLICT DO NOTHING`. Without that, the second run raises an error and the job fails noisily. It becomes the primary if you cannot reach the live `ops-box-2` crontab.
