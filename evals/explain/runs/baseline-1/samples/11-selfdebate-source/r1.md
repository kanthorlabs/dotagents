**What changes**

- `ops/hosts/ops-box-2/crontab` and the live crontab on `ops-box-2`: delete line 3, the `jobs.digest_builder` entry. The repo copy is only a record, so someone must edit the real host.
- `docs/migrations/2026-09-k8s-cutover.md`: tick the item for the `digest_builder` line.
- `db/schema.sql`: add `CREATE UNIQUE INDEX outbox_subscriber_digest_uq ON outbox (subscriber_id, digest_date)`.
- `jobs/digest_builder.py:8`: the INSERT gets `ON CONFLICT (subscriber_id, digest_date) DO NOTHING`. Without it, a second run would crash on the first conflict instead of skipping it.

**Recommendation.** Aelita recommends removing the crontab line. It removes the root cause, which is two schedulers for one job. It costs one edit on `ops-box-2`. Nothing else breaks. The `rotate-logs` line has the same leftover problem, and the cutover checklist already lists it. Add the unique index afterwards as a guard. Of your two options, the index beats deduping in `digest-mailer`. It makes duplicates impossible at the data layer. Mailer dedupe by email would also need a lookup of already-sent rows, because the second run can insert after the first rows are marked `sent`. The index cannot be created until duplicate rows are deleted. That includes rows from every Monday since late September.

**Alternative: unique index only.** The index with `ON CONFLICT DO NOTHING` stops the duplicates even if both schedulers stay. It beats the crontab edit when you cannot reach `ops-box-2` today. It leaves two jobs running and wastes one run each Monday. It becomes the primary when the schedulers cannot be reduced to one.
