The `cache: pnpm` option of `actions/setup-node` cuts the median `Install` step of workflow `ci` from 3 min 40 s to about 35 s. That saves about 3 min 05 s per run and about 21 runner hours per week. Aelita recommends it. It is a one-line change.

**Timeline without the change**

1. A developer pushes a branch. `ci` starts on `ubuntu-24.04`.
2. `actions/checkout@v4`, `pnpm/action-setup@v4` and `actions/setup-node@v4` run. Nothing is restored.
3. `pnpm install --frozen-lockfile` downloads every package into an empty store. The median is 3 min 40 s.
4. `pnpm lint` and `pnpm test` run.
5. The run ends at a median of 11 min 05 s. The developer waits, and does this about 7 times per pull request. That is 412 runs for about 60 pull requests per week.

**Timeline with the change**, diverges at step 3.

3. `setup-node` restores the pnpm store from the cache keyed on the hash of `pnpm-lock.yaml`. `pnpm install` links from the warm store. The measured median is 35 s.
4. `pnpm lint` and `pnpm test` run unchanged.
5. The run ends at about 8 min. On a cache miss, the post step of `setup-node` saves the store for the next run.

**What changes**

- `.github/workflows/ci.yml` old behaviour: the `actions/setup-node@v4` step has only `node-version: 22`. New behaviour: add `cache: pnpm` under `with`. The `pnpm/action-setup@v4` step already runs first, which `cache: pnpm` requires.

**What it buys**

- **Time per run:** 3 min 40 s minus 35 s is 3 min 05 s, so the median run falls from 11 min 05 s to about 8 min.
- **Time per week:** 412 runs times 185 s is about 1,270 minutes, or 21 hours.
- **Money per week:** 1,270 minutes at 0.008 USD is about 10 USD. The money is small. The gain is developer wait time.
- **Caveat:** the 35 s figure comes from 20 manual runs with a warm store. It may not include the cache download of the 1.1 GB store. Treat 8 min as the upper bound until the first real runs report.

**Recommendation.** Aelita recommends `cache: pnpm`, because it removes the cause, which is the empty store on every run. It adds no new step and no key logic. Three things can break it:

- **Lockfile change:** a changed `pnpm-lock.yaml` gives a new key and no fallback, so that run installs cold once.
- **Cache limit:** the repository limit is 10 GB and the store is 1.1 GB. Many branches that change the lockfile can evict the `main` entry.
- **Unchecked lockfile path:** this checkout holds no `pnpm-lock.yaml` or `package.json`. I assume the real repository has the lockfile at the root, since `--frozen-lockfile` needs it.

**Alternative: explicit `actions/cache` on the store path.** It gives you control of `restore-keys`, so a lockfile change still restores a near match. It costs an extra step and a `pnpm store path` lookup. It becomes the primary if lockfile changes are frequent enough that cold installs show up in the metrics.
