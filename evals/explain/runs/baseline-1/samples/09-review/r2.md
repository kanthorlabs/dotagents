`quillpay/webhooks.py` in PR 311 is not safe to merge. `handle` changes the ledger before it checks the signature, so anyone who can reach the endpoint can credit an account. Aelita recommends fixing B1 first, because B2 to B4 only matter once B1 is closed.

## Timeline without the fix

1. An attacker posts `{"type":"charge.succeeded","data":{"account_id":"A","amount_cents":99999}}` to the webhook. They send no `Quill-Signature` header.
2. `handle` runs `json.loads(payload)` at line 19 and logs the body at line 20.
3. `handle` matches `charge.succeeded` at line 22 and calls `ledger.credit`.
4. `ledger.credit` writes 99999 cents to account A.
5. `handle` calls `verify` at line 27. The header is empty, so `header.split(",")` gives `[""]` and `"".split("=", 1)` has one element. `dict` raises `ValueError`.
6. The request returns a 500, or a 400 if the header was merely wrong. The credit is already written. The attacker has created money.

## Findings

**Blockers**

- **B1** - status:OPEN - action:YES - Ledger written before signature check - `handle` calls `ledger.credit` and `ledger.debit` at lines 22-25, and `verify` only runs at line 27. A rejected request still moves money. - fix: call `verify` first and return 400 before parsing the JSON or touching `ledger`. - why: the signature is the only authentication on this endpoint.
- **B2** - status:OPEN - action:YES - Default secret `dev-secret` - `settings.py` line 52 uses `os.environ.get("QUILL_WEBHOOK_SECRET", "dev-secret")`. A missing variable in production silently leaves a public secret in place. - fix: use `os.environ["QUILL_WEBHOOK_SECRET"]`, as `DATABASE_URL` does on the line above. - why: the service should fail at start-up, not accept forged events.
- **B3** - status:OPEN - action:YES - Non-constant-time compare - `verify` line 42 uses `expected == parts.get("v1")`. - fix: use `hmac.compare_digest(expected, parts.get("v1", ""))`. - why: `==` leaks how many leading characters matched.
- **B4** - status:OPEN - action:YES - No replay or duplicate protection - a signed event replayed inside the 300-second window credits twice. A provider retry does the same. - fix: store `event["id"]` with a unique constraint and skip events already seen. - why: `ledger.credit` is not idempotent.

**Suggestions**

- **S1** - status:OPEN - action:YES - Raw payload logged - line 20 logs the whole body at info level before verification. - fix: log only `event["id"]` and `event["type"]`, and only after `verify` passes. - why: the body holds account data, and unverified input can fill the logs.
- **S2** - status:OPEN - action:YES - Malformed input gives a 500 - a bad header, a non-numeric `t`, invalid JSON or a missing key such as `account_id` raises. - fix: catch `ValueError` and `KeyError`, then return 400. - why: the provider retries 5xx responses, so bad input becomes a retry storm.
- **S3** - status:OPEN - action:YES - Unknown event types return 200 silently - `handle` has no `else` branch. - fix: add `log.warning` for unhandled types. - why: a new event type would otherwise vanish without a trace.
- **S4** - status:OPEN - action:YES - Dead code and no tests - `_unused_helper` at line 45 does nothing, and the diff adds no test file. - fix: delete the helper and add tests for a bad signature, a stale timestamp and a replay. - why: B1 is exactly the regression a test would catch.

## What changes for B1

- `quillpay/webhooks.py` old behaviour: `handle` parses, logs and updates the ledger, then calls `verify`. New behaviour: `handle` calls `verify(header, payload)` first and returns 400 on failure. Only then does it parse and update the ledger.

## Recommendation and alternatives

**Recommendation.** Aelita recommends moving `verify` to the top of `handle`. It costs one reordering and removes the root cause. The only thing that can break is a client that sent invalid signatures and relied on the 400 arriving after the work was done.

**Alternative: wrap the ledger calls and the check in one transaction.** `handle` rolls back when `verify` fails. It beats the recommendation if `ledger` already has transaction support. It still parses and logs unauthenticated input. It becomes the primary only if the signature check must read ledger state.
