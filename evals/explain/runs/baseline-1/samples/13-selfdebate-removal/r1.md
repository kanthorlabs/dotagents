`legacy_sku` is not dead, so Aelita recommends against a plain drop. `v_partner_feed` in `db/views.sql` reads it, and the nightly `partner_feed_export` sends that view to Oakline Supply. Your grep of `src/` missed it because the users sit in `db/`, `importers/` and `jobs/`.

**Existing behaviour**

1. `products.legacy_sku` holds the Brightstock item code for the 6,140 products imported on 12 March 2024. Newer products have `NULL`.
2. `v_partner_feed` computes `COALESCE(p.legacy_sku, p.sku) AS partner_ref`.
3. `partner_feed_export` selects `partner_ref` from the view and uploads `/tmp/oakline-feed.csv` to `sftp.oaklinesupply.com`.
4. Oakline Supply still keys its catalog on the Brightstock code, per `docs/history/2024-brightstock-migration.md`.

**Timeline without the fix**

1. A migration runs `ALTER TABLE products DROP COLUMN legacy_sku`.
2. Postgres refuses, because `v_partner_feed` depends on the column.
3. Someone adds `CASCADE`. Postgres drops `v_partner_feed` with the column.
4. The nightly `partner_feed_export` queries a view that no longer exists. The job errors and uploads nothing.
5. The view is rebuilt on `sku` alone. Oakline Supply receives new SKUs it does not recognise for 6,140 products.

**Timeline with the fix**, diverges at step 1.

1. A migration creates `partner_refs` and backfills it from every row where `legacy_sku IS NOT NULL`.
2. The same migration recreates `v_partner_feed` with `COALESCE(r.ref, p.sku) AS partner_ref` over a left join to `partner_refs`.
3. `DROP COLUMN legacy_sku` succeeds, because nothing depends on it.
4. The nightly `partner_feed_export` reads the same `partner_ref` values as before.
5. Oakline Supply receives an identical feed. You can confirm it by diffing the CSV from before and after the migration.

**What changes**

- `db/schema.sql`: delete `legacy_sku text,`. Add `CREATE TABLE partner_refs (product_id bigint PRIMARY KEY REFERENCES products(id), ref text NOT NULL)`.
- `db/views.sql`: replace `COALESCE(p.legacy_sku, p.sku)` with `COALESCE(r.ref, p.sku)`. Add `LEFT JOIN partner_refs r ON r.product_id = p.id`.
- `importers/brightstock_import.py`: the INSERT drops `legacy_sku`. A second insert writes `brightstock_code` into `partner_refs`. The import ran once, but a rerun would fail without this edit.
- `docs/history/2024-brightstock-migration.md`: replace `The column legacy_sku keeps the Brightstock item code` with a pointer to `partner_refs`.
- `jobs/partner_feed_export.py`: no change.

**Recommendation.** Aelita recommends moving the codes into `partner_refs` and then dropping the column. It removes the column you asked about and keeps the Oakline feed byte-identical. It costs one table and a 6,140-row backfill. It breaks if a product has a `legacy_sku` that the backfill skips, so the migration should assert that the `partner_refs` row count equals the count of non-null `legacy_sku`.

**Alternative: keep the column and mark it.** Add a `COMMENT ON COLUMN products.legacy_sku` that names Oakline Supply as its user. It costs nothing and risks nothing. It becomes the primary if Oakline Supply is expected to rekey to the new `sku` soon, because then `partner_refs` would be built only to be deleted.
