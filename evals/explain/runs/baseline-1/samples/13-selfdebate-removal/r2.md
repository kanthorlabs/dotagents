Aelita advises against dropping `legacy_sku` now. `v_partner_feed` reads it, and `partner_feed_export` sends that view to Oakline Supply. Your grep of `src/` missed this because the readers live in `db/`, `jobs/` and `importers/`.

**Existing behaviour**

1. `db/schema.sql:4` defines `products.legacy_sku`, a nullable text column.
2. `importers/brightstock_import.py:4` writes the Brightstock item code into it.
3. `db/views.sql:4` defines `partner_ref` as `COALESCE(p.legacy_sku, p.sku)`.
4. `jobs/partner_feed_export.py:7` selects `partner_ref` from `v_partner_feed`. It uploads the result to `sftp.oaklinesupply.com`.

**Timeline without the fix**

1. A developer runs `ALTER TABLE products DROP COLUMN legacy_sku`.
2. Postgres rejects the drop because `v_partner_feed` depends on the column.
3. Someone retries with `DROP COLUMN legacy_sku CASCADE`. Postgres silently drops `v_partner_feed`.
4. `partner_feed_export` runs and fails on `SELECT ... FROM v_partner_feed`. The feed to Oakline Supply stops.
5. Someone recreates the view with `p.sku AS partner_ref`. Old products now export their new `sku` instead of the Brightstock code. Oakline Supply sees unknown refs. The old codes are gone for good.

**Timeline with the fix**, diverges at step 1.

1. A developer asks Oakline Supply whether `partner_ref` must keep the Brightstock codes.
2. If the answer is no, one migration redefines `v_partner_feed` with `p.sku AS partner_ref`. It then drops `legacy_sku`. No `CASCADE` is used.
3. `importers/brightstock_import.py` stops inserting `legacy_sku`. Otherwise it fails on the missing column.
4. `partner_feed_export` runs. It sends the new `sku` values, and Oakline Supply expects them.

**What changes**

- `db/views.sql`: old `COALESCE(p.legacy_sku, p.sku) AS partner_ref`. New `p.sku AS partner_ref`.
- `db/schema.sql`: delete line 4, `legacy_sku text,`.
- `importers/brightstock_import.py`: the INSERT drops `legacy_sku` and `item["brightstock_code"]`.
- `docs/history/2024-brightstock-migration.md`: lines 4-5 describe a column that no longer exists. Add a note that the column was removed.

**Recommendation.** Aelita recommends keeping the column until Oakline Supply confirms it no longer needs the Brightstock codes. The drop is irreversible and changes the feed contract for every old product. Waiting costs one nullable column. If Oakline Supply still depends on the codes, the drop breaks their ingest.

**Alternative: drop now and keep the codes in the view.** Create `partner_ref_map(sku, partner_ref)` from the current `legacy_sku` values. Join it in the view. This removes the column with no feed change. It adds a table to maintain. It becomes the primary if you must clean up `products` now and Oakline Supply cannot change.

**Question.** Do you want to keep `legacy_sku` until Oakline Supply confirms, or drop it now with the `partner_ref_map` table?
