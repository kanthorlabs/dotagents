`list_orders` sorts by `created_at` alone, and `import_tidewater_batch` gives every row in a batch the same `created_at`. Page boundaries then fall inside groups of tied rows, and PostgreSQL may order those rows differently on each query. Aelita recommends adding `id DESC` as a tie-breaker to the `ORDER BY`.

**Existing behaviour**

1. `import_tidewater_batch` sets one `batch_time` and inserts about 200 rows with that same `created_at`.
2. `list_orders` runs `ORDER BY created_at DESC LIMIT 50 OFFSET (page-1)*50`.
3. PostgreSQL does not define the order of rows that tie on `created_at`. Each query can return them in a different order.

**Timeline without the fix**

1. Brennan Hardware imports a Tidewater batch of about 200 orders. All share one `created_at`.
2. The client requests page 3. The page boundary at row 150 or 200 falls inside the tied group.
3. PostgreSQL returns the tied rows in one order and sends the first 50 after the offset. Order 9001 is among them.
4. The client requests page 4. The tied rows come back in a different order for this query.
5. Order 9001 is now at a position the client has already passed, so it appears on page 4 as well. Order 9002 moved the other way and appeared on neither page.
6. The export holds 1,214 rows. 9 ids appear twice and 9 ids are missing. The row count stays correct because each duplicate replaces one missing row.

The ticket says no orders were created during the export. That rules out new rows shifting the offsets. The tie ordering is the remaining cause. No file shows the actual plan, so the exact row order PostgreSQL chose is inferred. The mechanism itself is documented PostgreSQL behaviour.

**Timeline with the fix**, diverges at step 3.

3. PostgreSQL sorts by `created_at DESC, id DESC`. Every row has one fixed position, because `id` is the primary key.
4. The client requests page 4. The order is identical to the order on page 3.
5. Each order appears on exactly one page.
6. The export holds 1,214 rows with no duplicates and no gaps.

**What changes**

- `src/orders/list_orders.py` old behaviour: `ORDER BY created_at DESC`. New behaviour: `ORDER BY created_at DESC, id DESC`.
- `docs/api.md` add one sentence: "Orders are sorted by creation time, newest first, with ties broken by `id` descending."

**Recommendation.** Aelita recommends the tie-breaker because it removes the cause, an ordering that is not total. It is a one-line change with no API change. It can cost a sort step on ties. An index on `(tenant_id, created_at DESC, id DESC)` would avoid that, if the query is slow. This fix does not protect an export from orders inserted mid-export, because offsets still shift.

**Alternative: keyset pagination.** The client passes the last `(created_at, id)` pair instead of a page number. It stays correct when orders are inserted during an export. It changes the API contract and every client. It becomes the primary if exports must stay correct while orders are created.
