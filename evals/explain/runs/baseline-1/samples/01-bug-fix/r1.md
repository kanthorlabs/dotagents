`list_orders` sorts only by `created_at`, and `import_tidewater_batch` gives every order in a batch the same `created_at`. Page boundaries then fall inside groups of tied rows, and PostgreSQL may order those rows differently on each page request. Aelita recommends adding `id DESC` as a tiebreaker in `list_orders`.

**Timeline without the fix**

1. `import_tidewater_batch` sets one `batch_time` and inserts about 200 Brennan Hardware orders with that identical `created_at`.
2. Brennan Hardware calls `GET /orders?page=1`. `list_orders` runs `ORDER BY created_at DESC LIMIT 50 OFFSET 0`.
3. PostgreSQL sorts the tied rows in an order that SQL does not define. It returns 50 of the 200 tied rows.
4. Brennan Hardware calls page 2 with `OFFSET 50`. This is a new query, and PostgreSQL may order the same tied rows differently. The plan can change with the `LIMIT` and `OFFSET` values.
5. Some rows that were on page 1 are now at positions 51 to 100, so they appear twice. Some rows never fall inside any page window, so they are missing.
6. The export holds 1,214 rows but only 1,205 distinct ids. This matches ticket HO-212: 9 duplicates and 9 missing.

**Timeline with the fix**, diverges at step 3.

3. PostgreSQL sorts by `created_at DESC, id DESC`. Because `id` is the unique primary key, the order is total.
4. Page 2 uses the same total order. Its `OFFSET 50` starts exactly where page 1 ended.
5. Every order appears in exactly one page.
6. The export holds 1,214 rows and 1,214 distinct ids.

**What changes**

- `src/orders/list_orders.py` old behaviour: `ORDER BY created_at DESC`. New behaviour: `ORDER BY created_at DESC, id DESC`.
- `docs/api.md` add one sentence under `GET /orders?page=N`: "Orders with equal `created_at` are ordered by `id`, newest first."

**Recommendation.** Aelita recommends the tiebreaker. It removes the root cause, which is a non-total sort order. It is a one-line change with no API change. It can still skip or repeat rows if orders are created or deleted during an export. HO-212 reports no creations, so that is not the cause here. An index on `(tenant_id, created_at DESC, id DESC)` would keep deep pages fast, but it is optional.

**Alternative: keyset pagination.** The API would take `?after=<created_at,id>` instead of `page=N`. It stays correct while orders are being created, and it stays fast on deep pages. It breaks the documented `page` contract for clients. It becomes the primary if exports must run during live order creation.
