`list_orders` sorts only by `created_at`, and `import_tidewater_batch` gives every row in a batch the same `created_at`. That leaves the order inside a batch undefined, so page boundaries can duplicate or drop rows. Aelita recommends adding `id DESC` as a tiebreaker. It costs one sort column.

**Timeline without the fix**

1. `import_tidewater_batch` sets one `batch_time` and inserts about 200 rows with that same `created_at` (`src/orders/bulk_import.py:5-10`).
2. Brennan Hardware exports on 21 October by requesting `GET /orders?page=N` until a page holds fewer than 50 rows.
3. `list_orders` runs page 3 with `ORDER BY created_at DESC LIMIT 50 OFFSET 100`. Rows with equal `created_at` can come back in any order.
4. `list_orders` runs page 4 as a separate query with `OFFSET 150`. PostgreSQL can order the same tied rows differently this time, because the sort size differs.
5. A tied row that page 3 left out of its slice can land on page 4 and also in page 3's slice. Another tied row falls in neither slice.
6. The export holds 1,214 rows, with 9 ids twice and 9 ids missing. The row count matches because each duplicate replaces a missing row.

**Timeline with the fix**, diverges at step 3.

3. `list_orders` runs page 3 with `ORDER BY created_at DESC, id DESC`. Every row has a unique position.
4. Page 4 uses the same total order. Its slice starts exactly where page 3 ended.
5. No row appears twice and none is skipped.
6. The export holds 1,214 unique rows.

**Unverified step.** Step 4 is inferred from the code. The exact PostgreSQL reordering is not checked, because there is no database here. The ticket's numbers fit it: duplicates equal missing rows, and the affected rows come from the Tidewater batches. Running the page 3 and page 4 queries with `EXPLAIN` on a copy of the Brennan Hardware data would confirm it.

**What changes**

- `src/orders/list_orders.py` old behaviour: `ORDER BY created_at DESC`. New behaviour: `ORDER BY created_at DESC, id DESC`. `id` is the primary key, per `docs/api.md`, so it is unique.

**Recommendation.** Aelita recommends the `id DESC` tiebreaker. It removes the ambiguity at its source, and `docs/api.md` still holds: 50 per page, newest first, same `page` parameter. It costs a wider sort key. An index on `(tenant_id, created_at DESC, id DESC)` avoids that cost, if one is needed. Nothing else breaks.

**Alternative: keyset pagination.** Clients pass the last `(created_at, id)` instead of `page`. It stays correct when orders are created mid-export, and it avoids deep OFFSET scans. It changes the API contract and every client. It becomes the primary if exports must stay correct while orders are being created.

**Alternative: unique timestamps in the import.** `import_tidewater_batch` would stamp each row separately. It does not fix existing rows, and two rows can still collide. It is not a substitute for the tiebreaker.
