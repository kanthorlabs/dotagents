`mintctl deploy staging` builds the current commit as a Docker image, pushes it, rolls it out to the staging cluster, and posts to Slack. Every step runs in order, and any failing command stops the run.

**Timeline**

1. **Read config.** `deploy("staging")` in `mintctl/deploy.py` opens `mint.toml` from the current directory. It takes `env.staging`: cluster `gke-mint-staging`, namespace `shop`, channel `#deploys-staging`.
2. **Read the commit.** Ines Albrecht's checkout of `mint-shop` supplies the short SHA from `git rev-parse --short HEAD`.
3. **Build the tag.** The tag is `registry.mint.internal/mint-shop:<sha>`. The host comes from `HOST` in `mintctl/registry.py`.
4. **Build.** `docker build -t <tag> .` runs in the current directory. This includes uncommitted changes, because the tag only records `HEAD`.
5. **Push.** `docker push <tag>` sends the image to `registry.mint.internal`.
6. **Set the image.** `kubectl --context gke-mint-staging -n shop set image deployment/mint-shop web=<tag>` updates the `web` container.
7. **Wait for rollout.** `kubectl rollout status deployment/mint-shop --timeout=300s` blocks for up to 300 seconds. A timeout raises an error and skips step 8.
8. **Notify.** `slack.post` in `mintctl/slack.py` sends "mint-shop <sha> is live on staging" to `#deploys-staging`. It uses the URL in `MINT_SLACK_WEBHOOK` and a 10-second timeout. A missing variable raises `KeyError` after the rollout has already succeeded.

**Observations**

- **No entry point.** No file in this directory parses `deploy staging` from the command line. I assumed something calls `deploy("staging")`.
- **No rollback.** If step 7 fails, the new image stays set on the deployment.
