`mintctl deploy staging` builds the current commit as a Docker image and pushes it to `registry.mint.internal`. It then points the `mint-shop` deployment on `gke-mint-staging` at that image, waits for the rollout, and posts to Slack.

**Timeline**

1. **Entry.** Ines Albrecht runs the command inside `mint-shop`. This directory has no CLI entry point, so I could not see how `deploy("staging")` gets called. I assume something outside these files does it.
2. **Config.** `deploy()` in `mintctl/deploy.py` opens `mint.toml` from the current directory. It reads `env.staging`: cluster `gke-mint-staging`, namespace `shop`, channel `#deploys-staging`.
3. **Tag.** `git rev-parse --short HEAD` gives the commit sha. The tag becomes `registry.mint.internal/mint-shop:<sha>`. The working tree is not checked, so uncommitted changes go into the image under the sha of the last commit.
4. **Build.** `docker build -t <tag> .` runs in the repository root.
5. **Push.** `docker push <tag>` uploads the image to `registry.mint.internal`.
6. **Release.** `kubectl --context gke-mint-staging -n shop set image deployment/mint-shop web=<tag>` updates the `web` container.
7. **Wait.** `kubectl rollout status deployment/mint-shop --timeout=300s` blocks until the rollout finishes or 300 seconds pass.
8. **Notify.** `slack.post` sends "mint-shop <sha> is live on staging" to `#deploys-staging`. It uses the webhook in `MINT_SLACK_WEBHOOK` with a 10-second timeout.

**Failure behaviour.** Steps 4 to 7 use `check=True`, so the first failing command raises and stops everything after it. A failed build sends no Slack message. A failed rollout leaves the new image set on the deployment, and no rollback runs. If `MINT_SLACK_WEBHOOK` is unset, step 8 raises `KeyError` after the deploy has already succeeded.
