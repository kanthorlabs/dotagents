`purge-worker` deletes in-progress uploads for `acme-labs` because `TenantConfig.validate` accepts `retention_days: 0`, which `docs/retention.md` does not support. Aelita recommends rejecting 0 in `validate`, as the docs already say.

**Existing behaviour**

1. `config/schema.py:10` rejects only values below 0, so 0 passes.
2. `purge/worker.py:5` sets `cutoff` to now minus `retention_days` days.
3. `purge/worker.py:7` deletes every upload with `created_at < cutoff`.
4. `purge/worker.py` never checks whether an upload is still in progress.

**Timeline without the fix**

1. `acme-labs` sets `retention_days: 0` in `tenants/acme-labs.yaml`.
2. `validate` accepts the value, because 0 is not below 0.
3. A user starts a multipart upload at 10:00. It can run for up to 6 hours.
4. `purge-worker` runs at 10:15 and computes `cutoff` as 10:15.
5. The upload has `created_at` 10:00, which is below `cutoff`, so `store.delete` removes it mid-transfer.
6. The user loses an upload that was still in progress.

**Timeline with the fix**, diverges at step 2.

2. `validate` raises `retention_days must be >= 1` for `acme-labs`.
3. The tenant config is rejected before `purge-worker` ever uses it.
4. The tenant sets a value from 1 to 3650, or deletes uploads through the API, as the docs describe.

**What changes**

- `config/schema.py` old behaviour: `validate` raises when `retention_days < 0`. New behaviour: it raises when `retention_days < 1` or `retention_days > 3650`, with the message `retention_days must be between 1 and 3650`.
- `tenants/acme-labs.yaml` old value: `retention_days: 0`. New value: `1`, or the tenant's chosen value.

**Recommendation.** Aelita recommends forbidding 0 in `validate`. The root cause is a schema that is looser than the documented range. This fix adds no mechanism. It costs one config edit for `acme-labs`. Two things can break it:
- Nothing calls `validate` today. A grep finds only its definition. The fix does nothing until the config loader calls it.
- Even at 1 day, `purge-worker` could delete an upload that has been in progress for more than 24 hours. The 6-hour limit makes that case impossible.

**Alternative: skip in-progress uploads in `purge-worker`.** The worker checks an upload status before `store.delete`. It would make a 0 value safe, and it protects any future bad config. It costs a status field. A grep finds no such field in this repository. It becomes the primary if tenants must be allowed zero retention.

**Question.** Should Aelita reject 0 in `validate` and wire `validate` into config loading, or add the in-progress check to `purge-worker`?
