The `reorder` job ran twice because neither region's lock protects a 4-minute job. Region does not change the cause or the fix, so the missing region does not block a decision. Aelita recommends a per-SKU idempotency key on each purchase order.

**Existing behaviour**

1. `run_reorder` in `planner/reorder.py:5` calls `locks.acquire` with `ttl_seconds=60`.
2. If the lock is taken, the job returns `skipped`. Otherwise it loops over `items_below_reorder_point()` and calls `create_purchase_order` for each item.
3. `acquire` in `planner/locks.py:9` sets a Redis key with `nx` and `ex=60`. Nothing releases or renews it.
4. `config/us-east.yaml` sets `lock_backend: none`, so `acquire` returns `True` every time at `planner/locks.py:7`.

**Branch A: the job ran in eu-west.** It uses `lock_backend: redis`.

1. Pod 1 starts at 01:00. It acquires `lock:reorder` with a 60-second TTL.
2. Pod 1 begins creating purchase orders. The job needs about 4 minutes.
3. The key expires at 01:01. Nothing renewed it.
4. The node restarts. Pod 2 starts at 01:02.
5. Pod 2 calls `acquire`. The key is gone, so it succeeds.
6. Both pods create a purchase order for HT-4410. Halvorsen Tools receives two identical orders.

**Branch B: the job ran in us-east.** It uses `lock_backend: none`.

1. Pod 1 starts at 01:00. `acquire` returns `True` without touching Redis.
2. Pod 1 begins creating purchase orders.
3. `autoscale_max_replicas: 3` allows extra pods, and the node restart adds one.
4. The node restart starts pod 2 at 01:02.
5. Pod 2 calls `acquire`. It gets `True` again, because the backend is `none`.
6. Both pods create a purchase order for HT-4410. Halvorsen Tools receives two identical orders.

**Timeline with the fix**, diverges at step 6 in both branches.

6. Each pod passes the key `reorder:2026-10-22:HT-4410` to `create_purchase_order`. The second call matches the first key and returns the existing order. Halvorsen Tools receives one order.

**What changes**

- `planner/reorder.py`: at line 8, `create_purchase_order(item.sku, item.reorder_quantity)` gains an `idempotency_key=f"reorder:{run_date}:{item.sku}"` argument. `run_date` is the date the job started.
- `stockpile.purchasing`: `create_purchase_order` accepts the key. It returns the existing order when the key already exists. This module is not in the current directory, so I have not read it. Whether it can enforce a unique key is unverified. Reading its code and its table schema settles that.

**Recommendation.** Aelita recommends the idempotency key. It removes the root cause, which is that a second run is not safe. It protects both regions and survives lock expiry, a crashed pod and a bad config. It costs one unique index on the purchase order table. It breaks if two legitimate orders for the same SKU must exist on one date.

**Alternative: repair the lock.**
- **What it is:** Set the TTL above the job length, or renew it while the job runs. Release the lock at the end. Change `us-east.yaml` to `lock_backend: redis`.
- **Where it wins:** It needs no change to `purchasing`.
- **Cost:** A pod that dies mid-job leaves the lock held until the TTL runs out, or the job gets skipped. A pod that dies after creating some orders can still repeat them on retry.
- **When it becomes the primary:** If `purchasing` cannot enforce a unique key.
