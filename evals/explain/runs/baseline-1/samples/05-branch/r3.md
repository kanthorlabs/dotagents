Two `restock-planner` pods both ran `reorder` because the lock failed in either region. The lock is a 60 second Redis key in `eu-west` and a no-op in `us-east`. Aelita recommends fixing both, because the ticket's missing region no longer matters.

**Existing behaviour**

1. `planner/reorder.py` calls `locks.acquire("reorder", ..., ttl_seconds=60)` once at the start of `run_reorder`.
2. `planner/locks.py` returns `True` at once when `lock_backend` is `none`. Otherwise it runs Redis `SET lock:reorder NX EX 60`.
3. `config/eu-west.yaml` sets `lock_backend: redis`. `config/us-east.yaml` sets `lock_backend: none` and allows 3 replicas.
4. Nothing releases the lock, and nothing checks for an existing order. The loop then creates one purchase order per item below its reorder point.

**Branch A: the duplicate ran in `eu-west`**

1. Pod A starts at 01:00. `acquire` sets `lock:reorder` with a 60 second TTL and returns `True`.
2. Pod A loops over items and creates purchase orders, including one for HT-4410.
3. At 01:01 the key expires. Pod A is still running, because the job takes about 4 minutes.
4. Pod B starts at 01:02 after the node restart. `SET NX` succeeds on the expired key.
5. Pod B reads the same item list. HT-4410 is still below its reorder point.
6. Halvorsen Tools receives two identical orders.

**Branch B: the duplicate ran in `us-east`**

1. Pod A starts at 01:00. `acquire` returns `True` without contacting Redis, because the backend is `none`.
2. Pod A loops over items and creates purchase orders, including one for HT-4410.
3. No lock exists at any point, so nothing can block a second pod.
4. Pod B starts at 01:02 and `acquire` returns `True` again.
5. Pod B reads the same item list. HT-4410 is still below its reorder point.
6. Halvorsen Tools receives two identical orders.

**Unverified:** step 5 assumes `db.items_below_reorder_point()` still lists HT-4410 after pod A orders it. No file in the repo settles this, and `purchasing` is not in the repo. Pod A's purchase order records or logs from that night would settle it. They would also show the region.

**Timeline with the fix**, diverges at step 1 in both branches.

1. Pod A acquires the lock with a TTL longer than the job. In `us-east` this is a real Redis lock.
4. Pod B calls `acquire` at 01:02. The key still exists, so `acquire` returns `False`.
5. Pod B returns `"skipped"`. Halvorsen Tools receives one order.

**What changes**

- `config/us-east.yaml`: old `lock_backend: none`. New `lock_backend: redis`.
- `planner/reorder.py`: old `ttl_seconds=60`. New `ttl_seconds=900`, about 3 times the 4 minute runtime.
- `planner/locks.py`: add a region to the key. Old `f"lock:{name}"`. New `f"lock:{region}:{name}"`, with `region` passed in from `region_config`.

**Recommendation.** Aelita recommends the config and TTL fix, because it works in both branches and needs no change outside this repo.
- **Cost:** a pod that crashes mid-job holds the lock for up to 15 minutes, so a retry in that window is skipped.
- **What can break:** both regions point at the host `redis-locks`. If that is one shared Redis, the region in the key stops one region's lock from blocking the other. I could not confirm whether it is shared.

**Alternative: idempotent purchase orders.** `create_purchase_order` would take a key such as `reorder:{sku}:{date}` and ignore repeats. It removes the root cause, which is that orders are not idempotent. It beats the lock fix when pods crash mid-job or when the lock service is down. It costs a change in `purchasing`, which is not in this repo, so I cannot check that it supports keys. It becomes the primary once you confirm `purchasing` can take a key.
