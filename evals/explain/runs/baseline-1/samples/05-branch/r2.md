`restock-planner` sent Halvorsen Tools two purchase orders because its `reorder` lock does not cover a 4-minute job in either region. Aelita recommends a 600-second lock TTL in `eu-west` and a Redis lock in `us-east`. This fixes the duplicate whichever region it came from.

**Existing behaviour**

1. `run_reorder` in `planner/reorder.py:5` calls `locks.acquire("reorder", ..., ttl_seconds=60)` and skips the run if it returns false.
2. With `lock_backend: redis`, `acquire` in `planner/locks.py:9` sets `lock:reorder` with `nx=True, ex=60`. The key vanishes after 60 seconds.
3. With `lock_backend: none`, `acquire` in `planner/locks.py:7` returns `True` every time.
4. `run_reorder` never renews or releases the lock. It then loops over `items_below_reorder_point()` and creates one order per item.

**Timeline without the fix**

1. Pod A starts `reorder` at 01:00 and calls `acquire`.
2. `eu-west` sets `lock:reorder` with a 60-second TTL. `us-east` returns `True` and sets no key.
3. At 01:01 the `eu-west` key expires while pod A is still running. In `us-east` no lock ever existed.
4. Pod B starts at 01:02 after the node restart and calls `acquire`.
5. `eu-west` finds the key gone, so `set nx` succeeds. `us-east` returns `True` again.
6. Both pods create a purchase order for SKU HT-4410. Halvorsen Tools receives two identical orders.

The step 6 outcome assumes HT-4410 is still below its reorder point at 01:02. `purchasing` is not in this repository, so I could not check that. Four minutes of runtime makes it likely.

**Why the region does not matter**

- **`eu-west`:** The 60-second TTL expires before the 4-minute job ends. Pod B gets the lock at 01:02.
- **`us-east`:** The lock backend is `none`, so any second pod runs. Its `autoscale_max_replicas: 3` makes overlap possible.
- **Result:** Both regions fail the same way, so the fix must cover both.

**Timeline with the fix, `eu-west`**, diverges at step 3.

3. The key `lock:reorder` is still held at 01:01, because the TTL is now 600 seconds.
4. Pod B calls `acquire` at 01:02 and `set nx` fails.
5. `run_reorder` returns `skipped` on pod B.
6. Pod A finishes at about 01:04. Halvorsen Tools receives one order.

**Timeline with the fix, `us-east`**, diverges at step 2.

2. `acquire` uses Redis and sets `lock:reorder` with a 600-second TTL.
3. The key is still held at 01:01.
4. Pod B calls `acquire` at 01:02 and `set nx` fails.
5. `run_reorder` returns `skipped` on pod B.
6. Halvorsen Tools receives one order.

**What changes**

- `config/us-east.yaml`: old `lock_backend: none`, new `lock_backend: redis`.
- `planner/reorder.py`: old `ttl_seconds=60`, new `ttl_seconds=600`. 600 seconds is 2.5 times the observed 4-minute runtime.
- `config/eu-west.yaml`: no change.

**Recommendation.** Aelita recommends the longer TTL plus Redis in `us-east`, because it removes the cause. The lock now outlasts the job in both regions.
- **Cost:** A pod that crashes mid-run blocks the next attempt for up to 10 minutes.
- **What can break:** Redis must be reachable from `us-east`. Only `planner/locks.py:3` names the host `redis-locks`, and no file says it serves both regions. A job longer than 10 minutes would still duplicate.

**Alternative: idempotent purchase orders.** `create_purchase_order` gets a key of SKU plus run date and ignores repeats. It protects against any lock failure. It needs a change in `purchasing`, which is not in this repository. It becomes the primary if you can change `purchasing` or if jobs may exceed 10 minutes.

**Question.** Do you approve the 600-second TTL and the `us-east` Redis lock, or do you want the idempotent purchase order key instead?
