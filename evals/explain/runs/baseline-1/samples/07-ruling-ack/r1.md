**Ruling recorded.** `invoice-mailer` sends from `invoices@mail.larkspur.io`, replacing `billing@larkspur.io`. No decision register exists in the project, so I'm quoting it here. I haven't edited `mailer/config.py` yet.

The next open item is the retry limit for bounced mails. `BOUNCE_RETRY_LIMIT = 12` with a 60 second interval gets the new sender blocked by `smtp-mx-2`. Aelita recommends 3 retries at 900 seconds.

**Existing behaviour**

1. `handle_bounce` in `mailer/bounces.py` receives each bounce with its `attempt` number.
2. It marks the message failed when `attempt >= config.BOUNCE_RETRY_LIMIT`.
3. Otherwise it sleeps `BOUNCE_RETRY_INTERVAL_SECONDS` and resends through `config.SMTP_RELAY`.
4. `docs/mail-provider.md` says `smtp-mx-2` blocks a sender for 24 hours when one recipient bounces more than 5 times in one hour.

**Timeline without the fix**

1. `invoice-mailer` sends INV-2207 to Oskar Brandt through `smtp-mx-2`. His mailbox is full, so it soft bounces.
2. `handle_bounce` waits 60 seconds and resends.
3. The mailbox stays full. The bounce repeats every minute, and the sixth bounce lands at about minute 5.
4. `smtp-mx-2` sees more than 5 bounces for one recipient in one hour. It blocks `invoices@mail.larkspur.io` for 24 hours.
5. Every invoice to every customer is refused for 24 hours because of one full mailbox.

**Timeline with the fix**, diverges at step 2.

2. `handle_bounce` waits 900 seconds and resends.
3. Retries go out at minutes 15, 30 and 45. The fourth bounce lands at about minute 45.
4. `attempt` reaches 3, so `handle_bounce` calls `mark_failed`. The recipient bounced 4 times, which is under the limit of 5, so there is no block.

**What changes**

- `mailer/config.py`: `BOUNCE_RETRY_LIMIT` changes from `12` to `3`.
- `mailer/config.py`: `BOUNCE_RETRY_INTERVAL_SECONDS` changes from `60` to `900`.
- `mailer/config.py`: `FROM_ADDRESS` changes to `invoices@mail.larkspur.io`, as ruled. `SMTP_RELAY` changes to `smtp-mx-2.larkspur.internal` as part of the move.

**Recommendation.** Aelita recommends the two config values. They forbid the retry pattern that triggers the block and add no new code. The cost is slower delivery to a mailbox that frees up quickly. Only one bounce of margin remains, so other mail to the same recipient in the same hour can still tip it over.

**Alternative: tell hard bounces from soft bounces.** `handle_bounce` would read the SMTP status and never retry a hard bounce. It beats the config change when many invoices go to dead mailboxes, because those use zero retries. It costs new parsing code in `mailer/bounces.py`. It becomes the primary when hard bounces are common.
