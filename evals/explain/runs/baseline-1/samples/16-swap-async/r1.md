`export_invoices` in `app/exports.py` sends no byte until it has built the whole CSV, so `gw-billing` closes the connection after 30 idle seconds and returns 504. Aelita recommends moving the export to a `taskq` job on the `documents` queue that emails a signed link, the way invoice PDFs already work.

**Existing behaviour**

1. `export_invoices` runs one `db.query` for every invoice row of the tenant.
2. It writes all rows into an in-memory `io.StringIO` buffer.
3. It returns the `Response` only after the buffer is complete.
4. `gw-billing` has `idle_timeout_seconds: 30` and `request_timeout_seconds: 300`.
5. `gunicorn.conf.py` gives 12 workers, and a worker stays busy until the response ends.

**Timeline without the fix**

1. An accountant at `northfield-accounting` requests `/exports/invoices.csv` at 08:05 on month end.
2. `export_invoices` runs the query. It takes 18 seconds and returns 1,840,211 rows.
3. The build starts. The worker sends no byte to `gw-billing`.
4. At 30 seconds of silence, `gw-billing` closes the connection with reason `gw-idle-timeout`.
5. The worker keeps building until second 240. The log shows `build_seconds=222`, `total_seconds=240` and `status=504`.
6. About 900 exports arrive in two days at month end, so workers saturate. The log shows `web_workers_busy=12/12`.
7. `/invoices` p99 rises from 0.4 s on a quiet day to 9.4 s.
8. The largest tenants never get a file, and every other tenant slows down. `orbis-tax` fails the same way at 121 s with 920,114 rows.

**Timeline with the fix**, diverges at step 2.

2. `export_invoices` enqueues `render_invoice_csv` on the `documents` queue. It returns `202` in milliseconds.
3. A `taskq` worker runs the query and writes rows to a temporary file instead of memory.
4. The job calls `storage.put` and `storage.signed_url`, then `mailer.send` to the accountant.
5. `northfield-accounting` gets a download link by email. No web worker was busy for more than a few milliseconds.
6. Month-end load lands on the `documents` queue, so `/invoices` stays near its 0.4 s p99.

**What changes**

- `app/exports.py` old behaviour: `export_invoices` queries, builds and returns the CSV inline. New behaviour: it enqueues the job with `request.tenant_id` and the requester's address, then returns `202`.
- `jobs/invoice_csv.py` add: `render_invoice_csv(tenant_id, recipient)` on queue `documents`. It reuses the CSV code, writes to a temp file, then calls `storage.put`, `storage.signed_url` and `mailer.send`.
- `docs/exports.md` add one line that CSV exports are asynchronous and arrive by email.

**Recommendation.** Aelita recommends the background job. It removes the cause, which is long work inside a web request. It reuses the `taskq`, storage and `mailer` path that invoice PDFs already use. It frees the web workers and has no row limit. The cost is a changed user experience, because the file arrives by email. Two things can break it. The requester's email address must be available on `request`. `storage.put` must accept a file object or a path for multi-million-row files. Both live in the `tallyhall` package, which is not in this repository, so I could not check them.

**Alternative: stream the response.** `export_invoices` yields rows as it reads them, with a server-side cursor. It beats the recommendation on user experience, because the download starts at once and no email is needed. It keeps the 300 s total cap, and it still holds one web worker per export. It becomes the primary if tenants must get the file in the browser and their exports finish well under 300 s.

**Alternative: raise `idle_timeout_seconds`.** This is a one-line change in `deploy/gateway.yaml`. It does not stop worker saturation, and the 300 s cap still applies. It becomes the primary only as a stopgap before month end.

**Question.** Should the CSV export become a `documents` queue job that emails a signed link, or must the file download in the browser, which means streaming?
