`export_contacts` in `app/exports.py` sends no bytes until the whole CSV is built. For `bluefin-logistics` that takes 89 seconds, so `edge-lb` hits its 30-second idle limit and returns 504. Aelita recommends streaming the CSV, so bytes flow from the first second.

**Timeline without the fix**

1. A user at `bluefin-logistics` clicks "Export contacts". `edge-lb` forwards the request to `ferngrove-web`.
2. `export_contacts` runs `db.query` and loads all 412880 rows. This takes 12 seconds, and the handler sends no bytes.
3. The handler writes every row into `io.StringIO`. This takes 77 more seconds, and the handler still sends no bytes.
4. At 30 seconds `edge-lb` sees no byte in either direction. It closes the connection and returns 504.
5. The worker keeps building until 89 seconds. The log shows `total_seconds=89`, and nobody receives the result.
6. The user sees a 504. `harrow-dental` has 3120 rows, finishes in 1 second and never hits this.

**Timeline with the fix**, diverges at step 2.

2. `export_contacts` returns a `Response` that wraps a generator. The header row goes out at once, and `db` reads rows through a server-side cursor.
3. The generator yields rows in chunks of a few thousand. Each chunk restarts the `edge-lb` idle timer.
4. The connection never sits idle for 30 seconds, so `edge-lb` keeps it open.
5. The last chunk goes out at about 90 seconds.
6. The user receives the full file, and memory use stays flat.

**What changes**

- `app/exports.py`: old behaviour is `db.query` plus `io.StringIO` plus `getvalue()`. New behaviour is a generator that fetches rows in batches, writes each batch with `csv.writer`, and yields the text. The `Response` receives the generator.

**Recommendation.** Aelita recommends streaming because it removes the root cause, which is a silent connection for 89 seconds. It needs no new component and no change to `edge-lb`. It also cuts memory, since the handler no longer holds 412880 rows plus the full text. Two things can break it, and neither is settled by the repository:

- **Framework support.** `ferngrove.web.Response` and `db` are not in this repository. I could not verify that `Response` accepts an iterator or that `db` offers a streaming cursor.
- **Worker timeout.** `deploy/gunicorn.conf.py` sets `timeout = 120`. If the workers are the sync class, that limit applies to the whole request. An export that grows past 120 seconds would then be killed even while streaming.

**Alternative: raise `idle_timeout_seconds` in `deploy/edge-lb.yaml` to 120.** This is a one-line change. It costs a longer idle window for every route on `ferngrove-web`. It fails again once a tenant's export passes the new limit. It becomes the primary only if `Response` cannot stream and cannot be changed.

**Alternative: background job plus email link.** This removes the time limit entirely. `docs/exports.md` says the stack has no job queue and no email service. Each would need an owner and on-call coverage, which is heavy for about 6 exports a day. It becomes the primary if exports outgrow the worker timeout.
