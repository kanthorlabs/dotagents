`export_contacts` builds the whole CSV in memory before it sends a byte, so `edge-lb` sees 30 seconds of silence on large tenants and closes the connection with a 504. Aelita recommends streaming the CSV from a generator. It adds no new component.

**Timeline without the fix**

1. A user at `bluefin-logistics` clicks "Export contacts". `edge-lb` forwards `GET /exports/contacts.csv` to `ferngrove-web`.
2. `export_contacts` runs `db.query` and loads all 412880 rows. This takes 12 seconds, and no byte goes out.
3. `export_contacts` writes every row into one `io.StringIO`. This takes 77 more seconds, and no byte goes out.
4. At second 30 `edge-lb` has seen no byte, so its `idle_timeout_seconds: 30` fires. It returns 504 (`reason=edge-lb-idle-timeout`).
5. `export_contacts` finishes at second 89 to 90 and returns the CSV. The connection is already closed, so the user gets nothing.

The log shows this twice for `bluefin-logistics`, at 09:12 and 14:02 on 2026-10-27. `harrow-dental` has 3120 rows, finishes in 1 second and returns 200.

**Timeline with the fix**, diverges at step 2.

2. `export_contacts` returns a streaming `Response` and yields the header row at once. `edge-lb` receives the first byte and restarts its idle timer.
3. The generator runs the query, then yields rows in batches. Each batch restarts the idle timer.
4. No gap reaches 30 seconds, so `edge-lb` keeps the connection open.
5. The last batch goes out at about second 90. The user downloads the full CSV.

**What changes**

- `app/exports.py`: `export_contacts` old behaviour is to build one string in `io.StringIO` and return it. New behaviour is a generator that yields the header, then batches of CSV lines. It returns `Response(generator, content_type="text/csv")`.
- `app/exports.py`: `db.query` stays as it is. The 12-second query finishes inside the generator after the header has gone out, so it cannot trip the timer.

**Recommendation.** Aelita recommends streaming, because it removes the root cause. The root cause is that no byte goes out for the whole build, and `docs/exports.md` says each byte restarts the idle timer. It needs no queue, no email service and no new owner. Two things can break it:

- **Gunicorn limit:** `gunicorn.conf.py` sets `timeout = 120` with the default sync worker, and the worker now stays busy for the full ~90 seconds. A tenant about 30% larger than `bluefin-logistics` would hit that limit and lose its worker.
- **Unverified API:** `ferngrove.web` is not in this repository, so I could not confirm that `Response` accepts a generator.

**Alternative: raise `idle_timeout_seconds` to 120.** It is a one-line change in `deploy/edge-lb.yaml`. It costs every route a longer idle window. It also fails again as tenants grow, because the buffered build keeps getting slower. It becomes the primary only if streaming is impossible in `ferngrove.web`.

**Alternative: background job and emailed link.** It has no time limit. It needs a job queue and an email service, and `docs/exports.md` says the stack has neither and each needs an owner and on-call. It becomes the primary when exports exceed the 120-second gunicorn limit.
