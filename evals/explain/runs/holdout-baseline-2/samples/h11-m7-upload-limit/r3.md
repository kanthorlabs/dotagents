`nginx` rejects Halvorsen Marine's CAD drawings because `client_max_body_size` is 10m, and Flask would reject them next for the same reason. Aelita recommends raising both limits to 200 MB now. That needs no frontend release and meets the Friday deadline.

**Existing behaviour**

1. `deploy/nginx/pinewood.conf:8` sets `client_max_body_size 10m` for the whole server.
2. `nginx` buffers the full request body to `/var/cache/nginx/client_temp` (20 GB volume) before it proxies to `pinewood-app`.
3. `app/settings.py:3` sets `MAX_CONTENT_LENGTH` to 10 MiB. `app/__init__.py:6` loads it, so Flask enforces it.
4. `upload_file` streams the file to the bucket `pinewood-files` at about 60 MB/s.

**Timeline without the fix**

1. Eirik Dahl at Halvorsen Marine uploads a 90 MB drawing to `/api/files`. His browser sends the `Content-Length` header.
2. `nginx` reads that header and compares it with the 10m limit.
3. `nginx` rejects the request with 413 before it reads the body. The log at `logs/nginx-error-2026-10-27.log` shows this at 09:14 (94371840 bytes) and 09:31 (167772160 bytes).
4. `pinewood-app` never sees the request.
5. Raising only the `nginx` limit would not be enough. Flask would reject the request with 413 at its own 10 MiB limit.
6. Every drawing of 60 to 180 MB fails. The yard review on Monday 2 November is at risk.

**Timeline with the fix**, diverges at step 2.

2. `nginx` compares the `Content-Length` with the new 200m limit. The request passes.
3. `nginx` buffers the body at the 2.5 MB/s office uplink. A 180 MB drawing takes about 72 s. The slow client holds no gunicorn worker during this time.
4. `nginx` hands the full body to `pinewood-app`. Flask accepts it under the new 200 MiB limit.
5. `upload_file` writes it to the bucket in about 3 s, well under the gunicorn `timeout` of 30 s.
6. The API returns 201. Eirik Dahl's drawing is stored.

**What changes**

- `deploy/nginx/pinewood.conf`: add `location = /api/files` with `client_max_body_size 200m` and the same `proxy_pass` and headers. The server-wide `10m` stays for other routes. Nginx prefers an exact match, so the new block takes the upload route.
- `app/settings.py`: change `MAX_CONTENT_LENGTH` from `10 * 1024 * 1024` to `200 * 1024 * 1024`.

**Recommendation.** Aelita recommends the two limit changes. They remove the cause, which is a cap sized for small documents. Checked facts back them:
- 25 drawings at 180 MB is 4.5 GB per day, which fits in the 20 GB buffer. `nginx` deletes each temp file after its request.
- The 3 s write time sits far inside the worker timeout.
- Only the upload route gets the larger limit.

The cost is disk buffering and a 200 MB body on that route. The 4 sync workers can handle 4 concurrent uploads, and each holds a worker for about 3 s. Any account can now send 200 MB to `/api/files`, so a per-account limit would need separate work.

**Alternative: direct-to-bucket upload with `presign_post`.** The browser posts straight to `pinewood-files`, and `pinewood-app` stays out of the data path. It removes the buffering and the size limit on the app. It needs a new endpoint and a web client change, because `storage.presign_post` exists but nothing calls it.
