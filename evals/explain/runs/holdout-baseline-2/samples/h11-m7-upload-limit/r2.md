Two separate 10 MB limits reject every Halvorsen Marine drawing, one in `nginx` and one in Flask. Aelita recommends raising both to 200 MB, with the nginx limit scoped to `/api/files`. That needs no frontend release and can ship before Friday 30 October.

**Timeline without the fix**

1. Eirik Dahl uploads a 94 MB drawing from the form on `docs.pinewood.example`. The browser sends a POST to `/api/files`.
2. `nginx` reads the Content-Length header. `client_max_body_size 10m` in `deploy/nginx/pinewood.conf:8` is smaller than the body.
3. `nginx` returns "413 Request Entity Too Large". The request never reaches `pinewood-app`. The log shows `client intended to send too large body: 94371840 bytes` at 09:14:02 on 2026-10-27.
4. A second drawing of 167772160 bytes fails the same way at 09:31:47.
5. Raising only the `nginx` limit moves the failure. `MAX_CONTENT_LENGTH = 10 * 1024 * 1024` in `app/settings.py:3` is loaded by `create_app`. Flask would reject the body in `upload_file` with its own 413.
6. Every drawing from 60 to 180 MB fails. Halvorsen Marine cannot meet its Monday 2 November yard review.

**Timeline with the fix**, diverges at step 2.

2. `nginx` sees a 94 MB body. The limit on `/api/files` is now 200m, so it accepts the request.
3. `nginx` buffers the body to `/var/cache/nginx/client_temp`. The 20 GB volume holds it easily. 25 drawings of 180 MB at most is 4.5 GB per day, and each temp file is removed after its request.
4. `nginx` forwards the body to `pinewood-app` at LAN speed. The slow 20 Mbit/s uplink is already absorbed by the buffering. Flask now accepts up to 200 MB.
5. `storage.put` streams the file to `pinewood-files` at about 60 MB per second. A 180 MB drawing takes about 3 seconds, well under the gunicorn `timeout = 30`.
6. `upload_file` returns 201 with the key. The slowest upload on the 20 Mbit/s uplink takes about 72 seconds, but only the client-to-`nginx` leg is slow.

**What changes**

- `deploy/nginx/pinewood.conf` old behaviour: `client_max_body_size 10m;` applies to the whole server. New behaviour: keep 10m on the server. Add `location = /api/files { client_max_body_size 200m; proxy_pass http://pinewood-app:8000; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; }` above `location /api/`.
- `app/settings.py` old behaviour: `MAX_CONTENT_LENGTH = 10 * 1024 * 1024`. New behaviour: `MAX_CONTENT_LENGTH = 200 * 1024 * 1024`.

**Recommendation.** Aelita recommends raising both limits to 200 MB. The largest drawing is 180 MB, so this leaves headroom. The nginx limit is scoped to one route, so other `/api/` routes keep 10m. Flask has no per-route limit here, so its global limit rises to 200 MB. The risk is that a client can now send 200 MB bodies to any Flask route. Only `/api/files` is reachable with a large body, because `nginx` blocks the others at 10m. The same limit must stay in sync in two files. A slow upload holds an `nginx` buffer slot but no gunicorn worker, so the 4 sync workers are not tied up.

**Alternative: presigned direct upload to the bucket.** The client would call a new endpoint that uses `storage.presign_post`, then POST straight to `pinewood-files`. This removes the size limits and the load on `pinewood-app`. `storage.presign_post` already exists. It needs a frontend change, because the web client sends a plain form POST.
