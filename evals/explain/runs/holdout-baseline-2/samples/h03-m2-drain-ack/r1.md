`lantern-worker` loses jobs on deploy because `consume.py:22` sets `auto_ack=True`, so RabbitMQ deletes each job on delivery. The pod then gets SIGKILL after 20s, while the drain waits up to 60s. Aelita recommends manual acks after the job finishes, plus a grace period longer than the drain.

**Timeline without the fix**

1. `consume.py:22` uses `auto_ack=True`. RabbitMQ forgets u-88217, u-88218 and u-88219 at 14:02:05 to 14:02:07. They only exist in the `ThreadPoolExecutor` of `lantern-worker-7f9c-2`.
2. At 14:02:10 Kubernetes sends SIGTERM. `consume.py:23` stops consuming and the log promises a drain of up to 60s.
3. `drain` calls `pool.shutdown(wait=False)`, which keeps pending work. At 14:02:21 u-88213 finishes, and u-88220 and u-88221 start. This is real work after SIGTERM.
4. At 14:02:30 the kubelet sends SIGKILL. `values-prod.yaml` sets `terminationGracePeriodSeconds: 20`, which is 40s before the drain deadline.
5. u-88217, u-88218, u-88219 and u-88221 have no `job done` line. The process died with no exception and no `drain deadline reached` warning.
6. RabbitMQ holds no copy, so nothing retries. The upload page shows the placeholder forever, as `docs/thumbnails.md` says. Jobs that were queued in the pool but never started are lost too, and the log cannot show them.

**Timeline with the fix**, diverges at step 1. Steps 2 and 3 are unchanged.

1. The worker consumes with `auto_ack=False` and `prefetch_count=4`. RabbitMQ keeps u-88217, u-88218 and u-88219 as unacked until each job finishes.
4. SIGKILL is now unlikely, because the grace period is 90s and the drain deadline is 75s. If a SIGKILL or a crash still comes, the connection drops.
5. RabbitMQ requeues every unacked job. Finished jobs were already acked.
6. Another worker renders the requeued jobs. The thumbnails appear.

**What changes**

- `worker/consume.py`: add `channel.basic_qos(prefetch_count=settings.CONCURRENCY)` and set `auto_ack=False`.
  - `on_message` submits a wrapper that runs `handle`, then calls `connection.add_callback_threadsafe` to `basic_ack`. pika channels are not thread-safe, so the pool threads cannot ack directly.
  - On an exception the wrapper logs it and calls `basic_nack` with `requeue=False`, so a bad job cannot loop.
- `worker/lifecycle.py`: `drain` takes the `connection`. It replaces `time.sleep(0.5)` with `connection.process_data_events(time_limit=0.5)`. After `stop_consuming`, nothing else runs the ack callbacks, so jobs that finish during the drain would never be acked and would be redelivered.
- `deploy/helm/values-prod.yaml`: change `terminationGracePeriodSeconds` from `20` to `90`. Add `LANTERN_DRAIN_SECONDS: "75"`, replacing the default of 60. `docs/thumbnails.md` gives video jobs up to 70s, so the drain must cover that and the grace period must exceed the drain.

**Recommendation.** Aelita recommends manual acks plus the longer grace period. This removes the root cause, which is that the broker forgets jobs the worker has not finished. It also covers OOM kills and node loss. The cost is possible redelivery. `put_thumbnail` writes a fixed key, so a repeat is harmless. A kill between `put_thumbnail` and `record_usage` would send `record_usage` twice for one `ref`. `meter.internal` belongs to Billing, and no file in this repository says whether it dedupes on `ref`.

**Alternative: raise only the grace period and drain.** Set `terminationGracePeriodSeconds: 90` and `LANTERN_DRAIN_SECONDS: 75`, with no code change. It is cheap and cannot cause duplicate billing. It still loses jobs on a crash or OOM kill. It becomes the primary if Billing confirms that `meter.internal` does not dedupe on `ref` and cannot start doing so.
