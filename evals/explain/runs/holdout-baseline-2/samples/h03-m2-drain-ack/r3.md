`lantern-worker` loses jobs on every deploy because it acks each message on delivery, and kubelet kills the pod 40 seconds before the drain can finish. Aelita recommends acking only after the job finishes, and aligning the grace period with the drain time.

**Timeline without the fix**

1. At 14:02:05 to 14:02:07, `lantern-worker-7f9c-2` starts videos u-88217, u-88218 and u-88219. Each takes 25 to 70 seconds.
2. At 14:02:10 the pod gets SIGTERM. `consume.py` stops consuming and `drain` waits up to 60s.
3. At 14:02:21 u-88213 finishes. A thread then picks up u-88220 and u-88221, which `auto_ack=True` had already pulled into the pool queue. u-88221 starts at 14:02:23.
4. At 14:02:30 kubelet sends SIGKILL, because `terminationGracePeriodSeconds` is 20 in `values-prod.yaml`. The 60s drain never gets to run.
5. The threads for u-88217, u-88218, u-88219 and u-88221 die mid-render. No `job done` line exists for them. There may be more jobs that sat unstarted in the pool queue.
6. RabbitMQ already acked all of them at delivery, so nothing is redelivered. The upload page shows its placeholder with no error, which matches `docs/thumbnails.md`.

**Timeline with the fix**, diverges at step 3.

3. `basic_qos(prefetch_count=4)` means the pool holds at most 4 unacked jobs. RabbitMQ keeps the rest in the queue.
4. At 14:02:30 kubelet keeps waiting, because the grace period is now 90s. `drain` runs up to 75s and keeps processing ack callbacks.
5. Finished jobs get acked. At 14:03:25 the drain deadline hits and the process exits. Any job still running stays unacked.
6. RabbitMQ requeues the unacked jobs and another worker renders them. Every upload gets its thumbnail.

**What changes**

- `worker/consume.py`: `basic_consume` changes from `auto_ack=True` to `auto_ack=False`. Add `basic_qos(prefetch_count=settings.CONCURRENCY)`. `on_message` submits a wrapper that runs `handle`, then calls `connection.add_callback_threadsafe` to `basic_ack`. On an exception it logs the error and does a `basic_nack` with `requeue=False`. Today `pool.submit` swallows exceptions silently, which is a second way to lose a thumbnail with no error.
- `worker/lifecycle.py`: `drain` takes the connection. The `time.sleep(0.5)` becomes `connection.process_data_events(time_limit=0.5)`. Without this, acks queued during the drain are never sent. Finished jobs would then be redelivered and rendered twice.
- `deploy/helm/values-prod.yaml`: `terminationGracePeriodSeconds` changes from 20 to 90. Add `LANTERN_DRAIN_SECONDS: "75"`. The default of 60 is shorter than a 70s video.

**Recommendation.** Aelita recommends manual ack with prefetch and a matching grace period. It removes the root cause, which is acking before the work is done. Any kill then costs a redelivery instead of a lost thumbnail. The cost is a possible duplicate render. If a kill lands between `put_thumbnail` and the ack, the job runs again. The S3 key is the same, so the overwrite is harmless. `record_usage` in `billing/client.py` sends no idempotency key, though. A redelivered job could bill twice unless `meter.internal` dedupes on `ref`. The Billing team owns that service, so no file here settles it.

**Alternative: only raise the grace period and drain time.** This is a config change only, with no code change. It is enough when the deploy always lands inside the drain window. It still loses jobs on a crash, an OOM kill or a node loss. It becomes the primary only if you need a hotfix before the code change ships.
