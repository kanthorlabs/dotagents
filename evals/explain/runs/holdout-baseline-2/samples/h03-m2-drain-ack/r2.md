`lantern-worker` loses these uploads because it acks each message on delivery and then gets SIGKILLed mid-render. The broker has already deleted the job, so nothing retries it and nothing logs an error. Aelita recommends acking after the job finishes and raising the grace period above the drain time.

**Timeline without the fix**

1. At 14:02:05 to 14:02:07, `lantern-worker-7f9c-2` takes the video jobs u-88217, u-88218 and u-88219. `consume.py:22` uses `auto_ack=True`, so RabbitMQ deletes each message on delivery.
2. At 14:02:10, SIGTERM arrives. `stop_consuming` runs and `drain` starts with a 60s budget (`LANTERN_DRAIN_SECONDS` default).
3. At 14:02:21, u-88213 finishes. `pool.shutdown(wait=False)` does not cancel queued work, so the pool starts u-88220 and u-88221 anyway.
4. At 14:02:30, kubelet sends SIGKILL. `values-prod.yaml` sets `terminationGracePeriodSeconds: 20`, which is shorter than the 60s drain and the 25 to 70s video renders.
5. The threads for u-88217, u-88218, u-88219 and u-88221 die mid-render. No exception and no log line is written. The last log line is the kubelet kill.
6. RabbitMQ holds no copy of these jobs, so nothing retries them. `thumbs/<upload_id>.webp` never appears and the upload page shows its placeholder forever.

**Timeline with the fix**, diverges at step 1.

1. `lantern-worker-7f9c-2` takes u-88217, u-88218 and u-88219 without acking. A prefetch limit of `CONCURRENCY` caps unacked jobs at 4.
4. Kubelet sends SIGKILL at 14:02:30, as before. The grace period is now 90s, so most videos finish before this point.
5. The AMQP connection drops. RabbitMQ requeues every unacked job.
6. Another worker renders each requeued job and writes the thumbnail. The uploads get their thumbnails.

**What changes**

- `worker/consume.py` old behaviour: `auto_ack=True` and unlimited prefetch. New behaviour: `basic_qos(prefetch_count=settings.CONCURRENCY)` and `auto_ack=False`. `on_message` passes `method.delivery_tag` to `handle`. The ack goes through `connection.add_callback_threadsafe`, because pika channels are not thread-safe.
- `worker/handler.py` old behaviour: `handle` has no error handling, and `pool.submit` hides exceptions in the future. New behaviour: `handle` logs any exception with the `upload_id` and nacks with requeue, and acks only after `record_usage` returns.
- `deploy/helm/values-prod.yaml` old value: `terminationGracePeriodSeconds: 20`. New value: `90`, so it exceeds `LANTERN_DRAIN_SECONDS` (60) and the longest video render (70s). Set `LANTERN_DRAIN_SECONDS` to 80 to match.

**Recommendation.** Aelita recommends ack-after-completion plus the longer grace period. Ack-after-completion removes the cause, because a killed job is redelivered instead of lost. The grace period only cuts how often kills happen. The cost is possible duplicate work. `put_thumbnail` writes a fixed key, so a repeat is harmless. `record_usage` could bill twice if a kill lands between the upload and the ack. The `ref` field may already dedupe, but `meter.internal` belongs to Billing and is not in this repository, so I could not verify that. `worker/render.py` is also missing from the repository, so I did not check it.

**Alternative: raise only the grace period.** Set `terminationGracePeriodSeconds` to 90 and change no code. It beats the recommendation on size, because it is a one-line change. It still loses jobs on an OOM kill, a node loss or any kill past 90s. It becomes the primary if Billing cannot confirm that `ref` dedupes and a double bill is worse than a missing thumbnail.
