The stale price comes from the per-pod `price_cache` in `pricing/service.py`, not from the CDN. Lowering the CDN TTL would change nothing. Aelita recommends dropping the 3600-second `TTLCache` and reading the database on each price request. The other fix is to have each pod subscribe to `price.changed`.

**Existing behaviour**

1. `cdn/rules.yaml` sets `/api/*` to `cache: false`. The 3600 TTL there belongs to `/product/*`, whose HTML holds no price.
2. `shop-api` runs 6 replicas. Each pod has its own in-process `price_cache`, a `TTLCache` with `ttl=3600`.
3. `update_price` in `admin/prices.py` calls `price_cache.pop(sku)`. That clears only the pod that handled the admin request.
4. `update_price` also publishes `price.changed`. Only `search/indexer.py` subscribes to it. No pricing code does.

**Timeline without the fix**

1. Before 10:02, all 6 pods hold KET-2210 at 39.90 in their `price_cache`.
2. At 10:02, Tove Lindqvist posts 34.90. The load balancer sends it to pod A.
3. Pod A writes the database, pops its own cache entry and publishes `price.changed`. Only the search indexer reacts.
4. Pods B to F still hold 39.90. Their entries expire up to 3600 seconds after they were filled.
5. A reload of `/api/prices?sku=KET-2210` goes to a random pod. Tove sees 34.90 on some reloads and 39.90 on others.
6. The last pod expires its entry around 10:58, and customers see 39.90 at checkout until then. This matches SM-140.

**Timeline with the fix**, diverges at step 4.

4. Pods B to F have no cached KET-2210 entry. The next request on each pod reads 34.90 from the database.
5. Every reload returns 34.90 from whichever pod serves it.
6. Customers see 34.90 at checkout right after step 3.

**What changes**

- `pricing/service.py`: delete `price_cache` and its `TTLCache` import. `get_price` returns `db.fetch_price(sku)` directly.
- `admin/prices.py`: delete the `price_cache` import and the `price_cache.pop(sku, None)` line.
- `cdn/rules.yaml`: no change. A 60-second TTL there would not touch `/api/*`.

**Recommendation.** Aelita recommends removing the per-pod cache. It removes the root cause, which is six caches that nothing keeps in sync. A price change then shows immediately, and there is no invalidation logic left to fail. It costs one database read per price request, and the product pages, cart and checkout all call this endpoint. If `db.fetch_price` is slow under that load, this option breaks.

**Alternative: subscribe each pod to `price.changed`.** Each pod calls `subscribe("price.changed", ...)` from `shared/events.py` and pops the SKU from its own `price_cache`. This keeps the read-through cache and its database savings. The cost is a startup hook in `shop.app`, and a pod that misses a Redis pub/sub message (which is not durable) stays stale for up to an hour. It becomes the primary if load tests show the database cannot take every price read.

**Alternative: your proposal, a 60-second TTL.** Set `ttl=60` on `price_cache`, and not in the CDN. It is one line and caps staleness at a minute. It still shows the old price for up to 60 seconds, which is wrong at checkout. It is the primary only if a one-minute delay is acceptable to the business.

**Question.** Should `get_price` read the database directly, or should each pod subscribe to `price.changed`?
