Lowering the CDN TTL changes nothing, because the CDN does not cache the price API. `cdn/rules.yaml:10-11` sets `/api/*` to `cache: false`. The stale price comes from `price_cache` in `pricing/service.py:5`, a per-pod TTLCache with a 3600 second TTL. Aelita recommends that every `shop-api` pod subscribes to `price.changed` and drops the SKU from its own cache.

**Existing behaviour**

1. `get_price` in `pricing/service.py` caches each SKU in an in-process `price_cache` for 3600 seconds.
2. `shop-api` runs 6 replicas (`deploy/api.yaml:6`). Each pod has its own `price_cache`.
3. `update_price` in `admin/prices.py:14` runs `price_cache.pop(sku)`. That clears only the pod that served the admin request.
4. `update_price` then publishes `price.changed`. The only subscriber in the repo is `search/indexer.py`, which updates the search index. No pod subscribes to clear its price cache.

**Timeline without the fix**

1. Before 10:02, all 6 pods hold 39.90 for KET-2210 in `price_cache`. Each pod filled its entry at a different time.
2. At 10:02, Tove Lindqvist saves 34.90. The load balancer sends the request to one pod.
3. That pod writes the database, clears its own `price_cache` and publishes `price.changed`. `search-indexer` updates the index. No `shop-api` pod reacts.
4. The product page calls `/api/prices?sku=KET-2210`. The CDN skips `/api/*`, so the load balancer picks a pod. The pod that took the admin write returns 34.90. The other 5 return 39.90. Tove sees both values on reloads.
5. Each of the 5 other pods keeps 39.90 until its own entry expires. That is up to 3600 seconds after its fill.
6. The last old price appears at 10:57 and checkout shows 39.90 until about 10:58. Customers pay the old price for nearly an hour.

**Timeline with the fix**, diverges at step 3.

3. The pod that took the write clears its cache and publishes `price.changed`. All 6 `shop-api` pods receive it and call `price_cache.pop("KET-2210")`.
4. The next `/api/prices` call on any pod misses the cache and reads 34.90 from the database.
5. Every pod caches 34.90. Reloads show 34.90 on every pod within about a second of the save.

**What changes**

- `pricing/service.py`: add `on_price_changed(event)`, which runs `price_cache.pop(event["sku"], None)`. Add `start_invalidation()`, which calls `subscribe("price.changed", on_price_changed)`.
- `admin/prices.py`: no change. The local `pop` stays and is harmless.
- `shop-api` startup: call `start_invalidation()` once per pod. The entrypoint `shop.app:app` is not in this repo, so I could not check where this call goes.

**Recommendation.** Aelita recommends the subscriber, because it removes the cause: pods never learn about a price change. It reuses the existing `price.changed` event and costs one Redis connection per pod. Redis pub/sub does not replay messages, so a pod that is disconnected during a publish keeps the old price until its TTL expires. Cutting `price_cache` TTL from 3600 to 300 limits that window to 5 minutes. Your CDN proposal fails because it edits a rule that never applies to `/api/*`. Setting `/api/*` to `cache: true` with 60 seconds would add a new cache layer. It would still show old prices for 60 seconds.

**Alternative: shorten the `price_cache` TTL to 60.** Change `ttl=3600` to `ttl=60` in `pricing/service.py:5`. It is one line and needs no Redis. The cost is up to 60 seconds of old price and more database reads. It becomes the primary if a minute of old price is acceptable and you want no new moving parts.

**Alternative: shared Redis price cache.** Pods read prices from Redis, so one `delete` clears them all. It is exact with no pub/sub gap. It costs a Redis read per price call and a larger change. It becomes the primary if a missed message is unacceptable.
