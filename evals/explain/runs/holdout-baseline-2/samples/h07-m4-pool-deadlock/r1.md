`checkout` holds one pool connection and then `hold_seats` asks the same pool for a second one. Once 10 requests in one pod hold a connection each, all of them wait for a connection that none can release. Aelita recommends passing the open connection into `hold_seats`.

**Existing behaviour**

1. `checkout` at `app/checkout.py:6` takes a connection from `pool` (`max_size=10`) and opens a transaction.
2. It inserts the order, then calls `hold_seats` at line 12.
3. `hold_seats` at `app/seats.py:5` calls `pool.connection()` again. It needs a second connection while the first is still held.

**Timeline without the fix**

1. At 19:00:00 the Halden Arena on-sale starts. `checkout-api-2` has `in_flight=14`.
2. Ten requests each take a connection at `checkout.py:6`. `pool_in_use=10`.
3. Each of the ten calls `hold_seats` and waits for a second connection. The other 4 requests wait at `checkout.py:6`. `pool_waiting=14`.
4. Nothing is released, because each holder waits on a waiter. `pg-copperline` shows 38 of 200 connections, so the database is idle.
5. At 19:00:31 the 30 second `timeout` fires. The log shows 10 `PoolTimeout` in `hold_seats` and 4 in `checkout`. All 14 requests return 500.
6. The freed connections go to the next 12 waiters. They deadlock the same way and fail at 19:01:02.

At normal traffic `in_flight=3` is below 10, so spare connections always exist and the second acquire succeeds. The limit is the pool size of one pod, not `max_connections`. The deadlock needs at least 10 concurrent checkouts in that pod.

**Timeline with the fix**, diverges at step 3.

3. `checkout` passes `conn` to `hold_seats`. It runs the seat `UPDATE` on the connection it already holds. It takes no second connection.
4. `checkout` updates the order to `held` and commits. The connection returns to `pool`.
5. The next waiting request takes that connection. Requests queue briefly and drain at database speed.
6. No request waits 30 seconds, and none fails with `PoolTimeout`.

**What changes**

- `app/seats.py` old behaviour: `hold_seats(event_id, seat_ids)` opens its own `pool.connection()`. New behaviour: `hold_seats(conn, event_id, seat_ids)` runs `conn.execute` and does not import `pool`.
- `app/checkout.py` old behaviour: line 12 calls `hold_seats(order.event_id, order.seat_ids)`. New behaviour: it calls `hold_seats(conn, order.event_id, order.seat_ids)`.

**Recommendation.** Aelita recommends passing `conn`. It removes the cause, which is the nested acquire. It also fixes a second bug. Today the seat hold commits on its own connection, so a later failure rolls back the order but leaves the seats held for 10 minutes. Now both writes share one transaction. The cost is a signature change. `checkout` is the only caller I found in `app/`.

**Alternative: cap concurrency per pod.** Add a semaphore of 5 around `checkout`, so nested acquires never exhaust the pool. It needs no signature change. It keeps the nested pattern and the split commit. It becomes the primary if `hold_seats` must keep its own transaction.
