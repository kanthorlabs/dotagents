`checkout` in `app/checkout.py` holds one pool connection and then asks the same pool for a second one inside `hold_seats`. Under load, every connection ends up held by a request that is waiting for another. Aelita recommends passing the open connection into `hold_seats`.

**Timeline without the fix**

1. At 19:00:00 the Halden Arena on-sale starts. Each `checkout-api` pod receives a burst of `POST /checkout` requests. The pool in `app/db.py` has `max_size=10`.
2. Ten requests on `checkout-api-2` run `pool.connection()` at `app/checkout.py:6`. They take all 10 connections and open a transaction each.
3. Each of the 10 calls `hold_seats`. At `app/seats.py:5` it asks the same pool for a second connection. None is free, so it waits.
4. The 4 later requests also wait at `app/checkout.py:6`. The log at 19:00:01 shows `pool_in_use=10 pool_waiting=14`.
5. No holder can finish, because each needs a connection that only another holder can release. Postgres shows `active_connections=38` of 200, so the database is idle. The stall is inside the pool.
6. At 19:00:31 `timeout=30` expires. The log shows 10 `PoolTimeout` errors in `hold_seats`, 4 in `checkout` and 14 `500` responses at once. The next wave fills the pool the same way and fails at 19:01:02.

At normal traffic, `in_flight` stays at 3 or below. The pool never runs out, so the second `pool.connection()` call always succeeds.

**Timeline with the fix**, diverges at step 3.

3. `hold_seats` receives the connection that `checkout` already holds. It runs its `UPDATE` on it and asks the pool for nothing.
4. Each request uses exactly one connection. The 10 in the pool finish their work and release. The 4 extra requests wait a few milliseconds.
5. Excess load queues briefly and drains. It no longer deadlocks.
6. The 30-second freeze and the mass `500` responses do not occur.

**What changes**

- `app/seats.py`: `hold_seats(event_id, seat_ids)` opens its own connection with `pool.connection()`. It becomes `hold_seats(conn, event_id, seat_ids)` and runs the `UPDATE` on `conn`. The `pool` import is deleted.
- `app/checkout.py`: line 12 changes from `hold_seats(order.event_id, order.seat_ids)` to `hold_seats(conn, order.event_id, order.seat_ids)`.

**Recommendation.** Aelita recommends the single connection. It removes the root cause, which is two pool acquisitions nested in one request. It also fixes a second bug. Today the seat hold commits on its own connection, so a failure after line 12 rolls back the order but leaves the seats held for 10 minutes. With one transaction, both roll back together. The cost is that the seat `UPDATE` now runs inside the order transaction, so the transaction stays open slightly longer. Any other caller of `hold_seats` breaks, so I need to check for them.

**Alternative: raise `max_size` above the concurrent request count.** It is a one-line change in `app/db.py`. It only moves the threshold, so a larger on-sale deadlocks the same way. It also multiplies connections by 4 pods against `max_connections=200`. It becomes the primary only if the code cannot change before the next on-sale.
