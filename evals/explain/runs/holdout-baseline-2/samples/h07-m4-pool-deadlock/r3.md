`checkout` holds one pooled connection and then calls `hold_seats`, which asks the same pool for a second one. Under load, every connection ends up held by a request that is waiting for another. Aelita recommends passing the open connection into `hold_seats`.

**Timeline without the fix**

1. At 19:00:00 the Halden Arena on-sale starts. `checkout-api-2` has 14 requests in flight against a pool with `max_size=10` (`app/db.py:8`).
2. 10 requests take a connection at `app/checkout.py:6` and open a transaction. `pool_in_use=10`. The other 4 wait for a connection at the same line.
3. Each of the 10 holders calls `hold_seats` (`app/checkout.py:12`). It runs `pool.connection()` at `app/seats.py:5`. The pool is empty, so the holder waits and keeps its first connection.
4. Nothing releases a connection. The 10 holders wait on the 4 waiters' slots, and the 4 waiters wait on the holders. `pool_waiting=14`. Postgres shows only 38 of 200 connections because the pool cap is hit, not the database cap.
5. At 19:00:31 the 30 s `timeout` (`app/db.py:9`) fires. 10 `hold_seats` calls and 4 `checkout` calls raise `PoolTimeout`. All 14 requests return 500 at once.
6. The next 12 queued requests repeat steps 2 to 5. They fail at 19:01:02. The 30 s freeze repeats for as long as the burst lasts.

At normal traffic `in_flight=3`. The pool never empties, so the second `pool.connection()` always succeeds and the bug stays hidden.

**Timeline with the fix**, diverges at step 3.

3. Each holder calls `hold_seats(conn, ...)` and runs the `UPDATE` on its own connection. No second connection is requested.
4. The holder commits and returns its connection in milliseconds. The 4 waiters get connections.
5. All 14 requests finish. Excess load now queues briefly instead of deadlocking.

**What changes**

- `app/seats.py` old behaviour: `hold_seats(event_id, seat_ids)` opens its own `pool.connection()`. New behaviour: `hold_seats(conn, event_id, seat_ids)` runs `conn.execute` on the connection it receives. Delete the `pool` import.
- `app/checkout.py` old behaviour: `hold_seats(order.event_id, order.seat_ids)`. New behaviour: `hold_seats(conn, order.event_id, order.seat_ids)`.

**Recommendation.** Aelita recommends passing `conn`, because it removes the cause. Each request then needs exactly one connection, so no request can wait while holding one. The seat hold also joins the order transaction. Today it commits on its own connection, so a failure after line 12 leaves seats held for 10 minutes with no order. The cost is a signature change. Any other caller of `hold_seats` must pass a connection. I found none in this repository.

**Alternative: raise `max_size` or lower `timeout`.** This changes only config. It raises the load at which the deadlock appears, and it fails the same way at a bigger on-sale. At 4 replicas, `max_size=10` already gives 40 connections, and 200 is the database limit. It becomes the primary only as a stopgap before the code change can ship.
