Search stayed down because retries multiplied each search into about 9 `ranker` requests, and `ranker` kept scoring queued requests that nobody was waiting for. Aelita recommends a bounded queue in `ranker` that rejects excess requests with 429.

**Timeline without the fix**

1. 14:02: The index merge slows `ranker`. p99 goes from 400 ms to 900 ms.
2. 14:04: `query-gw` has a 600 ms timeout, so requests time out. It retries each one twice, which makes 3 attempts per search.
3. 14:04: `searchClient.ts` waits 2000 ms and makes up to 3 attempts. The `query-gw` retries are inside each web attempt, so each search can make up to 9 `ranker` requests. 400 searches per second becomes about 3,600 requests per second, which matches the 3,500 in the notes.
4. 14:06: The merge ends. `ranker` can serve only about 1,200 requests per second, so the 3,500 per second still arriving is nearly 3 times its capacity.
5. 14:06 to 14:39: The queue has no limit, so it grows to about 180,000 requests. At 1,200 per second that is a wait of about 150 s, far beyond the 600 ms timeout. Every client has already given up, but `ranker` still scores each abandoned request. Each timeout triggers another retry, so the load sustains itself.
6. 14:39: Tomasz turns on the maintenance page. User traffic drops to zero. The queue drains in about 2 minutes (180,000 / 1,200 = 150 s) and is empty at 14:41. Search was down for 37 minutes with no cause left except the backlog and the retries.

**Timeline with the fix**, diverges at step 5.

5. 14:06: Each `ranker` instance holds a short queue, for example 64 waiting requests. That is about 0.4 s of work, which is under the 600 ms timeout. It rejects the rest at once with 429. `query-gw` does not retry 429, because `retry_on` covers only timeouts and 5xx.
6. 14:07: The backlog holds only requests that can still succeed. Real searches get through again within seconds of the merge ending. Search is down for about 4 minutes, not 37.

**What changes**

- `ranker/server.py`: old behaviour is that `rank` sends every request to `executor`, with an unlimited queue. New behaviour is that `rank` counts in-flight requests. Above the limit it returns HTTP 429 without calling `score`.
- `docs/capacity.md`: replace "The queue has no limit." with the new limit and the reason for it.

**Recommendation.** Aelita recommends the bounded queue with 429 in `ranker`. It removes the root cause, which is an unbounded backlog of stale work. It costs a few lines in `server.py`. Two things can go wrong. A limit set too low rejects real traffic during normal peaks. A limit set too high brings the backlog back. The choice of 429 matters: a 503 would match `retry_on: 5xx` and keep the retry storm going.

**Alternative: cut the retries.** Set `retries: 0` in `config.yaml` and `MAX_ATTEMPTS = 1` in `searchClient.ts`. This is simpler and removes the 9x amplification. It does not remove the backlog, so a real overload would still leave `ranker` scoring dead requests. It becomes the primary if `ranker` cannot be changed soon.

**Question.** Should `ranker` reject excess requests with 429 at about 64 queued requests per instance, or should we cut the retries first?
