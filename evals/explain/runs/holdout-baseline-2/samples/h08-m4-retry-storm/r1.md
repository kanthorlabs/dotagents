Search stayed down because `web` and `query-gw` retry timed-out requests, which multiplies 400 searches per second into about 3,600 `ranker` requests per second. That is three times the 1,200 per second that `ranker` can serve. Aelita recommends removing the stacked retries, because they are the cause and the unbounded queue only keeps the damage.

**Timeline without the fix**

1. The index merge starts at 14:02. `ranker` p99 rises from 400 ms to 900 ms, above the 600 ms `timeout_ms` in `query-gw/config.yaml`.
2. `query-gw` times out and retries up to 2 times. `searchClient.ts` in `web` also retries up to 3 attempts. One search becomes up to 3 × 3 = 9 `ranker` requests.
3. 400 searches per second × 9 gives 3,600 requests per second. The incident notes show 3,400 to 3,600 per second. `ranker` serves about 1,200 per second.
4. The merge ends at 14:06, but the load stays at 3x capacity. The queue has no limit, so it grows to about 180,000 requests.
5. A request now waits minutes in the queue, far beyond 600 ms. Every request times out and is retried.
6. `ranker` still scores requests that `query-gw` abandoned, because `rank` in `ranker/server.py` never checks for cancellation. The workers spend their time on dead requests, so the error rate stays at 97 %.
7. At 14:39 the maintenance page stops all user traffic. The queue drains in about 150 seconds (180,000 ÷ 1,200 per second). It is empty at 14:41 and search works again.

**Timeline with the fix**, diverges at step 2.

2. `query-gw` has `retries: 0` and `searchClient.ts` has `MAX_ATTEMPTS = 1`. One search stays one `ranker` request.
3. Load stays at 400 requests per second, a third of the 1,200 per second capacity.
4. The merge ends at 14:06. The backlog from the 4 slow minutes is a few thousand requests at most. It drains within seconds.
5. Waits fall below 600 ms and requests succeed.
6. Search recovers at about 14:06 without human action.

**What changes**

- `query-gw/config.yaml`: `retries: 2` becomes `retries: 0`. `retry_on` is no longer used.
- `web/src/searchClient.ts`: `MAX_ATTEMPTS = 3` becomes `MAX_ATTEMPTS = 1`. The loop then runs once.

**Recommendation.** Aelita recommends one retry layer at most, and none on timeout. A timeout means `ranker` is overloaded, so a retry adds load to the failing service. The cost is that a single transient 5xx now reaches the user. The user can search again by hand. It does not protect against an overload that comes from real traffic growth.

**Alternative: bound the `ranker` queue and drop stale requests.** `ranker` rejects work when the queue is full or the request is older than 600 ms. It beats the recommendation because it protects `ranker` from any overload, not only retries. It costs a code change in `ranker/server.py` and a decision on the limit. It becomes the primary if retries must stay for transient errors.
