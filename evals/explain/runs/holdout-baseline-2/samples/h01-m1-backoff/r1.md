Backoff alone will not fix this. `tidepool-sync` sends one request per contact, and Juniper allows 100 requests per minute, so the job cannot finish in its 2-hour deadline. Aelita recommends switching to `POST /v2/contacts:batchUpsert` and adding a small `Retry-After` retry as a safety net.

**Existing behaviour**

1. `sync/run_sync.py` loads all changed contacts and runs 8 workers.
2. Each worker calls `upsert_contact` in `sync/crm_client.py`, which sends one `PUT` per contact.
3. A 429 raises in `raise_for_status`. `sync_one` logs a warning and skips `mark_synced`.
4. The contact stays pending until the next night.

**Timeline without the fix**

1. The 01:00 run starts with 46,800 changed contacts. The Fairhaven import in TS-77 added 45,600 of them.
2. The 8 workers send about 400 requests per minute. The log shows 398 to 402.
3. Juniper allows 100 per minute per key, so about 300 per minute return 429.
4. Only 100 contacts per minute succeed. 46,800 contacts need 468 minutes, and the deadline is 120 minutes.
5. Backoff only spaces the retries. The ceiling stays at 100 contacts per minute, or 12,000 per run.
6. The job hits `activeDeadlineSeconds: 7200` with 11,940 upserted and 34,860 pending. Sales misses the Friday 09:00 UTC deadline.

**Timeline with the fix**, diverges at step 2.

2. `run_sync` splits the contacts into 468 batches of 100. Each batch is one request against the limit.
3. 4 workers each send a batch call that takes 5 to 7 seconds. That is 34 to 48 requests per minute, well under 100.
4. Each response lists a result per contact. `mark_synced` runs only for the successes.
5. 468 calls across 4 workers take about 14 minutes.
6. The run finishes far inside the deadline. Tonight's 01:00 run on 29 Oct clears the 34,860 pending contacts in about 11 minutes. The two November imports of 40,000 contacts each take about 400 calls.

**What changes**

- `sync/crm_client.py` **:** add `upsert_batch(contacts)`, which posts to `/contacts:batchUpsert` and returns the per-contact results. On a 429 it sleeps for `Retry-After` and retries up to 3 times. Delete `upsert_contact` once nothing calls it.
- `sync/run_sync.py` **:** `sync_one` becomes `sync_batch`. `main` chunks `contacts` into groups of 100 and maps the pool over the chunks. `WORKERS` drops from 8 to 4.

**Recommendation.** Aelita recommends batching because it removes the cause, which is 468 requests for each 46,800 contacts. It costs one code change. Two things can break. The response shape is not documented in `docs/juniper-api.md`, so I will read it from the first real response. A failed contact inside a batch must stay unmarked, which the per-result `mark_synced` handles. Keeping 8 workers would risk about 96 requests per minute at the 5-second batch time, so 4 workers leave margin.

**Why not backoff only.** It cannot raise throughput above 100 contacts per minute. It would also hold each worker for 60 seconds per 429, which wastes the 2-hour window.
