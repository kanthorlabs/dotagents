Backoff alone cannot fix this, because the API allows 100 requests per minute and the sync sends one request per contact. Aelita recommends moving the sync to `POST /v2/contacts:batchUpsert` and keeping a small `Retry-After` retry as a safety net.

**Timeline without the fix**

1. Marketing imports 45,600 Fairhaven leads on 26 October. `changed_contacts` returns 46,800 rows.
2. `run_sync` starts at 01:00 UTC with `WORKERS = 8`. Each worker calls `upsert_contact`, which sends one `PUT` per contact.
3. The log shows about 400 requests per minute against a limit of 100 per minute per key. About 300 per minute return 429.
4. `raise_for_status` raises on the 429. `sync_one` logs a warning and skips `mark_synced`. The contact stays pending.
5. Only 100 requests per minute succeed. The 7,200 s `activeDeadlineSeconds` caps one run at about 12,000 contacts.
6. The job hits its deadline at 02:59:58 with 11,940 upserted and 34,860 pending. Sales misses the Friday 09:00 UTC deadline in TS-77 unless 3 more full runs succeed.

**Timeline with the fix**, diverges at step 2.

2. `run_sync` groups the contacts into batches of 100. That makes 468 calls.
3. Each batch call takes 5 to 7 s. Eight workers send about 80 calls per minute, which is under the limit of 100.
4. `run_sync` reads the per-contact result of each batch. It calls `mark_synced` only for the contacts that succeeded.
5. 468 calls at about 80 per minute take about 6 minutes.
6. The job finishes near 01:07 UTC with 0 pending. A 429 on a batch waits for `Retry-After` and retries.

**What changes**

- `sync/crm_client.py`: add `batch_upsert(contacts)`. It posts to `/contacts:batchUpsert` and returns the per-contact results. On a 429 it sleeps `Retry-After` seconds and retries up to 3 times.
- `sync/run_sync.py`: `sync_one` becomes `sync_batch`. `pool.map` runs over chunks of 100. `mark_synced` runs only for the contacts that succeeded.
- `sync/crm_client.py`: keep `upsert_contact`, with the same retry, for single-contact use.

**Recommendation.** Aelita recommends batching, because it removes the cause. The sync spends one request per contact against a quota of 100 per minute. Batching cuts 46,800 requests to 468. Each of the two November imports of about 40,000 leads takes about 400 calls. The cost is a rewrite of the call path and of the success handling. The retry stays because 8 workers can still reach the limit.

**Why not backoff alone.** Backoff stops the wasted 429 calls, but throughput stays at 100 per minute. Pending contacts clear at about 12,000 per night. Three nights would barely cover 34,860 contacts, with no room for new changes. Each November import would need about 4 nights.

**Alternative: enterprise tier.** It raises the limit to 1,000 requests per minute and costs 1,450 USD per month. The lead time is 3 weeks, so it misses the Friday deadline. It becomes the primary if the batch endpoint proves unusable.
