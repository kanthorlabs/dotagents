Pointing `osprey-reports` at `pg-osprey-2` by itself breaks the job, because the job writes. Aelita recommends reading from the replica and keeping the single write on the primary. That needs three small edits.

**Existing behaviour**

1. `jobs/nightly_report.py` opens one connection from `DATABASE_URL`, which `deploy/cronjob.yaml` fills from `osprey-primary`.
2. `churn_by_plan` in `reports/queries.py` runs `CREATE TEMP TABLE churn_window`. That is a write.
3. `record_run` in `reports/runs.py` runs `INSERT INTO report_runs`. That is also a write.
4. `docs/database.md` says the hot standby rejects every write, including `CREATE TEMP TABLE` and `INSERT`.

**Timeline without the fix**

1. At 01:00 UTC the CronJob starts with `DATABASE_URL` taken from `osprey-replica`.
2. `jobs/nightly_report.py` connects to `pg-osprey-2`.
3. `revenue_by_region` is a plain `SELECT`. It succeeds.
4. `churn_by_plan` runs `CREATE TEMP TABLE churn_window`. `pg-osprey-2` rejects it.
5. The job exits with an error. `restartPolicy: Never` means no retry.
6. No PDF exists and `report_runs` has no row for that day. The nightly report fails.

**Timeline with the fix**, diverges at step 2.

2. `jobs/nightly_report.py` opens a read connection to `pg-osprey-2` and a write connection to `pg-osprey-1`.
3. `revenue_by_region` runs on the replica. It succeeds.
4. `churn_by_plan` runs as one `SELECT` with no temp table. It succeeds on the replica.
5. `write_pdf` writes `nightly-<day>.pdf`.
6. `record_run` inserts one row into `report_runs` on the primary connection. The heavy reads no longer touch the primary.

**What changes**

- `jobs/nightly_report.py`: `main` opens `REPLICA_DATABASE_URL` for the two report queries. It keeps `DATABASE_URL` for `record_run`.
- `reports/queries.py`: delete `CHURN_WINDOW`. `CHURN_BY_PLAN` selects directly from `subscriptions` with the same 30-day filter. `churn_by_plan` runs one statement.
- `deploy/cronjob.yaml`: add env `REPLICA_DATABASE_URL` from secret `osprey-replica`, key `url`. `DATABASE_URL` stays on `osprey-primary`.
- `reports/runs.py`: no change.

**Recommendation.** Aelita recommends the split. The cause is that one connection mixes reads and writes. The split removes the temp table and sends only a single small `INSERT` to the primary.

- **Why it is safe:** `logs/primary-load-2026-10-26.txt` shows the report takes the primary from 31 % to 88 % CPU for 22 minutes. It pushes checkout API p95 from 340 ms to 1,900 ms. All of that is read work, and it moves away.
- **Lag:** p99 lag is 2 seconds. The job reports on yesterday and runs an hour after midnight UTC, so lag cannot hide any invoice.
- **Cost:** the 22-minute read load moves to `pg-osprey-2`, which the dashboards service also uses. Dashboards may slow at 01:00.
- **What can break:** a long query on a hot standby can be cancelled when replication replay conflicts with it. No file in the repo shows the standby's conflict settings. I could not check them, so a cancelled query would fail the job.

**Alternative: keep the temp table and run everything on the primary.** Nothing changes, so it has no migration risk. It does not take any load off the primary. It becomes the primary option if the replica cannot hold the 22-minute queries.

**Alternative: write `report_runs` from a separate step.** The job only reads, and a second job records the run. This gives one connection per process. It costs a new job and a handoff for one `INSERT`. It becomes the primary option if the job's database role must be read-only.
