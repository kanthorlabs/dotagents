Pointing `osprey-nightly-report` at `pg-osprey-2` as is would crash the job, because it writes twice and the hot standby rejects every write. Aelita recommends reading from the replica and keeping one small write on the primary.

**Timeline without the fix**

1. `osprey-nightly-report` starts at 01:00 UTC with `DATABASE_URL` set from `osprey-replica`.
2. `revenue_by_region` runs on `pg-osprey-2` and succeeds, because it only reads.
3. `churn_by_plan` runs `CREATE TEMP TABLE churn_window`. The hot standby rejects it as a write.
4. `main` exits with an exception before `write_pdf`. No PDF exists and `report_runs` has no row.
5. `restartPolicy: Never` means no retry. The nightly report is missing in the morning.

**Timeline with the fix**, diverges at step 3.

3. `churn_by_plan` runs one read-only query with a subquery in place of the temp table. It succeeds on `pg-osprey-2`.
4. `write_pdf` writes `nightly-<day>.pdf`.
5. `record_run` opens a second connection to `pg-osprey-1` and inserts one row into `report_runs`.
6. The job ends. The primary served one `INSERT` instead of 22 minutes of report queries.

**What changes**

- `deploy/cronjob.yaml`: add `REPLICA_DATABASE_URL` from secret `osprey-replica`, key `url`. `DATABASE_URL` stays on `osprey-primary`.
- `jobs/nightly_report.py`: `main` opens a replica connection for the two queries. It opens a primary connection only for `record_run`.
- `reports/queries.py`: `churn_by_plan` currently runs `CREATE TEMP TABLE churn_window`, then selects from it. It will run one query, `WITH churn_window AS (...) SELECT plan, count(*) ...`. The result is the same.

**Recommendation.** Aelita recommends the split. It removes the cause, which is one connection doing both reads and writes. It also removes the load behind `logs/primary-load-2026-10-26.txt`. On 26 October, CPU rose from 31 % to 88 % and checkout API p95 rose from 340 ms to 1,900 ms from 01:00 to 01:22. Replication lag is p99 2 seconds. The job reads yesterday's data at 01:00, so lag cannot change the report. The cost is one extra secret and one extra connection. If `osprey-primary` is unreachable at step 5, the PDF exists but no run row does.

**Unverified.** A long query on a hot standby can be cancelled when replay conflicts with it. No file in the repository shows the standby's `max_standby_streaming_delay`. The first replica run will settle this.

**Alternative: stay on the primary and move the schedule.** Change `schedule: "0 1 * * *"` to an off-peak hour. It needs no code change. It still loads the primary for 22 minutes, and only the timing of the checkout slowdown changes. It becomes the primary option if you do not want the job to depend on the replica.
