Pointing `osprey-nightly-report` at `pg-osprey-2` breaks the job, because it writes to the database and a hot standby rejects every write. Aelita recommends moving the reads to the replica and keeping the one `INSERT` on the primary. That needs a small query rewrite and a second secret.

**Why the primary needs relief.** `logs/primary-load-2026-10-26.txt` shows the job running from 01:00 to 01:22. In that window `pg-osprey-1` CPU rises from 31% to 88%. Checkout API p95 latency rises from 340 ms to 1,900 ms.

**Existing behaviour**

1. `deploy/cronjob.yaml` sets `DATABASE_URL` from secret `osprey-primary`.
2. `jobs/nightly_report.py` opens one connection and uses it for everything.
3. `revenue_by_region` runs a read-only `SELECT`.
4. `churn_by_plan` runs `CREATE TEMP TABLE churn_window`, then a `SELECT` on it.
5. `write_pdf` writes the file.
6. `record_run` runs `INSERT INTO report_runs` and commits.

**Timeline without the fix**, if only the secret changes to `osprey-replica`

1. The cron job starts at 01:00 UTC with `DATABASE_URL` pointing at `pg-osprey-2`.
2. `revenue_by_region` succeeds, because it only reads.
3. `churn_by_plan` runs `CREATE TEMP TABLE`. `docs/database.md` says the hot standby rejects it.
4. The job exits with an error before `write_pdf`. No PDF exists.
5. `restartPolicy: Never` leaves it there. No nightly report for that day.

Even with the temp table gone, `record_run` would fail on the replica at its `INSERT`.

**Timeline with the fix**, diverges at step 1.

1. The cron job starts with `DATABASE_URL` from `osprey-primary` and `REPLICA_URL` from `osprey-replica`.
2. `revenue_by_region` runs on the replica.
3. `churn_by_plan` runs as one `SELECT` with a subquery and no temp table, on the replica.
4. `write_pdf` writes the file as before.
5. `record_run` inserts one row on the primary and commits. The heavy reads no longer touch the primary.

**What changes**

- `deploy/cronjob.yaml`: add env `REPLICA_URL` from secret `osprey-replica`, key `url`. Keep `DATABASE_URL`.
- `jobs/nightly_report.py`: open a replica connection for the two reports. Open a primary connection only for `record_run`.
- `reports/queries.py`: delete `CHURN_WINDOW`. Fold its `WHERE` into a subquery inside `CHURN_BY_PLAN`. `churn_by_plan` then runs one statement.

**Recommendation.** Aelita recommends the split. It removes the heavy reads from `pg-osprey-1` and respects the standby's read-only rule. The cost is a second connection and a query rewrite. The risk is that the report reads data up to 2 seconds old. The p99 lag is 2 seconds and the report covers yesterday, so it only matters if the job ran near midnight. The job runs at 01:00, so this is negligible.

**Alternative: keep the temp table and run `churn_by_plan` on the primary.** The code change is smaller. It beats the recommendation when the churn query is too complex to rewrite safely. It costs part of the load relief, because the churn query stays on the primary.
