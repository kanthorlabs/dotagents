`kestrel-billing` charged 212 subscribers twice because Berlin clocks went back on 25 October, so the 02:30 cron time happened twice. `charge_renewals` has no check for a subscription it already charged that day. Aelita recommends a guard inside the job, because it stops any double fire, not only this one.

**Existing behaviour**

1. `scheduler/clock.py` matches the cron string against local wall-clock time in `Europe/Berlin`.
2. `last_fired` blocks a repeat only within `MIN_GAP_SECONDS = 60`.
3. `billing/renewals.py` selects `renews_on <= today`. It calls `psp.charge`, then inserts a `renewal_charges` row with `settled = false`.
4. `billing/settle.py` moves `renews_on` forward one month. It runs only at 05:00 local.

**Timeline without the fix**

1. At 00:30Z, local time is 02:30+0200. `charge_renewals` fires and charges 212 subscribers through `psp.charge`.
2. At 00:45Z, `send_dunning` sends 41 emails.
3. At 01:00Z, Berlin goes from 03:00 CEST back to 02:00 CET.
4. At 01:30Z, local time is 02:30+0100. Cron `30 2 * * *` matches again. The last fire was 60 minutes ago, so the 60-second gap check passes.
5. `charge_renewals` still finds the same 212 rows, because `renews_on` only moves at 05:00. It does not look at `renewal_charges`, so it charges all 212 again.
6. At 01:45Z, `send_dunning` fires again and sends the same 41 emails.
7. At 04:00Z, `settle_renewals` settles 424 rows, which is two per subscriber.
8. 212 subscribers carry two identical charges dated 25 October.

**Timeline with the fix**, diverges at step 5.

5. `charge_renewals` tries to insert `(subscription_id, today)` for each subscription. All 212 inserts conflict with the rows from step 1, so it skips every charge and returns 0.
6. `send_dunning` still sends 41 duplicate emails.
7. `settle_renewals` settles 212 rows.
8. Each subscriber pays once.

**What changes**

- `billing/renewals.py`: old behaviour is charge first, then insert. New behaviour is `INSERT ... ON CONFLICT DO NOTHING` first, and `psp.charge` only when the insert took effect.
- `renewal_charges` table: add a unique index on `(subscription_id, charged_on)`. Check for existing duplicates before the migration. 25 October has 212 pairs.

**Recommendation.** Aelita recommends the insert-first guard in `charge_renewals`. It makes the job safe on DST changes, scheduler restarts and manual reruns. It costs one migration. If the process dies between the insert and the charge, that subscriber is skipped until the next run. Whether Payrail accepts an idempotency key on `POST /v1/charges` is unverified, and nothing in the repo settles it. The Payrail docs would settle it, and a key would close that gap. This fix leaves the duplicate dunning emails in place.

**Alternative: dedupe in the scheduler.** `scheduler/clock.py` skips a job that already fired for the same local date, or the scheduler runs jobs in UTC. This also fixes the dunning emails and needs no migration. It fails after a restart, because `last_fired` lives in memory. It becomes the primary if the duplicate emails matter more than the charge risk.
