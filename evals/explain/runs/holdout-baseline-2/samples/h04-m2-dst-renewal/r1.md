`kestrel-scheduler` fired `charge_renewals` twice because the Berlin clock showed 02:30 twice on 25 October. Aelita recommends that the scheduler fires each job once per local wall-clock minute. The job code stays as it is.

**Existing behaviour**

1. `scheduler/clock.py` `due_jobs` converts UTC to the job timezone and runs `matches(job.cron, local)`.
2. The only repeat guard is `MIN_GAP_SECONDS = 60`, measured in UTC.
3. `charge_renewals` in `billing/renewals.py` selects every subscription with `renews_on <= today`. It does not mark the subscription as charged.
4. `settle_renewals` moves `renews_on` forward one month. It runs at 05:00 local, after the charge job.

**Timeline without the fix**

1. At 00:30Z, Berlin is 02:30+0200. `charge_renewals` fires and charges 212 subscribers.
2. At 00:45Z, `send_dunning` fires and sends 41 emails.
3. At 01:00Z, Berlin clocks fall back from 03:00 to 02:00 (DST ended that day).
4. At 01:30Z, Berlin shows 02:30+0100. The cron matches again. The UTC gap is 3600 s, so `MIN_GAP_SECONDS` allows it.
5. `charge_renewals` still finds the same 212 rows, because `renews_on` only moves at 05:00. It charges them a second time.
6. At 01:45Z, `send_dunning` also repeats and sends the same 41 emails.
7. `settle_renewals` runs at 04:00Z and settles 424 rows. 212 subscribers now have two identical charges.

**Timeline with the fix**, diverges at step 4.

4. At 01:30Z, Berlin shows 02:30 again. The slot `(2026-10-25, 02:30)` already fired, so `due_jobs` skips it.
5. `charge_renewals` does not run. No second charge occurs.
6. `send_dunning` skips its repeated slot the same way.
7. `settle_renewals` settles 212 rows.

**What changes**

- `scheduler/clock.py`: delete the `MIN_GAP_SECONDS` check. Add a check that skips the job when `last_fired[job.name]` equals `(local.date(), local.hour, local.minute)`.
- `scheduler/loop.py`: old `last_fired[job.name] = now_utc`. New `last_fired[job.name] = (local.date(), local.hour, local.minute)`, with `local` computed before the `due_jobs` call.

**Recommendation.** Aelita recommends the slot key. The root cause is that the scheduler treats a local time as unique. The fix covers all three schedules, including `send_dunning`. It adds no new state. What can break: `last_fired` lives in memory, so a restart inside the repeated hour loses the guard. The spring-forward gap, where 02:30 never exists, still skips the job once a year.

**Alternative: make `charge_renewals` idempotent.** Skip subscriptions that already have a `renewal_charges` row for `today`, and send a per-subscription key to Payrail. It protects against any rerun, including restarts and manual runs. It does not fix `send_dunning`. It becomes the primary if money safety matters more than scheduler correctness. I found no file that shows whether Payrail accepts an idempotency key.
