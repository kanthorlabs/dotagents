`change_password` in `api/auth/password.py` never revokes the refresh tokens of the user's other devices. Aelita recommends deleting all of that user's rows in `refresh_tokens` on password change. The 15-minute access token expiry then meets SR-12 with no change to the middleware.

**Timeline without the fix**

1. Mara logs in on a phone and a laptop. Each device gets a 15-minute access token and a 30-day refresh token. `issue_tokens` stores the refresh hash in `refresh_tokens`.
2. A thief steals the phone.
3. Mara changes the password on the laptop. `change_password` updates `password_hash` and calls `issue_tokens`. It deletes no row.
4. The access token of the thief expires within 15 minutes. The thief calls `POST /auth/refresh` with the phone's refresh token.
5. `refresh_session` finds the row and deletes it. It never checks the password change. It issues a new token pair for the phone.
6. This repeats every 15 minutes for up to 30 days. The stolen phone keeps access after the password change.

**Timeline with the fix**, diverges at step 3.

3. Mara changes the password on the laptop. `change_password` updates `password_hash` and deletes every `refresh_tokens` row of the user. It then calls `issue_tokens` for the laptop.
4. The access token of the thief still works until it expires, at most 15 minutes. The thief calls `POST /auth/refresh`.
5. `refresh_session` finds no row and raises `PermissionError`.
6. The thief is out within 15 minutes. The laptop holds a fresh token pair and stays logged in. This matches both lines of the SR-12 requirement.

**What changes**

- `api/auth/password.py` add `DELETE FROM refresh_tokens WHERE user_id = %s` after the `UPDATE users` and before `issue_tokens`. This also drops the old refresh token of the laptop, which `issue_tokens` replaces.
- `api/auth/middleware.py` and `api/auth/tokens.py` stay unchanged.

**Recommendation.** Aelita recommends the refresh-token delete. The SR-12 limit of 15 minutes equals `ACCESS_TTL`, so no access-token check is needed. It costs one query per password change and nothing per request. Two things can break it:

- **Window:** a `refresh_session` call already in flight on the stolen phone can insert a new row after the delete. That row lives 30 days. The window is a few milliseconds.
- **Atomicity:** the update and the delete should run in one transaction. I did not find the `api.db` transaction API, so the fix has to use whatever it offers.

**Alternative: rotate `SIGNING_KEY`.** This kills every access token at once. It also logs out every user and the laptop of Mara, and it leaves the refresh tokens alive. It fails SR-12 and is dropped.

**Alternative: per-user revocation marker in `quayside-cache`.** The middleware checks Redis on each request. It ends sessions at once and closes the in-flight window. It adds a Redis read to 2,500 requests per second and breaks the rule in `docs/architecture.md` that the middleware reads neither the database nor Redis. It becomes the primary if SR-12 asks for revocation faster than 15 minutes.

**Question.** Does `change_password` delete all refresh tokens of the user and rely on the 15-minute access expiry, or do you want the Redis marker for instant revocation?
