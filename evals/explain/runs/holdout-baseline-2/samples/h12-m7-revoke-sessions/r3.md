`change_password` in `api/auth/password.py` never touches the `refresh_tokens` table, so a stolen phone keeps refreshing its session. Aelita recommends deleting all of the user's refresh tokens in `change_password` before it issues the new pair. That meets SR-12 with no change to the middleware.

**Timeline without the fix**

1. A user's phone holds access token A1, which lasts 15 minutes. It also holds refresh token R1, which has a row in `refresh_tokens`.
2. A thief takes the phone. The user changes the password on the laptop.
3. `change_password` updates `password_hash`. It then calls `issue_tokens` for the laptop, which inserts a new row.
4. `change_password` deletes no row, so the R1 row stays.
5. A1 expires after 15 minutes. The phone calls `POST /auth/refresh` with R1.
6. `refresh_session` deletes the R1 row and loads the user. It never checks the password. It issues a fresh pair with a new 30-day refresh token.
7. The phone repeats step 6 forever. The finding says 30 days, but the refresh window slides, so access never ends.

**Timeline with the fix**, diverges at step 3.

3. `change_password` updates `password_hash`. It then deletes every `refresh_tokens` row of the user.
4. `issue_tokens` inserts the laptop's new row. The laptop stays logged in.
5. A1 still works until it expires, at most 15 minutes. This meets the SR-12 limit.
6. The phone calls `POST /auth/refresh` with R1. No row exists, so `refresh_session` raises `PermissionError`. The phone is logged out.

**What changes**

- `api/auth/password.py`: `change_password` adds `DELETE FROM refresh_tokens WHERE user_id = %s` between the password update and `issue_tokens`.
- `api/auth/tokens.py`: no change.
- `api/auth/middleware.py`: no change. It stays free of database and Redis reads at 2,500 requests per second.

**Recommendation.** Aelita recommends revoking refresh tokens. `ACCESS_TTL` is 15 minutes, which is exactly the SR-12 limit, so no access-token check is needed. The cost is one DELETE per password change.

One race can break it. A refresh in flight can delete its row before the new DELETE runs, then insert a new row after it. The stolen phone then survives once. Running the password update and the DELETE in one transaction narrows this. A `password_changed_at` check in `refresh_session` closes it fully. I did not find whether `db.execute` supports transactions.

**Alternative: check a token version in the middleware.** Store a per-user version in `quayside-cache` and compare it on every request. Other sessions end at once. It adds a Redis read to 2,500 requests per second and breaks the stateless design in `docs/architecture.md`. It becomes the primary if SR-12 later demands immediate logout.
