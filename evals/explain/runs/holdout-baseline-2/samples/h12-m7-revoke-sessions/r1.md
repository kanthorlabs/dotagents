`change_password` in `api/auth/password.py` never touches the other refresh tokens of the user, so a stolen phone refreshes forever. Aelita recommends deleting all `refresh_tokens` rows of the user inside `change_password`. That meets SR-12 with no change to `middleware.py`.

**Existing behaviour**

1. `middleware.authenticate` checks only the JWT signature and `exp`. It reads no database, by design at 2,500 requests per second.
2. `issue_tokens` makes a 15-minute access token (`ACCESS_TTL`) and a 30-day refresh token (`REFRESH_TTL`). It stores the refresh hash with the `device_name`.
3. `refresh_session` deletes the presented refresh row and issues a new pair. It does not look at the password.

**Timeline without the fix**

1. Dana's phone holds refresh token R1 in `refresh_tokens`. A thief steals the phone.
2. Dana changes the password on the laptop. `change_password` updates `password_hash` and inserts a laptop row. The phone row stays.
3. The phone access token expires within 15 minutes.
4. The thief calls `POST /auth/refresh` with R1. `refresh_session` finds a valid row and issues a new pair.
5. This repeats every 15 minutes, and each refresh token lasts another 30 days. The thief keeps access with no end date.

**Timeline with the fix**, diverges at step 2.

2. `change_password` verifies the old password and updates `password_hash`. It deletes every `refresh_tokens` row of Dana. Then `issue_tokens` inserts the laptop row.
3. The phone access token stays valid for 15 minutes at most.
4. The thief calls `POST /auth/refresh` with R1. No row matches, so `refresh_session` raises `PermissionError`. The phone session is over.

**What changes**

- `api/auth/password.py`: in `change_password`, add `db.execute("DELETE FROM refresh_tokens WHERE user_id = %s", user.id)` after the password update and before `issue_tokens`. The laptop still gets a fresh pair, so it stays logged in.

**Recommendation.** Aelita recommends the refresh-token purge. SR-12 allows 15 minutes, and `ACCESS_TTL` is exactly 15 minutes. So cutting the refresh path is enough, and the stateless `middleware.py` stays fast. It costs one `DELETE`. Two things can break it. If the update and the delete are not in one transaction, a failure between them leaves the old sessions alive. I did not find the transaction helper of `api.db`, so use it if one exists. The other risk is that if `ACCESS_TTL` is ever raised above 15 minutes, SR-12 fails silently.

**Alternative: a `token_version` claim checked in middleware.** Each access token carries the user's version, and a password change bumps it. Other devices die at once, not within 15 minutes. It costs a Redis read on every request at 2,500 requests per second. It becomes the primary if the requirement tightens to immediate logout.

**Alternative: rotate `SIGNING_KEY`.** `deploy/secrets.md` says one key serves all users. A rotation would log out every user, including the device that changed the password. That breaks the second SR-12 requirement, so it is not a real option.
